# 11. Merge-driver installation is manual, so clones silently lack it — automate installation like the husky hooks, plus a health check

Status: Proposed — from the 2026-07-01 AI-harness review; NOT implemented. Re-verify file:line before acting.
Decision (2026-07-01, pack owner): revise the documented manual-install stance and AUTOMATE installation, mirroring the existing husky `prepare` precedent. The two-option framing below is resolved; the policy revision is in scope for this leaf.
Lens: ratchet · Area: merge-driver · Severity: high · Size: S · Confidence: high
Theme: baseline-merge-conflicts · Source: Musi AI-harness review 2026-07-01 (multi-agent + Codex second opinion + web research)

## Problem
Git never loads merge-driver commands from committed files; `.gitattributes` only *names* the driver. Every clone (and every contributor) must run `bun run lint:ratchet:install-merge-driver` once, and re-run it after driver/attribute changes. A clone that never ran it gets a raw textual JSON merge of `lint-ratchet.baseline.json` — `<<<<<<<` markers inside generated JSON, no recipe, broken parse — which in the multi-contributor adopting repo was likely the biggest real-world source of baseline merge pain (worse than the refuse-and-recipe behavior of leaf 10, which at least keeps valid JSON and prints instructions). Nothing in the repo detects or warns about the missing/stale driver today.

Correction found during verification: the manual install is a *documented deliberate stance*, not an oversight — `docs/guides/lint-ratchet.md:620-625` says installation is "intentionally manual rather than chained from `prepare` or `worktree:new`: package lifecycle scripts and worktree provisioning should not silently mutate a developer's local Git config." The pack owner reviewed that stance on 2026-07-01 and decided to revise it: the repo already crosses the same line for hooks (`"prepare": "husky"` writes `core.hooksPath` into local git config on every install), and in a multi-contributor repo the silent-textual-conflict failure mode is strictly worse than an automated local-config write. The guide revision lands in the same commit as the automation.

## Evidence
- `/workspace/scripts/git/install-lint-ratchet-merge-driver.sh:37-40,73-78` — writes `merge.lint-ratchet-baseline.*` to local git config, copies the driver to `$(git common dir)/musi/lint-ratchet-baseline-merge-driver.sh`, and mirrors attributes into `.git/info/attributes`. All local-only state.
- `/workspace/package.json:69` — `lint:ratchet:install-merge-driver` exists; `:116` — `"prepare": "husky"` already runs on every install (the natural always-runs seam). `.husky/post-checkout` exists and runs the worktree drift hook — a second candidate seam.
- `/workspace/docs/guides/lint-ratchet.md:605-625` — "Every developer and agent clone must install the local driver config once" + the intentionally-manual rationale; `:661-666` — the documented failure signature of a missing driver (conflict markers, no guidance) and its recovery.
- `/workspace/scripts/doctor.sh` — no merge-driver check exists (verified: zero matches for the driver or `merge.lint-ratchet` in doctor.sh).

## Proposed direction
Two commits, automation first (per the recorded decision):
1. **Automate installation.** Make `install-lint-ratchet-merge-driver.sh` cheaply idempotent (hash-compare the installed copy, the git-config entry, and the `.git/info/attributes` block; no-op with no output when everything is current). Then chain it from the always-runs seams: `prepare` (immediately after `husky`, matching the existing precedent at `package.json:116`) and the existing `.husky/post-checkout`/`post-merge` hooks (so a `git pull` that touches the in-repo driver or attributes refreshes the stale local copy without waiting for the next `bun install`), plus the worktree provisioning path so secondary worktrees are covered from birth. In the same commit, revise `docs/guides/lint-ratchet.md:620-625`: replace the intentionally-manual rationale with the new stance (automated, idempotent, husky-precedent) and keep the manual command documented as the recovery path.
2. **Health check as backstop.** `lint:ratchet:merge-driver:check` — a read-only script that verifies (a) `git config merge.lint-ratchet-baseline.driver` is set, (b) the installed copy exists in the git common dir and its hash matches `scripts/git/lint-ratchet-baseline-merge-driver.sh`, (c) the `.git/info/attributes` block is present and current. Prints one actionable line (`run bun run lint:ratchet:install-merge-driver`) on any miss. Wire it into `doctor.sh` as a WARN section (doctor is the designated read-only aggregator, and `--json` mode gives it a harness-diagnostics finding for free). Still worth having after automation: it catches clones from before the automation landed, environments where `prepare` was skipped (`--ignore-scripts`, some CI images), and verifies the automation itself works.

## Scope / caveats
- Commit 1 carries the policy revision and must update the guide text in the same change; commit 2 is independent and can land either side of it.
- The installer must stay fast and silent on the no-op path — it now runs on every install/checkout/merge; hash comparisons only, no git-config writes unless stale.
- `prepare` also runs in CI and ephemeral clones; the installer is local-config-only and idempotent, so this is harmless — but keep it exit-0 even when git config is read-only (degrade to a warning) so it can never break installs.
- The check and the installer must resolve the git *common* dir (worktrees share it — `install-lint-ratchet-merge-driver.sh:25-31` already shows the pattern) so secondary worktrees report correctly.
- Staleness comparison should hash the file bytes, not mtime; the installed copy legitimately lags after `git pull` touches the in-repo driver, and that is exactly the case the post-checkout/post-merge chaining must catch (guide `:622-625`).
