# 55. activateEncounter never tests its CAS-CONFLICT (double-activate) branch

Status: Proposed — read-only finding from the test-suite audit follow-up; NOT implemented. Re-verify file:line before acting.
Lens: defect-catching · Area: server · Severity: med · Size: S · Confidence: high
Theme: concurrency-coverage · Source: Musi test-suite audit follow-up 2026-06-14 (post-merge re-review, adversarially verified)

## Problem
The merge relocated `activateEncounter` into `services/encounter-combat/` (commit `36cf3b0e` "refactor(server): relocate activateEncounter to encounter-combat service"). The function's own header explicitly cites `docs/CONCURRENCY.md` **Pattern C** (`setEncounterState` compound-WHERE) as the race contract behind step 3, and step 3 is a compare-and-swap that transitions the encounter `setup → active` only if it is *still* in `setup`. That CAS is the entire reason the function fans out through `setEncounterState` rather than a plain `update`: a concurrent (or repeated) activation that already moved the encounter out of `setup` must fail with `CONFLICT`, not silently clobber a running combat.

But the new colocated `activate-encounter.test.ts` covers only **three** cases: the two `BAD_REQUEST` domain guards (no participants; not all initiative rolled) and the happy path (activate from `setup`, assert sorted/`active`). There is **no test for activating an already-non-`setup` encounter** — i.e. activating an encounter twice, or activating one that is already `active` — that asserts the `CONFLICT` rejection. The compound-WHERE matches 0 rows in that case and `setEncounterState` throws `CONFLICT`, but no test drives it. The very concurrency guard the code was designed around (and documents in its header) is unverified.

A regression that weakened the CAS — e.g. dropping `state: from` from the WHERE clause, or swallowing the `result.count === 0` path — would let a double-activate silently re-initialize a live encounter to round 1 / turn 0 (clobbering in-progress combat state) and **no test would catch it**. This is the same defect-class as finding #13 (an untested code path that is the only wiring of a critical branch) and finding #22 (a test that asserts too little to catch the regression it nominally guards), here on brand-new merge-added code that no existing finding covers.

## Proposed direction
Add one test to `activate-encounter.test.ts` that drives the CAS-CONFLICT branch: create an encounter with valid participants (all initiative rolled), then either call `activateEncounter` **twice** and assert the second call rejects, or pre-set the encounter to `active` and activate once and assert it rejects — in both cases asserting the tRPC `CONFLICT` error (the compound-WHERE `updateMany` affecting 0 rows, throwing the `CONFLICT` from `setEncounterState`). Use `.rejects.toMatchObject({ code: "CONFLICT" })`, mirroring the existing `BAD_REQUEST` assertions' shape. Follow `docs/CONCURRENCY.md` Pattern C. Optionally also assert that the encounter's `round`/`currentTurnIndex` were NOT reset on the rejected second call, to pin the "no silent clobber" contract directly.

Use the existing DB-backed harness — the imported `db` from `test-db.ts` and the file's `createCampaign`/`createEncounter`/`createTestUser` fixtures — so the new test exercises the real compound-WHERE update rather than a mock. Coverage strictly increases; no source change.

## Scope / caveats
- One test-file addition (`activate-encounter.test.ts`); **no source change**. The CAS and the `CONFLICT` throw already exist and are correct — this finding closes a coverage gap on an existing branch, it does not change behavior.
- **Keep it DB-backed.** The CAS is a real compound-WHERE `updateMany` whose 0-row outcome is what produces `CONFLICT`; a mocked `tx` would have to re-implement the WHERE/`result.count` logic to produce the rejection, i.e. it would re-implement the system-under-test and prove nothing — see finding #38 for why mocking-and-reimplementing concurrency semantics is discouraged. The existing file is already DB-backed, so this is no new infrastructure.
- Distinct from finding #13 (spell-attack rng seam) and #22 (realtime invalidation assertion) — same defect *class* (untested critical branch / asserts too little), different code. This targets brand-new merge-relocated code (`36cf3b0e`) that no existing audit finding covers.
- Re-verify before acting: confirm `setEncounterState` still throws `CONFLICT` on `result.count === 0` (`encounter-state-mutations.ts:88-93`) and that `activateEncounter`'s step-3 `from: "setup"` is unchanged — the merge that created this gap could be followed by further edits.
