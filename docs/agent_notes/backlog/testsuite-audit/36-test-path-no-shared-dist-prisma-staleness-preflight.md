# 36. Test path has no shared-dist / prisma-client staleness preflight, so a stale build looks like a red suite

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: scripts/ (test-runner provisioning / DX) · Severity: med · Size: S-M · Confidence: high
Theme: provisioning-robustness · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
Running `bun run test` (or `test:changed` / `test:server` / `test:client` / `test:scripts`) against a stale-or-unbuilt `@musi/shared` dist, or a generated Prisma client older than `schema.prisma`, produces dozens of confusing `<X> is not a function` / undefined-import failures with no hint that the cause is an unbuilt workspace dep rather than broken tests. This is not hypothetical: it is the exact artifact that made THIS audit's baseline look like dozens of failing tests (~61 in the audit's own stale-build worktree, an environment-specific figure rather than a reproducible count) when the suite is green at HEAD — the `@musi/shared` dist and the generated Prisma client in the worktree were stale, not the tests.

There is no guard on the test path. `@musi/shared`'s `exports` map resolves every subpath (`./schemas/*.js`, `./rules/*.js`, `./dice/*.js`, `./map/*.js`, `./test/*.js`, `./constants`) to `./dist/**` compiled output, so server, client, and scripts tests import the BUILT dist, not source — 110 `from "@musi/shared"` import sites across 69 server test files alone. `vitest.sh`, `test-changed.sh`, and `test-scripts.sh` contain zero build / freshness / preflight logic. Both `packages/shared/dist` and the generated Prisma client dir are gitignored, so a fresh clone or rebase lacks both until something builds them.

The asymmetry is the tell. The LINT path already guards the identical resolve-from-dist hazard via `scripts/lib/lint-dist-preflight.sh` (wired into `lint.sh:20` and `lint-changed.sh:39`, and reachable through the pre-commit lint slot). But that guard is EXISTENCE-only — it loops `[ -f ]` over a fixed list of sentinel `.d.ts` files — so it catches an unbuilt dist but not a stale-but-present one, which is precisely the scenario that produced the red baseline. Prisma is only half-covered: `prisma-client-freshness.sh` CAN detect staleness (`schema -nt client`), but it only runs from pre-commit's `warn_if_staged_schema_needs_generate`, gated on the schema appearing in `git diff --cached` (staged-only, warn-only). A fresh or rebased worktree where the schema simply moved under you never fires it. And `worktree-db.sh`'s `ensure_dependencies` short-circuits on mere directory presence of `node_modules` + the Prisma client dir, so it never regenerates a stale client and never builds the shared dist at all.

Net: a new dev, a CI lane, or an agent on a fresh or rebased worktree sees a red suite that looks like broken tests but is purely a build-staleness artifact — and nothing in the test entrypoints or docs points at the real cause.

## Evidence
- `packages/shared/package.json:8-32` — the `exports` map resolves `./schemas/*.js`, `./rules/*.js`, `./dice/*.js`, `./map/*.js`, `./test/*.js`, and `./constants` all to `./dist/**` compiled output; tests import the built dist, not source. Both `packages/shared/dist` and `packages/server/src/generated/prisma` are gitignored (verified via `git check-ignore`), so a fresh clone or rebase lacks both until built.
- `scripts/vitest.sh:77-104` — the repo-owned Vitest runner selects `VITEST_CMD` and executes it with no dist / prisma / shared freshness or preflight step (`rg -i 'dist|prisma|shared|freshness|preflight|build'` over the file returns NONE); `bun run test` routes through this script.
- `scripts/lib/lint-dist-preflight.sh:29-33` — the LINT path already guards the identical "resolve `@musi/shared` from `packages/shared/dist`" hazard (wired at `lint.sh:20`, `lint-changed.sh:39`), but it is EXISTENCE-only (`[ -f "$repo_root/$output" ]` over a fixed sentinel list), so it does NOT catch a stale-but-present dist — and no test-path analog exists at all.
- `scripts/test-changed.sh` — no build / dist / prisma / freshness preflight (the only `preflight` hit, line 18, is a code comment about resolving the triple-dot diff's common-ancestor base ref, unrelated to build staleness); `scripts/test-scripts.sh` likewise has no shared-build or prisma:generate step.
- `.husky/pre-commit:69-85` (invoked at line 130) — `warn_if_staged_schema_needs_generate` is the only place `musi_prisma_client_freshness` runs, guarded by a staged-only `git diff --cached … | grep -qx '…schema.prisma'` and warn-only; a rebased or fresh worktree with an unstaged schema delta gets no warning. The freshness helper itself is `scripts/prisma-client-freshness.sh:11` (`[ "$schema" -nt "$client" ]`).
- `scripts/worktree-db.sh:655-658` — `ensure_dependencies` returns early when `node_modules` and the Prisma client DIRECTORY merely exist, so a stale generated client is never regenerated and `@musi/shared` dist is never built (no `filter @musi/shared … build` / `tsc -b` anywhere in `worktree-db.sh`; only `prisma:generate` runs, and only on the cold path at lines 667-671).

## Proposed direction
Give the test path the same staleness preflight the lint path has, but with mtime (not just existence) checks. Add a `scripts/lib/test-dist-preflight.sh`, sourced by `vitest.sh` (and reachable through `test-changed.sh`), that:

- when `packages/shared/dist` outputs are MISSING OR older than `packages/shared/src`, runs `bun run --filter @musi/shared build`; and
- when the generated Prisma client is missing OR `schema.prisma` is `-nt` the client (reuse `musi_prisma_client_freshness` from `scripts/prisma-client-freshness.sh` so the staleness rule stays in one place), runs `bun run --filter @musi/server prisma:generate` —

emitting a one-line `building stale workspace dep before tests` notice so the cause is never silent. Keep both conditions guarded on actual staleness and fast so the common already-built path adds no measurable time; the build/generate only runs when something is genuinely out of date.

At minimum (the low-risk variant), skip the auto-build and instead add an explicit fast FAIL-with-actionable-message guard, plus a `doctor.sh` `check_shared_dist_freshness` / `check_prisma_client_freshness` pair modeled on `check_dependency_freshness` (`doctor.sh:543`, which already drives `musi_dependency_freshness` through `note_pass` / `note_fail` / `note_warn`), and a worktree-drift-hook entry that warns post-checkout / post-merge. Either variant adds provisioning robustness without touching a single test assertion, so suite coverage is strengthened, never weakened.

Estimated impact: eliminates the highest-friction false-red in the suite — the exact artifact that made this audit's baseline look like dozens of failing tests (the audit's own stale-build environment, not a reproducible count) — for every fresh/rebased worktree, CI lane, and agent, turning a multi-minute confused debugging session into a self-explaining (and, in the auto-build variant, self-healing) build step. No per-run speed cost on the already-built common path.

## Scope / caveats
TOUCH: `scripts/vitest.sh`, `scripts/test-changed.sh`, a new `scripts/lib/test-dist-preflight.sh`, `scripts/doctor.sh`, and optionally the worktree-drift hook. NOT-TOUCH: any test assertion or test file — coverage is preserved because nothing the tests check changes; the only addition is ensuring the dep they import is fresh before they run. RISK: low for the fail-fast / doctor variant; the auto-build variant adds a build step to the test entrypoint, so keep it conditional on staleness and fast to avoid slowing the common path. PATH NOTE: the Prisma freshness helper lives at `scripts/prisma-client-freshness.sh` (not under `scripts/lib/`), while the new preflight should live in `scripts/lib/` alongside `lint-dist-preflight.sh`.

This finding folds in the standalone "lint path already guards this" observation: the fix is explicitly to port the lint-path preflight pattern (`scripts/lib/lint-dist-preflight.sh`) to the test path, upgrading existence-only checks to mtime-based ones along the way.

SEQUENCING: standalone; independent of the dedup / test-content findings. BOUNDARY: this is the only non-dedup, non-test-content finding in this lens — a provisioning / DX robustness gap in dogfood tooling (`scripts/**`, weighted above product code), not a test-content issue, and not covered by any of the existing test-content/structure/duplication slugs. SEVERITY rationale: med, not high — it masks the CAUSE of a build artifact and has a manual workaround (rebuild shared + `prisma:generate`); high is reserved for findings that mask genuine test failures or weaken coverage, neither of which applies here.
