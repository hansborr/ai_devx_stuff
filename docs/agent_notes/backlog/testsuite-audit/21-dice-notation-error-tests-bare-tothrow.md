# 21. dice-notation parser error tests use bare `toThrow()` — wrong-branch validation failures pass silently

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: defect-catching · Area: shared · Severity: low · Size: S · Confidence: high
Theme: rules-validation-branch-discrimination · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
`parseDiceNotation` is the front door for every dice expression in the app — attack rolls, damage, custom `/roll` notation, and anything downstream of `packages/shared/src/dice`. It defends itself with several distinct, deliberately specific validation guards, each raising its own message: keep-count below the minimum (`Keep count must be at least 1`), keep-count exceeding the die count (`Keep count (N) cannot exceed die count (M)`), a die with fewer than one side (`Die must have at least 1 side`), more than 1000 sides (`Die cannot have more than 1000 sides`), and more than 100 dice (`Cannot roll more than 100 dice at once`). Inputs that match no dice/flat term at all fall through to a single generic `Invalid dice notation: "..."`.

The 12 error-case tests assert only bare `.toThrow()`. That asserts *that* the parser rejected the input, but not *why*. Because several of these inputs are crafted to exercise one specific guard, a regression that fires the wrong branch — guards reordered or merged, a specific guard collapsed into the generic `Invalid dice notation` fallthrough, or a numeric bound shifted so a different bound rejects first — still leaves every test green. The suite cannot distinguish "rejected for the right reason" from "rejected for any reason," so it silently under-protects the exact discrimination it was written to test. This is a latent test-depth gap, not an active bug: the guards behave correctly today; the tests just wouldn't notice if they stopped.

The discrimination value is uneven. Only `abc` and `xd20` collapse to the generic `Invalid dice notation` message and gain little from tightening — bare `toThrow()` is honest for them (and `4d6k3`/`d` also reach that generic fallthrough). The value sits in the inputs that target a *named* guard with a *distinct* message: `2d6kh3` (keep > count), `4d6kh0` (keep < min), `1d1001` (sides > max), `101d6` (count > max), `1d0` (sides < min), and `-1d6` (negative die count). `-1d6` is a sixth guard-discriminating case, not a generic one: a *leading* `-` is not consumed as a term sign (the sign branch in `splitIntoTerms` requires `i > 0`, which fails at `i = 0`), so it hits the dedicated `else if (ch === "-")` throw at `dice-notation.ts:84`, raising the distinct `Invalid dice notation: negative die count` message — it should be tightened to `toThrow(/negative die count/)`. Empty string and whitespace-only are likewise *not* generic: both hit the dedicated `Dice notation cannot be empty` guard at `dice-notation.ts:25`.

## Evidence
- `packages/shared/src/dice/dice-notation.test.ts:212-260` — the `describe("error cases")` block; `rg -c 'toThrow\(\)'` confirms 12 bare `toThrow()` calls and `rg 'toThrow\(/'` confirms **zero** `toThrow(/.../)` (regex-matched) usages anywhere in `packages/shared/src`.
- `packages/shared/src/dice/dice-notation.test.ts:237-243` — `2d6kh3` (keep > count, line 238) and `4d6kh0` (keep < min, line 242) both asserted with bare `toThrow()`, yet the source raises two different messages at `dice-notation.ts:113-114` vs `:110`.
- `packages/shared/src/dice/dice-notation.test.ts:245-251` — `1d1001` (too many sides, line 246) and `101d6` (too many dice, line 250) both bare; source messages differ at `dice-notation.ts:134` vs `:137`.
- `packages/shared/src/dice/dice-notation.test.ts:230` — `1d0` (zero-sided) bare; hits the distinct `Die must have at least 1 side` guard at `dice-notation.ts:131`.
- `packages/shared/src/dice/dice-notation.ts:109-138` — five separate `throw new Error(...)` guards (lines 110, 113-114, 131, 134, 137) with distinct messages the tests never differentiate; `MIN_KEEP_COUNT`/`MIN_DIE_SIDES`/`MAX_DIE_SIDES`/`MAX_DIE_COUNT` defined at `:7-10`.
- `packages/shared/src/dice/dice-notation.ts:25` — the dedicated `Dice notation cannot be empty` guard that `""` and `"   "` hit (not the generic fallthrough), and `dice-notation.ts:84` — the `else if (ch === "-")` throw raising `Invalid dice notation: negative die count` that a *leading* `-` (e.g. `-1d6`) reaches.
- `packages/shared/src/dice/dice-notation.ts:158` — the generic `Invalid dice notation: "..."` fallthrough that `abc`, `xd20`, `4d6k3`, and `d` land on.

## Proposed direction
Tighten the six guard-discriminating assertions to `toThrow(/fragment/)`, where each fragment is a stable substring of the message that guard raises — e.g. `/cannot exceed die count/` (`2d6kh3`), `/Keep count must be at least/` (`4d6kh0`), `/cannot have more than 1000 sides/` (`1d1001`), `/Cannot roll more than 100 dice/` (`101d6`), `/must have at least 1 side/` (`1d0`), and `/negative die count/` (`-1d6`). Match a fragment, not the whole string, so interpolated values and minor wording tweaks don't churn the test. Leave `abc`, `xd20`, `4d6k3`, and `d` as bare `toThrow()` — they correctly resolve to the generic `Invalid dice notation` fallthrough and have nothing more specific to assert. (Tightening `""`/`"   "` to `/cannot be empty/` is optional and lower-value, since both share the single `Dice notation cannot be empty` guard at `:25`.)

This is purely additive to coverage: every input still must reject (the existing guarantee is preserved), and now six of them must reject *for the documented reason*, closing the wrong-branch blind spot. No source change, no new test cases, no inputs removed. Estimated runtime impact is effectively zero — `toThrow(/.../)` is the same synchronous throw-and-match as `toThrow()`, adding only a regex test against an already-captured error message; no new spec, no new fixture, no measurable wall-clock change.

## Scope / caveats
Touch only `packages/shared/src/dice/dice-notation.test.ts`; do not modify `dice-notation.ts` or any guard wording/ordering (the point is to *pin* the current behavior, not change it). Confine the regex assertions to the six guard-specific cases identified above — resist the urge to add fragments to the truly generic cases (`abc`, `xd20`, `4d6k3`, `d`), where they would be brittle (asserting `Invalid dice notation` couples the test to the fallthrough wording without adding branch value). For completeness, the source also has two guards the test suite does not currently exercise — `Too many groups` (`dice-notation.ts:50`) and the `Dice notation cannot be empty` guard (`:25`) — so the enumeration above is not the full guard set; tightening those is out of scope here. This introduces (rather than drifts from) the stronger `toThrow(/.../)` convention in `packages/shared` — there are currently zero such usages — which is fine, but keep it scoped to this file rather than sweeping it across the package. This finding was tracked under a single source observation (`_mergedFrom` lists the same title) so no separate material is folded in. Low risk: a mechanical assertion tightening with no behavioral change, fully within `packages/shared` (the shared → server → client flow is not engaged). No coverage removed.

Related (post-merge): the merge-new `packages/shared/src/rules/damage-types.test.ts` exhibits the same pattern — 9 bare `toThrow()` calls, zero `toThrow(/.../)`. It is the same shared-package wrong-branch blind spot, so the tightening sweep should include it (still scoped per-file, not a package-wide rule).
