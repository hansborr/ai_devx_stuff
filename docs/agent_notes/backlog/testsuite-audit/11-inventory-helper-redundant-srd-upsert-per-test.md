# 11. inventory-test-helper re-upserts static SRD reference data on every test (already globally seeded + template-cloned)

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: speed · Area: server · Severity: low · Size: S · Confidence: med
Theme: per-test-redundant-work · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
`setupInventoryTestContext` is the per-test fixture for the inventory routers — both `inventory.test.ts` and `inventory-list.test.ts` call it from `beforeEach`. Inside it, `seedMinimalSrd()` fires five sequential `prisma.*.upsert()` calls (`abilityScore`, `species`, `feat`, `background`, `class`) before creating the test character. Every one of those upserts is a no-op against the worker DB the test already runs in.

SRD reference data is seeded exactly once, by `global-setup.ts` (`seed: seedSrd`), into the base test database. Each Vitest worker then gets its own DB via `CREATE DATABASE ... WITH TEMPLATE <seeded base>`, so the seeded SRD rows are physically copied into the clone. `cleanDb()` — run at the top of `setupInventoryTestContext` — deliberately does **not** delete any SRD tables (species, classes, feats, backgrounds, ability scores); its trailing comment states this is intentional because the data is "static reference data seeded once by global-setup.ts." So at the moment `seedMinimalSrd()` runs, all five IDs already exist as PK rows, and each upsert resolves to `update: {}` — a PK-conflict that writes nothing.

The IDs are confirmed present in the global seed: `ability-str` is a literal in `seed-srd.ts`, `class-fighter` is a literal in `seed-srd-classes.ts`, and `species-human` / `feat-alert` / `background-acolyte` are produced at seed time from the SRD JSON `index` fields (`species-${index}`, `feat-${index}`, `background-${index}`), all of which exist in the SRD source data. The strongest proof is the sibling fixtures: `spell-test-helper.ts` and `rest-test-helper.ts` reference `species-human`, `background-acolyte`, and `class-wizard` directly with **zero** per-test upserts and pass — establishing that referencing the globally seeded IDs is the correct, already-load-bearing pattern.

One of the five upserts is dead weight even on its own terms: `ability-str` is never used as a foreign key by this helper. The character it builds writes raw ability numbers inline (`strength: 16`, …) into `stats.create`, so the `abilityScore` row is neither read nor referenced.

The redundant work scales with the suite: `inventory.test.ts` (28 `it()`) + `inventory-list.test.ts` (17 `it()`) = 45 tests × 5 upserts ≈ 225 no-op upsert round-trips per run. The cost is small, but the seeding is also misleading: it implies the inventory tests must establish their own SRD, contradicting the global-seed contract every other server fixture relies on.

- `packages/server/src/test/inventory-test-helper.ts:105` — `const srd = await seedMinimalSrd()` runs inside `setupInventoryTestContext`, which `inventory.test.ts` and `inventory-list.test.ts` both invoke from `beforeEach` (e.g. `inventory-list.test.ts:34-35`). The character built at lines 106-126 uses `stats.create` with raw numbers, so the `ability-str` upsert is never referenced as an FK.
- `packages/server/src/test/global-setup.ts:20` — `prepareTestDb({ dbUrl, seed: seedSrd })` (lines 20-23) seeds SRD reference data once for the base test DB (`seedSrd` imported at line 8 from `../seed/seed-srd.js`).
- `packages/server/src/test/worker-test-database.ts:57` — worker DB is created with `CREATE DATABASE ... WITH TEMPLATE <base>`, so the seeded SRD rows are already present in every worker clone.
- `packages/server/src/test/clean-db.ts:41-42` — comment confirms "SRD reference data (species, classes, etc.) is NOT cleaned between tests … seeded once by global-setup.ts"; no SRD `deleteMany` exists in `cleanDb()`, so the cloned SRD rows survive every test.
- `packages/server/src/seed/seed-srd.ts:71` (`id: "ability-str"`) and `packages/server/src/seed/seed-srd-classes.ts:119` (`id: "class-fighter"`) — literal seeded IDs; `species-human`/`feat-alert` are derived from the SRD JSON `index` fields at seed time in `seed-srd.ts:133`/`208` (`species-${index}`/`feat-${index}`), while `background-acolyte` is derived in `seed-srd-backgrounds.ts:122` (`background-${bg.index}`) — `human`/`alert`/`acolyte` all present in the SRD source data.
- `packages/server/src/test/spell-test-helper.ts:29-31` and `packages/server/src/test/rest-test-helper.ts:33-35` — both reference `species-human`, `background-acolyte`, and `class-wizard` directly with zero per-test upserts (`rg -c "upsert"` → 0 in both), proving the proposed pattern is the established norm.

## Proposed direction
Delete `seedMinimalSrd()` from `inventory-test-helper.ts` and have `setupInventoryTestContext` reference the globally seeded + template-cloned IDs directly when building the character — `speciesId: "species-human"`, `backgroundId: "background-acolyte"`, `classId: "class-fighter"` — mirroring `spell-test-helper.ts` / `rest-test-helper.ts`. The `abilityScore` upsert is dropped outright (unused). If any required ID were ever genuinely missing from the global seed, add it to `seedSrd` once rather than re-upserting it per test.

Coverage is unchanged: the removed upserts write no rows that the cloned DB does not already contain, so every inventory assertion sees exactly the same data. Verify with `bun run test -- packages/server/src/routers/inventory.test.ts` and `bun run test -- packages/server/src/routers/inventory-list.test.ts` (same 28 + 17 cases, same pass counts).

Estimated impact: ~225 fewer upsert round-trips per run; each is a sub-millisecond local-Postgres PK-conflict upsert, so the wall-clock saving is on the order of tens of ms across the suite — minor. The real value is maintainability: removing dead per-test seeding that masks the global-seed contract and that would otherwise be copied into the next helper by example.

## Scope / caveats
Touch only `packages/server/src/test/inventory-test-helper.ts`. Do not modify `global-setup.ts`, `clean-db.ts`, `worker-test-database.ts`, the seed sources, or the two inventory test files (their assertions and `beforeEach` wiring stay as-is). Risk is near-zero: two sibling fixtures already depend on the same seeded IDs (`species-human`, `background-acolyte`), so the contract this finding leans on is already exercised in CI. Before removing, re-confirm each referenced ID is present in the global seed (verified here for all four FK IDs; the fifth, `ability-str`, is removed entirely as unused).

This is intentionally inventory-scoped and small. A merged duplicate of this finding observed the same redundancy under a slightly different phrasing; both reduce to the single `inventory-test-helper.ts` change above. A genuinely larger, separately-tracked follow-up would consolidate the same per-test "minimal SRD upsert" anti-pattern wherever else it appears across server test fixtures and document the seeded-ID contract in one place — but that broader sweep is a distinct finding, not part of this leaf. Coverage is preserved because the removed upserts produce no rows that the template-cloned DB does not already carry.
