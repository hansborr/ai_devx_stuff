# 31. Four codemod fixture-runner tests each carry a byte-identical ~115-line fs/JSON harness with no shared module

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: scripts/codemods (test harness) · Severity: med · Size: M · Confidence: high
Theme: shared-test-fixture-extraction · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
The four codemod fixture-runner tests — `concurrency-guard.test.ts`, `expand-barrel.test.ts`, `structured-logging-fix.test.ts`, and `trpc-shared-schema-codemod.test.ts` — each inline the **same** two helper blocks, copied verbatim. The first is a JSON-metadata validator block (`unknownProperty` / `optionalBoolean` / `requiredStringArray` / `optionalStringArray` / `optionalString`); the second is an fs+stdout block (`copyDirectoryContents` / `relativeFiles` / `expectDirectoriesToMatch` / `withCapturedStdout` / `expectStdout` / `errorMessage` / `throwCapturedError`). On top of those two blocks, all four repeat the identical `tempRoots` `afterEach` drain, and three of them (`concurrency-guard`, `expand-barrel`, `structured-logging-fix`) repeat a byte-identical `fixtureNames` `readdirSync` enumeration.

The duplication is provable, not approximate. The five-function validator block hashes to `c1070d35…` in all four files; the seven-function fs/stdout block hashes to `1845562d…` in all four; the `fixtureNames` block hashes to `b05e48a4…` in the three non-trpc files. That is roughly 43 (validators) + 72 (fs/stdout) lines duplicated per file across two regions — about 115 identical lines each, ~460 lines across the four files for those two universal regions. The `fixtureNames` block (`b05e48a4…`) is byte-identical in only three of the four files (the trpc file has a distinct `fixtureNames(kind)`), so it is a smaller additional win on top of the 460, not part of it. The only genuine per-codemod differences are: the imported `run*` function, the `runTwice` handling (which `concurrency-guard` omits entirely), and the failure assertion — three files assert `toBeInstanceOf(CodemodError)` while `expand-barrel` asserts the weaker `toBeDefined()` plus an `errorMessage` string check and an `expectedRoot` after/before fallback.

Why it matters: this is the repo's highest-weighted, lowest-coverage project (`scripts/**` is the tooling that maintains the rest of the codebase), and there is no shared scripts test-support module for this harness — `scripts/codemods/lib/` holds only production helpers plus one production sibling test (`walk-ts-files.test.ts`), and `scripts/vitest.config.ts` declares no `setupFiles`. So any change to fixture-metadata shape (e.g. a new `case.json` field), or to directory-compare or stdout-capture semantics, must be edited in four places by hand and will silently drift the moment one file is missed. The drift is invisible because every copy still compiles and passes against its own fixtures.

- No shared scripts fixture-runner harness exists: `scripts/codemods/lib/` lists only the `trpc-shared-schema*` production helpers (including the `trpc-shared-schema.ts` barrel — the hyphen-suffix glob does not exclude it), `walk-ts-files.ts`, and `walk-ts-files.test.ts`; none is a fixture-runner harness. `scripts/vitest.config.ts` declares no `setupFiles` — VERIFIED.
- Precedent for the extraction lives in-repo: `scripts/drift-ai/` already uses a `.test-helper.ts` convention (`matcher.test-helper.ts`, `git-log-fixture.test-helper.ts`), so the proposed shared module name fits an established pattern rather than inventing one.

## Proposed direction
Extract one shared module — `scripts/codemods/lib/fixture-runner.test-helper.ts`, matching the existing `drift-ai/*.test-helper.ts` precedent — exporting the metadata validators (`readFixtureMetadata` and its `optional*`/`required*` primitives), `copyFixtureInto(workRoot)` (the `copyDirectoryContents` plus `mkdtempSync`/`tempRoots` lifecycle), `expectDirectoriesToMatch`, `withCapturedStdout`/`expectStdout`/`throwCapturedError`/`errorMessage`, and an `enumerateFixtures(root)` for the shared `fixtureNames` shape. Add a `runFixtureCases(it, { fixtureRoot, run, failure })` driver where `failure` selects between the `errorClass: CodemodError` assertion and the `expand-barrel` variant (`toBeDefined` + `errorMessage` contains + `expectedRoot` after-or-before fallback). Each test then declares only its `run*` binding, fixture root, `runTwice` policy, and failure variant.

Crucially, the driver must accommodate the two real shape differences, not flatten them: (1) `expand-barrel`'s weaker `toBeDefined()` + `errorMessage` path and its `expectedRoot` fallback — a single uniform `errorClass` parameter would silently strengthen that assertion and change what the test protects; (2) `trpc-shared-schema-codemod`'s two-kind parameterization and per-kind `fixtureNames(kind)` — the driver should take the resolved fixture root so the trpc file can call it twice. Keep every `it.each(fixtureNames())(...)` enumeration in the test files so the actual fixture cases (the real assertions) are untouched; only the scaffolding moves into the shared module.

Estimated impact: deletes ~115 byte-identical lines per file across the two regions (~460 lines total once the shared `afterEach`/imports are folded in), and collapses four edit sites for fixture-metadata shape, directory-compare, and stdout-capture semantics down to one. This is a maintainability/drift win, not a runtime win — there is no measurable test-speed change, since the same fs operations run per fixture either way. Coverage is preserved because only scaffolding is hoisted; the `it.each` fixture cases and their assertions are not edited.

## Scope / caveats
TOUCH: the four `scripts/codemods/*.test.ts` files and a new `scripts/codemods/lib/fixture-runner.test-helper.ts`. NOT-TOUCH: the codemod production code, the fixture corpora under `scripts/codemods/fixtures/**`, and the `it.each` enumerations. RISK: low — the validator and fs/stdout regions are provably byte-identical (hashes above); the sole nuances are (a) `expand-barrel`'s distinct failure-assertion variant, which the driver must support rather than force into a uniform `CodemodError` check, and (b) `concurrency-guard`'s absence of `runTwice`, so the driver's `runTwice` must default off. Verify by running the scripts project (`bun run test:scripts:file -- scripts/codemods/<file>.test.ts` per file, or the whole scripts project) and confirming the same per-fixture pass counts before and after.
