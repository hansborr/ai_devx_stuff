# 38. rest-service.test.ts hand-rolls a ~145-line Prisma/$transaction fake that re-implements the optimistic-lock semantics already covered by DB-backed tests

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: server · Severity: low · Size: M · Confidence: high
Theme: mock-reimplements-sut · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
`rest-service.test.ts` mocks Prisma in full. Two hand-built fixtures — `makeMockContext` (~99 lines) and `buildTxForRetry` (~46 lines) — assemble a bag of `vi.fn()` mocks whose `$transaction` immediately invokes the callback with a fake `tx`. (The post-audit merge `692b437a` added identical `encounterParticipant.findMany` + `combatLog.create` mock blocks to **both** builders, growing the very duplication this finding flags.) The problem is not the mocking per se; it is that the fake **re-implements the very behavior under test**. The stats mock manually sets `updatedStats.version = freshStats.version + 1` on every `updateMany`, models optimistic-key matching on `hitDiceUsed` in the class `updateMany`, and returns `version: 2` from `findUniqueOrThrow`. A handful of tests then assert that the SUT *called* `updateMany` with the exact `where: { version: 1 }, data: { version: { increment: 1 } }` shape, rather than asserting an observable state change.

That assertion is a tautology risk. The SUT (`rest-service.ts`) does **not** write that SQL — it delegates to `updateCharacterStatsLocked` (`character-stats-mutations.ts`), which is the sole place that emits `where: { …, version }, data: { …, version: { increment: 1 } }`. `executeShortRest` / `executeLongRest` only pass a mutator callback into that helper. So a rest-service test that pins the version-CAS SQL shape is really asserting `updateCharacterStatsLocked`'s contract by proxy, against a mock the same test file authored — it passes iff the mock and the helper share assumptions, and it would keep passing even if the real lock contract changed underneath. Meanwhile the genuine optimistic-lock behavior is already validated against real Postgres in `character-stats-mutations.test.ts` (version → 2, CAS conflicts) and in the router suites (`rest.test.ts` / `rest-long.test.ts` assert `version === 2` and exercise concurrent lost-update / P2034 paths).

The maintainability cost is the second half: a new developer must read 90+ lines of mock plumbing — including an explicit `eslint-disable` for the helper's untyped return — to understand a rest, and must mentally diff the fake DB against the real one to trust any version-shape assertion. The P2034 retry / broadcast-suppression tests are the exception that justifies keeping a mocked unit: real-Postgres conflict timing is non-deterministic, so deterministic conflict injection there carries real value.

## Proposed direction
Keep the P2034 retry and broadcast-suppression cases as fast mocked units (`rest-service.test.ts:564-587` and the all-retries-fail case below it) — they require controllable conflict injection that is hard to force deterministically against real Postgres. For the pure rest-math cases (HP recovery cap, min-1-per-die, multiclass hit-die distribution, exhaustion clamp, death-save reset, concentration clear), assert on the returned `RestResult` (already the pattern at :541's `toEqual`) and lean on the real-DB router/helper tests for the version/lock behavior, so the mock no longer needs to model version semantics at all. Then drop the SQL-shape assertions at :292-297, :446-454, :464-472 that re-derive the lock contract from the hand-written simulation. Where a mocked unit is retained, collapse `buildTxForRetry` into a parameter of `makeMockContext` (e.g. a `freshVersion`/conflict flag) to eliminate the second fake-`tx` builder and the duplicated `tx` shape.

Estimated impact: removes a tautology-prone DB simulation and ~145 lines of mock plumbing a new dev must decode, and shifts lock-semantics trust onto the real-Postgres router/helper tests that already own it. No runtime saving — these are already fast mocked units; the win is defect-catching honesty and onboarding clarity, not speed. Net: preserve every behavioral assertion (RestResult math, broadcast-once invariant, conflict handling); only stop re-deriving the version-CAS SQL shape.

## Scope / caveats
Single test file (`rest-service.test.ts`), plus optionally a glance at `character-stats-mutations.test.ts` to confirm the version → 2 case stays. The removable assertions are redundancy/brittleness, not incorrectness, so this is low risk and not blocking.

Critical coverage caveat — two unit cases have **no** router equivalent and MUST be retained as mocked units (re-pointed to assert on `RestResult`, not deleted), because the router fixture `setupRestContext` builds a single-class **Wizard** at CON 14 (`rest-test-helper.ts:24-35`):
- multiclass hit-die distribution (`rest-service.test.ts:349`, block ~349-378) — the router never exercises a multiclass character;
- min-1-HP-per-die with negative CON (`rest-service.test.ts:380`, `constitution: 6` at :385) — the router fixture's CON 14 can never drive the `Math.max(1, …)` floor.

By contrast, exhaustion-clamp, death-save reset, and concentration-clear ARE covered against real Postgres in `rest-long.test.ts:102-191`, so leaning those router-ward is safe. Keep the P2034 retry / broadcast-suppression units. Distinct from the other already-filed findings: this is a mock-reimplements-SUT / coupling concern, not a colocation move (cf. codebase-audit slug 34 `saving-throw-tests-misplaced`) and not a duplicate-coverage deletion — every observable behavior stays under test, just sourced from the layer that actually owns it.
