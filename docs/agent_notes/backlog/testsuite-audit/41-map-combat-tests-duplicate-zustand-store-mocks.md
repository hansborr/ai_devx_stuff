# 41. Two big map/combat tests duplicate a verbatim Zustand store-mock factory (vtt-drawer-store + map-canvas-store)

Status: Done — implemented 2026-06-14 (batch 5a)
Lens: maintainability · Area: client · Severity: low · Size: S-M · Confidence: high
Theme: mock-scaffold-duplication · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
`combat-map-panel.test.tsx` and `map-detail-view.test.tsx` each hand-roll two large Zustand store mocks, and both mocks are duplicated between the files. The first is the `vtt-drawer-store` `vi.mock` factory: a `useVttDrawerStore: vi.fn(selector => selector(state))` whose `state` literal lists five data fields plus thirteen hand-stubbed actions (`reset`, `close`, `openCharacter`, `openMonster`, `collapseForCast`, `setCastAtLevel`, `beginCastPlacement`, `setCastTargetTokenId`, `expand`, …), followed by an `INITIAL_STATE` literal. This factory is **byte-for-byte identical** across the two files (a `diff` of the two blocks reports zero differences). The second is the `map-canvas-store` `canvasState` mock — a 51-field object covering `stagePosition`/`stageScale`/`selectedTokenId`/`activeTool`/`gridVisible`/`cellSizePx`, the nested `measurement`/`fogDraw`/`drawing`/`template` sub-objects, and the full set of `vi.fn()` action stubs (`zoomIn`, `resetTransient`, `startFogDraw`, `finalizeTemplate`, `setPlacedCells`, …). Both files reproduce the same field set; one inlines it as a module-level constant, the other rebuilds it inside `setupCanvasStore`.

This matters for maintainability, not correctness. Because each copy manually mirrors the real store's action surface, every new store action silently goes **un-stubbed** in each copy until a test happens to call it and trips over `undefined is not a function`. Adding or renaming a store field means editing both copies in lockstep, and the two are already drifting in structure (constant vs. closure) even though the payload is the same. It is exactly the kind of copy-paste scaffolding that quietly rots: the next person to add a `vtt-drawer-store` action has no signal that two test files need the same stub.

## Evidence
- `packages/client/src/components/campaign/combat/combat-map-panel.test.tsx:24-51` — the `vtt-drawer-store` `vi.mock` factory (`useVttDrawerStore` selector mock with 13 action stubs + `INITIAL_STATE`); `:88-142` — the `canvasState` `map-canvas-store` mock (51 indented fields, confirmed by field count).
- `packages/client/src/components/campaign/maps/map-detail-view.test.tsx:50-77` — the `vtt-drawer-store` `vi.mock` factory; a `diff` against `combat-map-panel.test.tsx:24-51` reports **IDENTICAL**. The same `map-canvas-store` field set is rebuilt inside `setupCanvasStore` at `:117-173`.
- Scope confirmed: `rg -l 'openCharacter: vi.fn()'` and `rg -l 'vi.mock("@/stores/vtt-drawer-store'` each return **only these two files**. The other ~18 `vtt-drawer-store` consumers use the **real** store via `useVttDrawerStore.getState()/.setState()` (e.g. `vtt-action-bar.test.tsx`, `in-vtt-drawer.test.tsx`, `cast-rail.test.tsx`, `confirm-cast-strip.test.tsx`) — none hand-roll the action-stub factory.
- For `map-canvas-store`, `rg -l 'setPlacedCells: vi.fn()'` returns **only these two files**; the third `vi.mock("@/stores/map-canvas-store")` caller — `packages/client/src/components/campaign/tokens/map-token-mutations.test.tsx:69-73` (the `vi.mock` block opens at line 69; `selector({ selectToken: mockSelectToken })` is at line 72) — uses a trivial single-field selector mock and would not use the proposed factory.

## Proposed direction
Add a small shared mock-store helper under `packages/client/src/test/` (the existing test-helper home, alongside `mock-react-konva.tsx`, `mock-trpc.tsx`, the `fixtures-*` files, and `wizard-test-utils.tsx`) — e.g. `buildVttDrawerStoreMock(overrides?)` and `buildMapCanvasStoreMock(overrides?)`, each returning the default state object with `vi.fn()` action stubs and a shallow `overrides` merge. Have each test's `vi.mock` factory delegate to it through the established import-inside-factory pattern already used in both files (`vi.mock("@/lib/trpc.js", async () => { const { createMockTRPCModule } = await import("@/test/mock-trpc.js"); … })`, `combat-map-panel.test.tsx:8`), which respects vitest's `vi.mock` hoisting. Each test keeps its own assertions, its own hoisted `mockResetDrawer`/`mockSelectToken`/`mockResetTransient` spies (passed in via `overrides`), and its own `INITIAL_STATE` re-export needs — only the default state/stub boilerplate is centralized.

Estimated impact: collapses ~130+ lines of duplicated store-mock scaffolding across the two files to a single source of truth, and — the real win — makes new store actions get stubbed in both call sites automatically the moment the helper is extended. This is a maintainability/onboarding fix, not a runtime-speed fix; expect negligible test-time change.

## Scope / caveats
Narrow and low-blast-radius: touch only `combat-map-panel.test.tsx`, `map-detail-view.test.tsx`, and the new `packages/client/src/test/` helper. This is a **2-file verbatim duplication, not a 12/8-file sprawl** — do **not** pull in the ~18 files that use the real `vtt-drawer-store` (`getState`/`setState`) or the third `map-canvas-store` caller (`map-token-mutations.test.tsx`) that uses a trivial single-field selector; they would not use (and in some cases could not use) the proposed factory, and forcing them onto it would add indirection without removing duplication. Use the import-inside-factory pattern to satisfy `vi.mock` hoisting (a bare top-level reference would hoist above the helper import and throw). Pure boilerplate consolidation: zero assertion edits, no source changes, no coverage gap — the same stubs back the same render paths, so coverage is preserved by construction. Verify by re-running both files (`bun run test -- packages/client/src/components/campaign/combat/combat-map-panel.test.tsx` and `… maps/map-detail-view.test.tsx`) for identical pass counts. Distinct from the already-filed drift-ai duplication findings (#24/#26/#27), which cover different surfaces; this is a self-contained client-test mock dedup.
