# 49. lint-ratchet hash const and currentById builder are re-hand-rolled across test files with no shared helper

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: scripts/lint-ratchet/*.test.ts (fixture/builder duplication) · Severity: low · Size: S · Confidence: high
Theme: shared-test-fixture-extraction · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
The `scripts/lint-ratchet/` test suite hand-rolls two genuinely shareable fixtures across files instead of importing them from one place. First, the fixture rule-source-hash constant `const FIXTURE_HASH = \`${LINT_RATCHET_CONFIG_HASH_PREFIX}${"a".repeat(64)}\`` is copied verbatim into three files (`lint-ratchet-summary.test.ts`, `lint-ratchet-zero-baseline.test.ts`, `lint-ratchet-check-registry.test.ts`), and a fourth file (`lint-ratchet-baseline.test.ts`) defines the same value under the name `FIXTURE_RULE_SOURCE_HASH`. Second, the `entries → LintRatchetCurrentById` builder is character-for-character equivalent between `lint-ratchet-summary.test.ts` and `lint-ratchet-zero-baseline.test.ts`: identical name (`currentById`), identical signature (`(entries: readonly [string, readonly [string, LintRatchetCurrentItem][]][]) => LintRatchetCurrentById`), and a functionally identical body that walks `entries` into a `Map<string, Map<...>>` (the only difference is one file's `for` loop has braces and the other's is a one-liner).

This matters because `lint-ratchet` is load-bearing tooling — the ratchet guards every ratcheted-lint promotion in the repo, and its baseline/current shape (`LintRatchetCurrentById`, `LintRatchetRuleSourceHashesById`) is exactly the kind of contract that changes when a ratchet metric is added. Today, any change to that shared fixture shape has to be threaded by hand into each copy of the builder, and the duplicated hash const can silently drift between files — a stale or mistyped copy in one file would weaken that file's guard without any single source of truth flagging it. There is no shared test-fixture module under `scripts/lint-ratchet/` (the only helper there, `debt-log-parse-helpers.ts`, is production parse code, not a test fixture); the `*.test-helper.ts` pattern that would house this already exists and is used next door under `scripts/drift-ai/` (`git-log-fixture.test-helper.ts`, `matcher.test-helper.ts`).

## Evidence
- `scripts/lint-ratchet/lint-ratchet-summary.test.ts:70-78` and `scripts/lint-ratchet/lint-ratchet-zero-baseline.test.ts:66-72` — the genuinely identical `currentById` builder: same name, same `(entries: readonly [string, readonly [string, LintRatchetCurrentItem][]][]) => LintRatchetCurrentById` signature, functionally identical body (summary uses a braced `for`, zero-baseline a one-line `for`). This is the only truly duplicated builder.
- `scripts/lint-ratchet/lint-ratchet-summary.test.ts:19`, `lint-ratchet-zero-baseline.test.ts:27`, `lint-ratchet-check-registry.test.ts:29` — `const FIXTURE_HASH = \`${LINT_RATCHET_CONFIG_HASH_PREFIX}${"a".repeat(64)}\`` copied verbatim; `lint-ratchet-baseline.test.ts:112` defines the identical value as `FIXTURE_RULE_SOURCE_HASH`.
- `scripts/lint-ratchet/lint-ratchet-baseline.test.ts:130-180` — `current()` is a RELATED but DIFFERENT builder (different name, 7-tuple `CurrentPathEntry` signature carrying `firstLine`/`lines`/`perFunction`/`firstMessage`/`firstMessageId`), so it is NOT part of the shared kernel. The original "reimplemented three times with same signature" claim was over-stated — it is two.
- `scripts/lint-ratchet/lint-ratchet-check-registry.test.ts:81-83` — `currentById()` here is a nullary helper returning a hardcoded single-entry map (`new Map([[orphanRatchet.id, new Map()]])`), a distinct signature, also NOT the shared builder.
- `scripts/lint-ratchet/lint-ratchet-output.test.ts:91-178` writes a TypeScript *string* to disk (`writeFixtureRatchetConfig` via `writeFileSync`) for a subprocess fixture and so cannot consume an in-process factory; `scripts/lint-ratchet/lint-ratchet-debt-log-write.test.ts:22-33` uses a bespoke local-source ratchet and spells the same hash as a raw `\`sha256:${"a".repeat(64)}\`` literal at line 35 rather than referencing the `LINT_RATCHET_CONFIG_HASH_PREFIX` const (the prefix const itself resolves to `"sha256:"`, so the resulting value is identical to `FIXTURE_HASH` — the difference is the raw literal, not a different hash). Both must be EXCLUDED from the dedup.
- `scripts/lint-ratchet/` directory — no `*.test-helper.ts` exists (only the production `debt-log-parse-helpers.ts`), while `scripts/drift-ai/` already carries the `*.test-helper.ts` pattern; `LINT_RATCHET_CONFIG_HASH_PREFIX`, `LintRatchetCurrentById`, and `LintRatchetCurrentItem` are all exported from `./lint-ratchet-baseline.js`, so a new helper can re-export the const and house the builder without new surface.

## Proposed direction
Add `scripts/lint-ratchet/lint-ratchet.test-helper.ts` that exports `FIXTURE_HASH` and the `entries → currentById` builder (both re-using the already-exported `LINT_RATCHET_CONFIG_HASH_PREFIX` / `LintRatchetCurrentItem` / `LintRatchetCurrentById` from `lint-ratchet-baseline.ts`), and import them across the files that genuinely share them: the `currentById` builder into `lint-ratchet-summary.test.ts` and `lint-ratchet-zero-baseline.test.ts`, and the hash const into `lint-ratchet-summary.test.ts`, `lint-ratchet-zero-baseline.test.ts`, and `lint-ratchet-check-registry.test.ts` (rename `baseline.test.ts`'s local `FIXTURE_RULE_SOURCE_HASH` to the imported const, or leave it — it is the one file with a richer local `current()` and can keep its own naming). Keep `lint-ratchet-baseline.test.ts`'s 7-tuple `current()` and `lint-ratchet-check-registry.test.ts`'s nullary `currentById()` local — they have distinct signatures and folding them in would force a lossy lowest-common-denominator factory. This is mechanically safe and coverage-preserving: it relocates a Map-building helper and a one-line const, touching zero assertions. Estimated impact is on maintainability, not run-time — it removes the duplicated hash const across three (arguably four) files and the exact `currentById` builder across two, so a future ratchet-shape change updates one helper instead of several, removing the path by which a stale copy silently weakens a guard on load-bearing tooling. Verify by running the touched files (`bun run test:scripts:file -- scripts/lint-ratchet/lint-ratchet-summary.test.ts`, `... lint-ratchet-zero-baseline.test.ts`, `... lint-ratchet-check-registry.test.ts`) — same pass counts, no assertion edits.

## Scope / caveats
TOUCH: `lint-ratchet-summary.test.ts`, `lint-ratchet-zero-baseline.test.ts`, `lint-ratchet-check-registry.test.ts`, and a new `scripts/lint-ratchet/lint-ratchet.test-helper.ts`. NOT-TOUCH: `lint-ratchet-baseline.test.ts`'s `current()` (distinct 7-tuple signature), `lint-ratchet-check-registry.test.ts`'s nullary `currentById()`, `lint-ratchet-output.test.ts` (writes TS source as a string for a subprocess — cannot consume an in-process factory), and `lint-ratchet-debt-log-write.test.ts` (bespoke local-source ratchet + raw `sha256:` literal instead of the exported prefix const, though the resulting hash value is the same). Including any of those excluded files would be a category error, not a dedup. Risk: low; the scope is narrow and assertion-free. Severity/size were lowered to low/S from the candidate's med/M after re-verification showed the genuinely shared surface is narrower than first claimed — a hash const plus one builder, not a six-file ratchet-fixture family (this finding folds in `_mergedFrom`: "Per-file LintRatchetConfig fixture + currentById/current builder + ruleSourceHashes Map are re-hand-rolled across 6 lint-ratchet test files"; the per-file `LintRatchetConfig` objects and `ruleSourceHashes` Maps are NOT character-equivalent across files and are intentionally excluded). Sequencing: independent; this is the DOMAIN-FIXTURE half of lint-ratchet dedup. The TMP-DIR half (`writeBaselineFixture` / `tempDebtLog` / `tempRoots`) is a separate, merged cross-cutting scripts-tmp-repo finding and could co-locate since it lands in the same package, but neither blocks the other. Not covered by any of the existing testsuite-audit slugs.
