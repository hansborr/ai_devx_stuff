# 14. RuleTester invalid cases never assert map-selected `{{placeholder}}` substitution, so wrong helper/suggestion mappings ship green

Status: Done — both RuleTester files now assert the interpolated `data:` payload alongside `messageId`.
Lens: defect-catching · Area: eslint-rules · Severity: med · Size: S-M · Confidence: high
Theme: untested map-driven diagnostic guidance · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
Two local lint rules build their actionable repair instruction by looking up a value in a map keyed on the offending delegate/event, then interpolate that selected value into the diagnostic message. In `concurrency-guard`, the violation message ends with `How to fix: {{suggestion}}`, where `{{suggestion}}` is `DIRECT_WRITE_SUGGESTIONS.get(target.delegate)` — one of five distinct repair strings (e.g. `encounterParticipant` → "Use updateParticipantStatsLocked..."). In `socket-registry-broadcasts`, the message names `{{helper}}`, selected as `REGISTRY_OWNED_EVENTS.get(eventName)` — one of seven event→helper pairs (e.g. `map:tokenUpdated` → "broadcastMapTokenUpdate(...)"). That map-selected value *is* the text the developer is told to apply; if it points at the wrong helper, the rule fires correctly but tells the author to do the wrong thing.

Yet not one RuleTester invalid case asserts the substituted output. Every invalid case pins only `messageId` (`"noDirectWrite"` / `"noDirectEmit"`), and the lone regex case in `concurrency-guard.test.js` anchors on the trailing `codemod:concurrency-guard -- <file>` prose — which renders *after* `{{suggestion}}` in the template — so its `.*` never spans the suggestion text. The complementary `message-guidance.test.js` suite iterates `entry.rule.meta.messages` as *raw* template strings with `{{placeholder}}` unsubstituted, so it structurally cannot validate runtime substitution either. The net effect: the map-selection logic that distinguishes one delegate/event from another — exactly the part most likely to be mis-edited when these maps grow — is entirely unguarded. If `characterSpellSlot` were remapped to a rest helper, or `map:tokenUpdated` to `broadcastCampaignUpdate`, the whole suite would stay green while the rule confidently hands developers wrong repair guidance. For two dogfood lint rules that exist to teach correct concurrency/broadcast boundaries, a silent-wrong-advice failure mode defeats their purpose.

## Evidence
- `eslint-rules/concurrency-guard.js:22-40` — `DIRECT_WRITE_SUGGESTIONS` map of 5 delegate→helper repair strings (`characterStats`, `encounterParticipant`, `encounter`, `characterSpellSlot`, `characterClass`); selected via `.get(target.delegate)` and interpolated as `{{suggestion}}` at `concurrency-guard.js:134` (used in the `noDirectWrite` template at `:113`).
- `eslint-rules/concurrency-guard.test.js:49,54,62` — three invalid cases assert only `messageId: "noDirectWrite"`; the fourth (`:44`) uses `message: /codemod:concurrency-guard -- <file>.*docs\/CONCURRENCY\.md/u`, whose anchor sits *after* the `{{suggestion}}` slot in the template, so its `.*` covers only post-anchor prose and never pins the suggestion text.
- `eslint-rules/socket-registry-broadcasts.js:11-19` — `REGISTRY_OWNED_EVENT_HELPERS` (7 event→helper pairs), wrapped into the `REGISTRY_OWNED_EVENTS` map at `:21`; selected via `.get(eventName)` at `:78`, passed into report `data` at `:84` (template placeholder `{{helper}}` at `:59`).
- `eslint-rules/socket-registry-broadcasts.test.js:100,105,110,115` — all four invalid cases assert only `messageId: "noDirectEmit"`, never the helper text. The drift-guard at `:61-65` imports the map but maps to `[eventName]` (keys only, `:62`), so it pins event names against the registry yet drops every helper *value*.
- `eslint-rules/message-guidance.test.js:136` — iterates `messageEntriesFor(entry)`, which returns `Object.entries(entry.rule.meta.messages)` (`:85-90`) — raw template strings with placeholders unsubstituted — so it cannot validate runtime substitution. Contrast `eslint-rules/max-lines.test.js:44-46`, the in-repo precedent that asserts a fully-substituted runtime message via a `message:` literal ("3 effective lines, above the 2 line limit").

## Proposed direction
In the invalid cases for `concurrency-guard` and `socket-registry-broadcasts`, augment the bare `messageId` assertions with the interpolated value — RuleTester verifies a `data` object against the reported diagnostic, so add `data: { suggestion: ... }` / `data: { helper: ... }` (or, equivalently, a `message:` regex/literal that includes the selected helper/suggestion). Cover at least one representative entry per distinct map value so the map-selection branch is pinned across ~9 entries (5 suggestions + 7 helpers, less the overlap already exercised by existing invalid cases). Keep every existing `messageId` assertion in place (coverage-preserving) and *add* the `data` pin alongside it (coverage-strengthening) — follow the asserted-substitution precedent at `max-lines.test.js:45`. This is purely additive test work; no rule source, harness, or message template changes. Estimated impact: closes a silent false-negative window where a mis-edited map value — the actual repair instruction shown to developers — ships undetected for two dogfood lint rules. No speed impact (a handful of extra assertions on cases that already run).

## Scope / caveats
Touch only the two rule test files (`eslint-rules/concurrency-guard.test.js` and `eslint-rules/socket-registry-broadcasts.test.js`); do not modify rule source, the maps, the message templates, or the shared `message-guidance` harness. Risk is low — additive assertions on already-firing cases. This sits in the eslint-rules dogfood/tooling tier, so the lowest coverage thresholds apply, but the maps *are* the rule's product surface and warrant the pin. No overlap with the 37 existing codebase-audit slugs (none touch `eslint-rules`). It is distinct from the other two eslint-rules findings in this pack: this one asserts interpolated VALUES, the registry-completeness finding keeps the LISTS in lockstep (the drift-guard at `socket-registry-broadcasts.test.js:61-65`), and the runTwice finding covers codemod idempotence — no functional overlap, though all three live in the same two test files and should land in a coordinated edit to avoid churn. The candidate write-up's claim about the `:44` regex was corrected during verification: the `.*` does not span `{{suggestion}}` because the suggestion renders *before* the regex anchor in the template — conclusion unchanged.
