# 45. GitRunner rev-parse stub is hand-rolled across drift-ai test files while a cleaner record-based makeStubGit sits file-private

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: scripts/drift-ai (tooling/dogfood) · Severity: low · Size: S · Confidence: high
Theme: shared-test-fixture-extraction · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
The command-level drift-ai tests inject a fake `GitRunner` to make repo-root resolution deterministic, and every one of them re-implements the same tiny dispatcher by hand: answer `rev-parse --show-toplevel` with `${repoRoot}\n`, then `throw new Error(\`unexpected git invocation: git ...\`)` for anything else. That two-branch shape is copied — with cosmetic variation between `args.join(" ")` and a hoisted `key` local — into `harness-freshness.test.ts`, `semgrep-candidates-command.test.ts`, `coldspots.test.ts`, `hotspots.test.ts`, and again in the top-level `scripts/drift-ai.test.ts`, plus several more inline rev-parse copies inside those same files (`coldspots.test.ts:318`, `hotspots.test.ts:369` and `:396`). The throw string `"unexpected git invocation: git ..."` alone appears at 17 sites under `scripts/`.

Meanwhile the strictly-better generalization already exists. `prototype-subcommands.test.ts:29-39` writes `makeStubGit(responses: Record<string, string>)` (look up `args.join(" ")` in a response map, else throw the standard error) plus a one-line `makeCurrentGit(repoRoot)` built on top of it — so `prototype-subcommands.test.ts` is itself the 6th rev-parse-resolving file (it holds the canonical `makeStubGit`) — and the *identical* `makeStubGit` is re-typed verbatim in `scripts/drift-ai.test.ts:147`. Both copies are file-private; nobody outside their file can reuse them. So the same git-stub contract is expressed several slightly different ways across five-plus files, and the toplevel-response value or the unexpected-invocation throw message can drift between suites with nothing to keep them in lockstep.

This is a tooling/dogfood file (`scripts/drift-ai` is the repo's own drift sensor), so the duplication weighs more than the same pattern would in product test code — but it is pure test-ergonomics with no correctness exposure, hence low severity. Notably the sibling `git-log-fixture.test-helper.ts` already documents the exact precedent for this fix in its header ("the tests previously re-derived this layout by hand in ~9 files ... This helper is the single source"), so the extraction home and convention are established.

## Evidence
- `scripts/drift-ai/harness-freshness.test.ts:188-194` — `gitAtEmptyRepo()` hand-rolls the stub inline (`if (args.join(" ") === "rev-parse --show-toplevel") return \`${repoRoot}\n\`;` then the standard throw at `:192`).
- `scripts/drift-ai/semgrep-candidates-command.test.ts:28-33` — `makeCurrentGit(repoRoot)` is the identical rev-parse-only stub, throw at `:31`.
- `scripts/drift-ai/coldspots.test.ts:46-58` — `coldspotsGit` is the same stub extended with a `--since=` window branch (throw at `:56`); a second standalone rev-parse copy lives in `markerStaticGitResponse` at `:318`.
- `scripts/drift-ai/hotspots.test.ts:38-50` — `hotspotsGit` is the same stub extended with `log`/`-G` suppression branches (throw at `:48`); two more inline rev-parse copies at `:369` and `:396`.
- `scripts/drift-ai/prototype-subcommands.test.ts:29-39` — the reusable `makeStubGit(responses: Record<string,string>)` (throw at `:33`) + `makeCurrentGit(repoRoot)` the others should share, but file-private; verbatim-reinvented at `scripts/drift-ai.test.ts:147-153`.
- Pattern total: the throw string `"unexpected git invocation: git ..."` occurs at 17 sites across `scripts/` (rg) — `drift-ai.test.ts` alone holds 7 of them (lines 151, 764, 785, 800, 814, 1481, 1918), so the duplication is concentrated in that one top-level file. A rev-parse-resolving `GitRunner` stub appears in the 6 cited drift-ai test files (harness-freshness, semgrep-candidates-command, coldspots, hotspots, prototype-subcommands, `drift-ai.test.ts`); two further files (`coldspots-blame.test.ts:38`, `hotspots-suppression-churn.test.ts:43`) share only the `unexpected git invocation` throw string, not the rev-parse branch.
- `scripts/drift-ai/git-log-fixture.test-helper.ts:1-83` — the existing, established home for shared drift-ai git-fixture builders; its header documents the same "hand-rolled in ~N files → one helper" consolidation precedent.

## Proposed direction
Promote `makeStubGit(responses: Record<string, string>)` and a thin `currentRepoGit(root: string)` convenience (the `{ "rev-parse --show-toplevel": \`${root}\n\` }` case) into the existing `git-log-fixture.test-helper.ts` (or a sibling `git-runner.test-helper.ts` if you prefer to keep the log-format builder separate from the dispatcher), then delete the two file-private `makeStubGit` copies in `prototype-subcommands.test.ts` and `scripts/drift-ai.test.ts` in favor of the export. Have the rev-parse-only stubs (`harness-freshness.test.ts`'s `gitAtEmptyRepo`, `semgrep-candidates-command.test.ts`'s `makeCurrentGit`) call `currentRepoGit(repoRoot)` directly — each collapses to a one-liner.

For `coldspots.test.ts`/`hotspots.test.ts`, do **not** force them into the flat `Record<string, string>` form: their stubs parse a `--since=` window argument and branch on `-G`, which a static key→value map cannot express. The realistic shape there is a small procedural base from the helper — e.g. a `withFallback(repoRoot, handler)` that answers `rev-parse --show-toplevel` and emits the shared throw on a miss, wrapping the call site's own `log` logic — or simply leaving those two files inline if the procedural wrapper is not clearly cleaner. The gain for them is only the rev-parse line + the throw string; the window/`-G` logic stays inline. Behavior-preserving throughout: same return values, same throw on unexpected invocations, no assertion changes.

Estimated impact: a single source of truth for the git-stub contract (the toplevel response shape and the `"unexpected git invocation"` error string), so any future change to how drift-ai shells out to git for repo-root resolution is reflected in one helper instead of five-plus divergent copies; the two rev-parse-only stub functions collapse to one line each, and the two duplicate `makeStubGit` definitions become one export. No measurable run-time change — this is maintainability/onboarding, not speed.

## Scope / caveats
TOUCH: the cited drift-ai test files (`harness-freshness`, `semgrep-candidates-command`, `coldspots`, `hotspots`, `prototype-subcommands`, and `scripts/drift-ai.test.ts`) plus `git-log-fixture.test-helper.ts` (or a new sibling helper). NOT-TOUCH: any assertions, and any drift-ai production code (`hotspots-history.ts`, the subcommand sources, the `GitRunner` type). RISK: trivial for the pure rev-parse-only files (mechanical one-line swap); for `coldspots`/`hotspots` the win is bounded to the rev-parse line and the throw — their window-parsing and `-G` branching must stay inline because a flat `Record<string, string>` cannot model them, so do not over-fit the record shape onto them.

Coverage is preserved because every call site keeps the same observable stub behavior; verify with `bun run test:scripts:file -- scripts/drift-ai/<file>.test.ts` for each touched file (same pass counts, zero assertion edits).

SEQUENCING: independent of the cross-cutting tmp-dir / `mkdtempSync` scaffold finding, though both live in `scripts/` and could share the same helper module; this one is the `GitRunner` *dispatch contract* (what git args return what / what throws), whereas that one is fs lifecycle, so keep them as distinct changes. The throw-string "drift" risk is today only cosmetic — `${key}` and `${args.join(" ")}` render identically — so the consolidation is about preventing future divergence, not fixing a present bug.
