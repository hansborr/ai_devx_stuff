# 37. Page/route tests hand-duplicate react-router Link/useNavigate and useAuth mock scaffolding across ~13 files with no shared helper

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: client · Severity: low · Size: M · Confidence: high
Theme: mock-scaffold-duplication · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
Every client page/route test re-declares the same two mock blocks by hand. The first is a `vi.mock("@tanstack/react-router", ...)` block carrying an inline `Link: ({ children, to }) => <a href={to}>{children}</a>` stub plus per-test `useNavigate`/`useSearch`/`useParams` overrides. The second is a `vi.mock("../hooks/use-auth", ...)` block returning a hand-typed copy of the auth-hook shape filled with throwaway `vi.fn()`s. Neither has a shared helper, despite the same `packages/client/src/test/` directory already housing ~25 fixtures-* / mock-trpc-* / render-helper helpers — so the convention is "share your test scaffolding" everywhere except these two mocks.

Because each copy is hand-written, the shapes drift, and they drift *silently*. The real `AuthContextValue` has 7 fields (`user`, `isLoading`, `isAuthenticated`, `login`, `register`, `logout`, `refreshUser`), but most page mocks return only 6 — they omit `refreshUser`. Only `settings-page.test.tsx` includes it (because that page actually calls it), proving the field set is being guessed per-file from what the component happens to touch rather than from the hook contract. The `Link` stub drifts too: the minimal variant ignores `params`/`className`, while `dashboard-page.test.tsx` grew a richer variant that resolves `$campaignId` from `params` and forwards `className`. A new contributor writing a page test has no canonical stub to copy, so they pick one of the existing variants and re-guess which auth fields and which Link props matter — and a future change to the auth hook or router API silently fails to reach the incomplete mocks. A router API change today means editing 9+ files; an auth-hook signature change means editing 13.

## Evidence
- `packages/client/src/pages/login-page.test.tsx:12-33` — `vi.mock("../hooks/use-auth")` returns a 6-field shape (no `refreshUser`) with throwaway `vi.fn()`s (lines 12-21), then the inline `Link: ({ children, to }) => <a href={to}>` minimal stub plus `useNavigate`/`useSearch` overrides (lines 23-33).
- `packages/client/src/pages/dashboard-page.test.tsx:26-46` — the drifted Link variant: it additionally accepts `params`/`className`, resolves `to.replace("$campaignId", params?.campaignId ?? "")`, and forwards `className` — a richer stub than login's, with no shared origin.
- `packages/client/src/pages/settings-page.test.tsx:11-21` — the only `useAuth` mock that includes `refreshUser` (line 19), proving the shape is hand-guessed per file rather than derived from the hook contract.
- `packages/client/src/hooks/auth-context.tsx:25-33` — the real `AuthContextValue` interface declares all 7 fields incl. `refreshUser`; the value object is assembled at lines 113-121. Most page mocks return only 6, so they are silently incomplete relative to the real hook.
- Pattern counts (rg, re-verified at HEAD): the inline `Link: ({ children` stub appears in **9** client test files (`character-create-page`, `register-page`, `campaign-detail-page`, `login-page`, `homebrew-page`, `collection-detail-page`, `app-header`, `members-panel`, `collection-card`); `vi.mock(...hooks/use-auth)` appears in **13** client test files. No `mock-router.*` or `mock-auth.*` helper exists under `packages/client/src/test/` (directory listed — 25 helpers present, none for router or auth).

## Proposed direction
Pure refactor; assertions and coverage unchanged. Add two helpers under `packages/client/src/test/`:

1. `mock-router.tsx` — a `mockReactRouter({ navigate, search, params })` factory that spreads `importOriginal` and overrides `useNavigate`/`useSearch`/`useParams`, plus a single canonical **superset** `Link` stub that handles `to` + `params` (`$param` substitution) + `className` + `search`. This superset covers both real variants (the plain `<a href={to}>` and dashboard's params/className-resolving form), so adopting it strengthens the minimal stubs rather than weakening the rich one.
2. `mock-auth.ts` — a `mockUseAuth(overrides)` factory returning the full 7-field hook shape (with `refreshUser` included), so every adopter is complete-by-construction and a future auth-hook field addition is a one-line change in the helper instead of a 13-file sweep.

Tests `vi.mock` against the helper and keep per-test variation through `vi.hoisted` refs (the existing `mockNavigate`/`authState` pattern). Estimated impact: removes ~15-25 lines of boilerplate per file, ends the silent `refreshUser`-shaped drift, and turns "router/auth API change edits 9-13 files" into "edits one helper." No behavioral change to any component; the only test-observable difference is that previously-incomplete auth mocks become complete, which can only surface latent reliance on a missing field (a coverage gain, not a loss).

## Scope / caveats
Scope the full-shape `mockUseAuth(overrides)` static factory to the ~6 files that already use the full-shape `vi.fn(() => ({...}))` pattern: `login-page`, `register-page`, `dashboard-page`, `settings-page`, `campaign-detail-page`, `character-create-page` (all re-verified to return the 6-field shape, settings being the 7-field outlier). Do **not** force the factory onto the other adopters:
- The injection-pattern files — `auth-guard.test.tsx`, `guest-guard.test.tsx`, `app-header.test.tsx` — drive `useAuth` via `vi.mocked(...).mockReturnValue(...)` per-test with minimal shapes; they need a thin `mockReturnValue`-friendly path, not a static factory.
- The deliberate minimal `{ user }` stubs — `map-detail-view.test.tsx:88`, `combat-map-panel.test.tsx:73` (`useAuth: () => ({ user: { id: "user-test" } })`), and `join-page.test.tsx:60` (`useAuth: () => ({ user: authState.user })`) — intentionally assert against a one-field shape; leave them, or give them a separate thin helper. Forcing the full shape here adds noise without value.

The `Link` stub has two real variants today (plain vs. params/className/search-resolving); a single canonical superset stub covers both, so the migration is mechanical. Low risk, pure refactor, no coverage stakes — verify by running the touched files (`bun run test -- packages/client/src/pages/...`) and confirming identical pass counts. This pairs with already-filed codebase-audit #22 (`22-test-helper-dirs-no-orientation.md`): that finding adds an orientation doc for `packages/client/src/test/`, and the two new helpers here should be listed in it. This is a duplication/maintainability finding, not a bug or dead-code finding — the mocks work today; they are merely hand-copied and drift-prone.
