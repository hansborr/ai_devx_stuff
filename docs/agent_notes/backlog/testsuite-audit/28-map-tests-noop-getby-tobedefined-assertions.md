# 28. Tautological `getBy*().toBeDefined()/toBeTruthy()` assertions in template/fog map tests

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: defect-catching · Area: client · Severity: low · Size: XS · Confidence: high
Theme: assertion-hygiene · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
Several of the map-rendering tests assert `expect(screen.getByLabelText(...)).toBeDefined()` or `expect(getByTestId(...)).toBeTruthy()`. Testing-Library `getBy*` queries throw synchronously when the element is missing (or when more than one matches), so by the time the chained `.toBeDefined()`/`.toBeTruthy()` runs, the query has already either thrown or returned a real `HTMLElement`. An `HTMLElement` is always defined and always truthy, so the tail assertion can never fail on its own — the query *is* the gate, and the matcher adds nothing. These are no-op tail assertions: they document intent ("this button exists") but verify nothing beyond what the query already enforced, and notably do not check DOM attachment or visibility the way `toBeInTheDocument()` would.

The cost is small but real for onboarding and for the defect-catching story we tell about these files: a reader skimming the suite sees an `expect(...)` per element and assumes each is a meaningful guard, when most are inert. The one place this actually matters is `template-toolbar.test.tsx`'s `"highlights active template button"` case, which renders with `activeTool="template-sphere"`, re-queries the sphere button, and then only asserts the element is defined — it never checks that the button is in fact highlighted. The test's name promises an active-state assertion the body does not make, so a regression that stopped highlighting the active tool would sail through green.

## Evidence
- `packages/client/src/components/campaign/maps/template-toolbar.test.tsx:16-20,38-40` — 8 inline `getByLabelText(...).toBeDefined()` assertions across `"renders all 5 shape buttons"` (lines 16-20) and `"shows size presets when a template tool is active"` (lines 38-40); the `getByLabelText` query is the only real check on each line.
- `packages/client/src/components/campaign/maps/template-toolbar.test.tsx:30-34` — `"highlights active template button"` renders with `activeTool="template-sphere"`, then `const sphereBtn = screen.getByLabelText("Sphere template")` followed by `expect(sphereBtn).toBeDefined()`; the active/highlighted state the test name promises is never asserted.
- `packages/client/src/components/campaign/maps/fog-overlay.test.tsx:31,65,257,269` — four `expect(getByTestId(...)).toBeTruthy()` assertions on mocked konva nodes (`konva-shape` at 31/65, `konva-rect` at 257/269).
- `packages/client/src/components/campaign/maps/template-overlay.test.tsx:48` — `expect(screen.getByTestId("template-origin")).toBeDefined()`.
- Pattern count: across the three files there are **13 chained `getBy*(...).toBeDefined()/.toBeTruthy()` tail matchers** — 8 in `template-toolbar.test.tsx` (lines 16-20, 38-40), 4 in `fog-overlay.test.tsx` (lines 31, 65, 257, 269, all on `getByTestId`), 1 in `template-overlay.test.tsx` (line 48). Counting the `sphereBtn` variable assertion (line 33) and the two `container.firstChild` checks (`fog-overlay.test.tsx` lines 24, 42) brings the all-`.toBeDefined()/.toBeTruthy()` total to 16; this doc uses the strict chained-`getBy*()` definition (13) throughout.
- `packages/client/src/test/setup.ts:1` — `import "@testing-library/jest-dom/vitest";` is loaded globally, so `toBeInTheDocument()` is available everywhere; the prevailing sibling-file style already uses it heavily (`map-toolbar.test.tsx` 24 occurrences, `maps-panel.test.tsx` 16 occurrences).

## Proposed direction
Swap each `getBy*(...).toBeDefined()/.toBeTruthy()` tail matcher for `.toBeInTheDocument()` (jest-dom), so the assertion reads as an explicit presence/attachment check and matches the dominant style in the neighbouring map tests. This is a mechanical 1:1 replacement on the cited lines and does not change what passes or fails for the simple "element exists" cases — the `getBy*` query was, and remains, the gate.

The genuine coverage win is the `"highlights active template button"` case (`template-toolbar.test.tsx:30-34`): strengthen it to assert the actual active state. **Re-verify the component first:** `template-toolbar.tsx` (~line 46) expresses the active tool via `variant="secondary"` (→ a `bg-secondary` Tailwind class) and exposes **no** `aria-pressed` / `data-active` attribute today. So the assertion that works against the current component is the styling-class check — `expect(sphereBtn).toHaveClass("bg-secondary")` — paired with a non-active button asserting `.not.toHaveClass("bg-secondary")`. Do **not** lead with `expect(sphereBtn).toHaveAttribute("aria-pressed", "true")`: that attribute does not exist on the rendered button and the assertion would fail red. The cleaner-but-larger alternative is to first add a semantic `aria-pressed` / `data-active` attribute to the Button in `template-toolbar.tsx` and then assert that, so the test couples to behavior rather than a CSS class (the styling-class assertion is admittedly brittle styling-contract coupling). Either way, that single change converts a test that asserts nothing about its own subject into one that catches an active-tool-highlight regression.

Estimated impact: near-zero on run time (assertion swaps only). Defect-catching delta is essentially nil for the `toBeInTheDocument()` swaps — the queries already fail loudly on a missing element — and meaningfully positive for the one active-button case, which gains real state coverage.

## Scope / caveats
Touch only the three cited map test files; no source change, no new flakiness, and coverage strictly does not decrease. Frame and prioritize honestly: the `toBeInTheDocument()` swaps are readability/consistency cleanups, not new defect-catching, and the fog/template targets render through the `react-konva` mock (`template-overlay.test.tsx:4` and `fog-overlay.test.tsx:5` both `vi.mock("react-konva", ...)`), so those nodes are trivially-attached mock divs — do not over-promise on attaching `toBeInTheDocument()` there. The lone substantive item is the active-button assertion in `template-toolbar.test.tsx`; everything else is cosmetic.

This is the weakest finding in the audit set — file it as a tidy mechanical cleanup, sequenced below any behavioral-gap findings, and consider folding the active-button strengthening into whichever pass touches `template-toolbar.tsx` next rather than spending a standalone change on it.
