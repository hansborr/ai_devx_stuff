# 8. cleanDb() issues 22 sequential prisma.deleteMany() round-trips per call — collapsible to one transaction (or one CASCADE TRUNCATE)

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: speed · Area: infra · Severity: med · Size: S · Confidence: med
Theme: db-isolation-cost · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
`cleanDb()` empties the non-SRD tables with 22 individually-awaited `prisma.deleteMany()` calls, fully sequential and hand-ordered for FK safety (`packages/server/src/test/clean-db.ts:12-43`). Each call is its own round-trip to Postgres, and the whole chain runs in the global `beforeEach` on the per-test critical path for every server test (`packages/server/src/test/setup.ts:44-47`). 20 of the 22 calls are also wrapped in a `deleteIfExists` try/catch (`clean-db.ts:3-10`) that swallows "does not exist" errors, adding per-call overhead and obscuring the FK ordering that actually matters.

Two things make the chain collapsible to a single round-trip with no behavioral change. First, the per-test invariant is simply "non-SRD tables are empty before each test"; the SRD reference tables (species, classes, spells, monsters, etc.) are deliberately preserved (`clean-db.ts:41-42`) and seeded once by global setup. Second — and this is the sharper point folded in from the merged supplement — most of the 22 deletes are not just sequential but **redundant**: the character/campaign child tables all carry `onDelete: Cascade` back to three roots (`User`, `Campaign`, `Character`), so deleting those three roots already removes every child row. The hand-maintained 22-entry list is therefore both slow (22 hops) and a maintenance liability (it must be extended every time a new child table is added, and today it is already incomplete — see Evidence).

Verified schema facts that make the single-statement variants safe: all 57 models use string `cuid()` IDs with zero `@default(autoincrement())` columns (`RESTART IDENTITY` is a no-op, no behavioral change), and no SRD/reference model FKs into `User`/`Campaign`/`Character`, so a `CASCADE` rooted at the cleaned tables cannot reach the seeded SRD data.

The same incompleteness extends to character children: `characterSpell`, `characterMetamagic`, and `inventoryItem` all carry `onDelete: Cascade` from `Character` (e.g. the `1009`/`1092` regions) yet are **also absent from the 22-entry list** — they are cleared only by FK cascade today, never by a direct `deleteMany` in `clean-db.ts`.

## Proposed direction
Lowest-risk first step (coverage-identical, no raw SQL): wrap the existing `deleteMany` chain in a single `prisma.$transaction([...])` — one round-trip, no `TRUNCATE ... ACCESS EXCLUSIVE` lock semantics, no manual reordering concern, and the exact same set of deletes. The pre-test DB state is byte-for-byte identical, so every test's coverage is preserved unchanged.

If the round-trip saving warrants going further, replace the chain with a single `prisma.$executeRawUnsafe('TRUNCATE TABLE "users", "campaigns", "characters" RESTART IDENTITY CASCADE')` rooted at the three cascade parents. CASCADE removes the manual ordering and reaches every child table — including the ~6 encounter/map tables the current list omits — and trimming the list to its three roots removes the maintenance burden of extending it as the schema grows. Keep the SRD tables out of the statement either way (they are not in the root set and nothing cascades into them).

Estimated impact: cuts ~21 round-trips to 1 per `cleanDb`. Postgres is same-host (per-worker DBs over localhost), so each saved hop is sub-millisecond RTT; realistic saving is seconds to low-tens-of-seconds across the ~1900 server tests, not dramatic. It compounds with the double-clean finding (which removes a redundant second `cleanDb` per test).

## Scope / caveats
Touch only `clean-db.ts`. Prefer the `$transaction` variant first — strictly safer, zero raw-SQL or lock surface, and a literal 1:1 collapse of today's behavior. Reserve the `TRUNCATE ... CASCADE` variant for a follow-up if the per-test saving justifies the larger change. Critical correctness note for the TRUNCATE path: do **not** "TRUNCATE the 22 listed tables" literally — that list is incomplete (encounters, maps, combat logs, etc. are cleaned only by FK cascade from `Campaign` today, per the Evidence), so a naive table-by-table TRUNCATE would leave orphan rows. Root the TRUNCATE at `users`/`campaigns`/`characters` and let CASCADE do the work, or enumerate every per-test table explicitly. One FK wrinkle to keep in mind when reasoning about roots: `CampaignMember.character` is `onDelete: SetNull` (`schema.prisma:1157`), but `CampaignMember` itself cascades from both `Campaign` and `User`, so it is still fully reached from the three roots. The other `SetNull` relations point *into* SRD tables and are also safe under a roots-only TRUNCATE because those SRD roots are not truncated: `InventoryItem.equipment`→`Equipment` (`schema.prisma:1093`) and `EncounterParticipant.monster`→`Monster` (`schema.prisma:1314`) — the SRD parents survive, so nullable FKs into them are untouched.

Pre-relied-upon schema facts must be re-verified before adopting the raw variant: no `autoincrement` columns (confirmed at HEAD — all `cuid()`) and no SRD/reference table FKs into the cleaned roots (confirmed at HEAD). Coverage is preserved in all variants because the pre-test DB state is identical; this finding changes only *how* the tables are emptied, never *which* rows survive.

This finding merges a supplement ("reduce-to-cascade-roots"): the insight that the 22 child deletes are not merely sequential but redundant given the three `onDelete: Cascade` roots. Sequencing: orthogonal to and compounds with the double-clean finding (different cause: that one removes a redundant call, this one collapses one call's round-trips). Preserve the `beforeAll`-vs-`cleanDb` constraint flagged by the "beforeAll-wiped-rows" finding — any data a suite seeds in `beforeAll` is wiped by the first global `beforeEach` `cleanDb()`; collapsing the deletes does not change that contract, but a reviewer touching this area should keep it in view.
