# 9. 8 pure-node seed/parser server tests pay the full DB-setup tax (globalSetup + per-test cleanDb) for zero DB use

Status: Done — landed 2026-07-19 (`c4a3ea78`). The `src/seed/**` tests run in a DB-free `server-unit` vitest project with no setupFiles/globalSetup and blanked database env (`packages/server/vitest.unit.config.ts:17,26`). Problem statement below is the historical finding.
Lens: speed · Area: server · Severity: low · Size: M · Confidence: high
Theme: project-routing · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
The server vitest project applies a single, DB-heavy lifecycle to every file it matches. Its config picks up `src/**/*.test.ts` and unconditionally wires `setupFiles: [src/test/setup.ts]` and `globalSetup: [src/test/global-setup.ts]` onto all of them. `global-setup.ts` builds the test schema from migrations and seeds SRD reference data once per run, while `setup.ts` provisions a locked per-worker Postgres database, dynamically imports the Prisma client, and runs `cleanDb()` in a `beforeEach` that fires before *every* test in the project — 22 `deleteMany()` round-trips per test.

Eight seed/parser test files live under `packages/server/src/seed/**` and so are swept into that lifecycle, yet none of them touch the database at all. Their imports are pure: text parsers (`spell-splitter`, `level-heading`, `parse-glossary-entry`, `parse-spell-block`, `extract-spell-metadata`), a weapon-data builder (`buildWeaponData`), and one schema-validate-plus-`fs.readFileSync` check (`spell-area-of-effect-overrides`). A grep for `prisma`/`cleanDb`/`trpc` across all eight returns zero hits. These 62 `it()` blocks are pure-node assertions over strings, schemas, and file reads — and every one of them is gated behind a `beforeEach` that wipes 22 tables it will never read or write, plus the dynamic Prisma import the worker took on for nothing.

This matters for run-time, not correctness: the tests are correct and stay correct. They simply pay a database tax for a database they never use. The waste is bounded — the heavy per-worker DB clone is provisioned once (guarded by `LIFECYCLE_PROCESS_KEY` in `setup.ts`), so the cost is not a fresh clone per file — but the residual `cleanDb()` round-trips and Prisma binding recur on every `beforeEach`, and the coverage map already excludes `src/seed/**`, so nothing about routing these files elsewhere changes what coverage measures.

## Evidence
- `packages/server/vitest.config.ts:16-19` — `include: ["src/**/*.test.ts"]` with `setupFiles: ["src/test/setup.ts"]` and `globalSetup: ["src/test/global-setup.ts"]` applied to ALL server tests, including everything under `src/seed`.
- `packages/server/src/test/setup.ts:44-47` — `beforeEach` runs `await cleanDb()` for every server test file (and resets the auth rate limiter); `cleanDb` itself is unconditional.
- `packages/server/src/test/clean-db.ts:12-43` — `cleanDb()` issues 22 `deleteMany()` round-trips (20 wrapped in `deleteIfExists`, plus `session` + `user` directly) on every `beforeEach`.
- `packages/server/src/test/setup.ts:40-42` — the per-test setup dynamically imports the Prisma client (`await import("../prisma/client.js")`) for every file, DB-using or not.
- `packages/server/src/test/global-setup.ts:20-23` — `prepareTestDb({ dbUrl, seed: seedSrd })` builds the schema and seeds SRD once per run.
- `packages/server/vitest.config.ts:31` — `src/seed/**` is already excluded from server coverage, so routing these tests to a DB-free project does not change coverage attribution.
- Seed/parser scope: 8 files / 62 `it()` blocks, all with zero `prisma`/`cleanDb`/`trpc` references — `packages/server/src/seed/{generate-srd-spells,level-heading,seed-srd-equipment,spell-area-of-effect-overrides}.test.ts` (10/6/1/2 `it()`), `spell-parser/{extract-spell-metadata,parse-spell-block}.test.ts` (11/13), `rules-glossary-parser/parse-glossary-entry.test.ts` (16), and the merge-added `seed-srd.test.ts` (3 `it()`, reads tmp JSON via the merge-added `seed-data-loader.ts`). Their imports are pure parsers, a schema validator, and `fs.readFileSync`/tmp-file reads.

## Proposed direction
Route the DB-free seed/parser tests through a setup path that skips DB provisioning, preserving every assertion. Preferred shape: add a second vitest project (e.g. `server-unit`) with **no** `setupFiles`/`globalSetup`, matching `src/seed/**`, running alongside the existing `server` project; exclude `src/seed/**` from the `server` project's `include` so each file runs in exactly one place. Same tests, same assertions, just without the unused DB lifecycle — `cleanDb()` never fires and the dynamic Prisma import never happens for these files. An alternative that touches fewer config surfaces is to make `setup.ts` lazily skip DB provisioning + `cleanDb` when the running file matches a DB-free directory glob, but a separate project is cleaner and self-documents the contract ("these tests must stay DB-free").

Estimated impact: removes the per-test `cleanDb()` (22 `deleteMany()` round-trips) and the dynamic Prisma import from 62 DB-free tests. Because the heavy per-worker DB clone is provisioned once (guarded by `LIFECYCLE_PROCESS_KEY` in `setup.ts`), the full-suite headline saving is smaller than a naive per-file sum — the residual win is the recurring `beforeEach` clean plus the Prisma binding these files no longer take on. A modest but real, low-risk speed win on the seed scope, with a clean pattern to extend later.

## Scope / caveats
Pilot with the 8 confirmed-DB-free seed/parser files only; these are the slug's scope (this finding folds in the duplicate "7 pure-node seed/parser tests pay full server DB-setup tax" report — same files, same claim). The merge-added `seed-srd.test.ts` is a confirmed-DB-free file that the proposed `src/seed/**` project glob already captures, so it needs no extra per-file verification. Before widening to other server files that *look* DB-free, individually verify each candidate: several server tests depend on `global-setup`'s seeded reference data and would break under a no-`globalSetup` project — e.g. `packages/server/src/routers/monster.test.ts:29` ("returns all seeded monsters with default pagination") and the seed-count locks in `packages/server/src/routers/srd.test.ts` (`toHaveLength(6/18/9/12)`, `name` assertions on seeded species/classes). Do not move anything that reads seeded SRD. A strict grep suggests ~28 additional DB-free-looking files exist, but the false-positive rate is high, so do not bulk-move — extend only with per-file verification.

Risk is low and scoped: a new project changes only scheduling/setup, not assertions, and coverage is preserved exactly because thresholds key on source-path globs (`packages/server/src/**`) with `src/seed/**` already excluded, not on the running project. This is distinct from the `cleanDb`-internals finding (which speeds up the clean itself) — here the goal is to not run the clean at all for these files; the two are complementary, not overlapping.
