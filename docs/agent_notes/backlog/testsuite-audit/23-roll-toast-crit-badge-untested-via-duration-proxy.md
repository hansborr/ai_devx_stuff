# 23. roll-toast crit logic (NAT 20 / NAT 1 badge) tested only via the duration proxy, never the rendered badge

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: defect-catching · Area: client · Severity: low · Size: S · Confidence: high
Theme: user-visible-output-untested · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
`roll-toast.test.ts` exercises `showRollToast` through eight `it()` cases that each assert exactly one thing: the toast `duration` — `5000` for a crit, `4000` otherwise. Because `duration` is derived directly from `detectCrit`'s return value (`const duration = crit ? CRIT_TOAST_DURATION : NORMAL_TOAST_DURATION`), the duration is a faithful proxy for crit detection. The crit-detection rule itself — d20-only gating, the `kept ?? rolls` selection for advantage/disadvantage, the single-effective-die guard, and the `=== 20` / `=== 1` mapping — is therefore genuinely validated by these cases. That branch logic is **not** the gap.

The gap is the user-visible output. `toast.custom` is mocked as a bare `vi.fn()`, so the render callback handed to it never runs; `RollToast` is never rendered and `CRIT_STYLES` is never read. The actual badge a player sees — the `"NAT 20"` / `"NAT 1"` text plus its container/badge styling — has zero test coverage anywhere in the client. A regression that swaps `NAT 20` ↔ `NAT 1`, blanks a `badgeText`, drops the badge `<span>`, or mis-wires `CRIT_STYLES[crit]` would keep `duration` at `5000` and sail past all eight assertions. The file's own header comment even concedes the shape of the problem: "Instead, let's extract and test directly" / "detectCrit is not exported, we test via showRollToast's behavior" — an intent that was never followed through for the render side. The uncovered slice is small (a static `CritType -> badge string` table) but it is precisely the part a user reads, and it is unguarded.

## Evidence
- `packages/client/src/lib/roll-toast.test.ts:4-8` — header comment ("let's extract and test directly" / "detectCrit is not exported, we test via showRollToast's behavior"); `packages/client/src/lib/roll-toast.test.ts:10-12` mocks `react-hot-toast` so `toast.custom` is a bare `vi.fn()` — the render callback that builds the badge never runs.
- `packages/client/src/lib/roll-toast.test.ts:40` — `expect(call![1]).toEqual({ duration: 5000 })`; all eight `it()` cases (lines 35-98) assert only `call![1]` (the options object's `duration`), never the rendered node `call![0]`.
- `packages/client/src/lib/roll-toast.ts:7-18` — `detectCrit` holds the crit rule (d20-only via `notation.includes("d20")`, `effectiveRolls = first.kept ?? first.rolls`, `length !== 1` guard, `=== 20`/`=== 1`); this branch logic is faithfully exercised through the duration proxy.
- `packages/client/src/lib/roll-toast.ts:36-50` — `CRIT_STYLES` defines `badgeText` `"NAT 20"` / `"NAT 1"`, the actual user-visible output, consumed by `RollToast` at lines 52-82 (the badge `<span>` createElement at lines 67-73, with the `styles.badgeText` child on line 72). A scoped grep for `"NAT 20"` / `"NAT 1"` / `badgeText` / the `RollToast` component across `packages/client/src/**/*.test.ts*` returns zero matches (the only `RollToast` hits in tests are the `showRollToast` function, which contains it as a substring, plus `hooks/use-ability-roll.test.ts` and `hooks/use-weapon-roll.test.ts`, which also match only via the `showRollToast` substring — both mock it as `vi.fn()` and assert nothing about the badge).

## Proposed direction
Add one render-anchored assertion while keeping all eight duration cases intact. Two coverage-preserving routes:

1. Render-the-output route: invoke the callback that `toast.custom` receives (it is `mock.lastCall[0]`, a `(t) => ReactElement`), or render `RollToast` directly, then assert the badge for a crit vs non-crit result — e.g. that the `"NAT 20"` text is present for `makeResult([20])`, `"NAT 1"` for `makeResult([1])`, and that no badge text appears for a non-crit. jsdom render is deterministic, so no flakiness is introduced.
2. Pure-helper route: add a one-line `export` for `detectCrit` (or a thin `critBadge(crit): string | null` helper) and unit-test the `CritType -> badgeText` mapping directly, independent of React.

Either way add at least one assertion bound to the user-visible badge so that swapping/blanking `badgeText` or breaking the badge container fails a test. Estimated cost is a handful of assertions in a single fast jsdom file; no measurable runtime impact (the existing eight cases already mount nothing expensive, and one render of a trivial element is sub-millisecond). The fix strictly strengthens coverage — the duration cases stay, and the previously-unguarded render slice becomes guarded.

Bonus the same test can guard (not the primary gap): `detectCrit` gates crit detection on `notation.includes("d20")` (`roll-toast.ts:9`), which also returns true for substrings like `1d200` — so a single effective `[20]` rolled on a `1d200` would be (mis)labeled `NAT 20`. This latent edge is untested today and a `detectCrit`/render helper test (pure-helper route) could pin it down alongside the badge string-mapping.

## Scope / caveats
Touch only `packages/client/src/lib/roll-toast.test.ts` (plus a single one-line `export` in `roll-toast.ts` if you choose the pure-helper route). Do not rewrite the duration cases — `detectCrit`'s branch logic is already faithfully validated through the duration proxy, so this finding is **not** a claim that crit detection is untested; the genuine and only gap is the render/badge string-mapping. Blast radius is a static string table, so risk is low.
