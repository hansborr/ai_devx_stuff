# 10. BCRYPT_SALT_ROUNDS hardcoded at 12 makes real-auth-path tests (register / changePassword / rate-limit) pay ~150ms per hash

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: speed · Area: server · Severity: low · Size: S · Confidence: high
Theme: auth-bcrypt-cost · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
`BCRYPT_SALT_ROUNDS` is a plain `const = 12` in `config/auth.ts` with no env or test override. It feeds `hashPassword` (`auth-service.ts:19`) — the one helper every real registration / change-password / register-then-login flow goes through — so each of those hash-generation ops costs ~150ms of CPU-bound bcrypt work. The test fixtures already proved 4 rounds is fine for tests: `fixtures.ts` hashes seed users at `TEST_BCRYPT_ROUNDS = 4` for direct DB inserts. But that cheap path only covers tests that *insert* a pre-hashed user; any test that drives the actual `auth.register` / `auth.login` / change-password procedures re-hashes through the 12-round const.

The cost concentrates in `auth-rate-limit.test.ts`, among the slowest files in the server suite. Its "blocks login after too many attempts from same IP" case does one real `register` (one 12-round hash) and then fires 10 back-to-back real `login` injects. That ~5.7s is purely the real bcrypt compares against the stored 12-round register hash plus the register hash itself — **not** any real-time window wait: the limiter compares `Date.now()` against `resetAt` and the test never sleeps, and the 429-returning 11th request is cheap because `authRateLimiter.check()` short-circuits before bcrypt (`auth.ts:144` runs before `verifyPasswordOrDummy` at `auth.ts:150`). `auth-service.test.ts` adds 3 more real 12-round `hashPassword` ops (success / wrong-password / distinct-salt). Meanwhile the deterministic unit test `trpc/rate-limit.test.ts` already covers the window/limit/reset logic instantly via `vi.useFakeTimers()` + `advanceTimersByTime`, so the slow router file is re-verifying window behavior through real bcrypt for marginal added coverage.

This finding merges two observations: (1) the hardcoded 12-round const with no test override, and (2) the fake-timer unit test being fast/deterministic while its router sibling pays real bcrypt + (claimed) window waits — adversarial re-verification confirmed the router file's slowness is real bcrypt, not window sleeps.

## Evidence
- `packages/server/src/config/auth.ts:14` — `export const BCRYPT_SALT_ROUNDS = 12;`, a plain const with no env-var read or test branch.
- `packages/server/src/services/auth-service.ts:19` — `return hash(password, BCRYPT_SALT_ROUNDS);` inside `hashPassword`, the helper every real register/change-password flow calls.
- `packages/server/src/services/auth-service.ts:35` — the missing-user timing-oracle dummy hash (`hash(DUMMY_PASSWORD_PLACEHOLDER, BCRYPT_SALT_ROUNDS)`) shares the **same** const; lowering it would break the timing guard (see caveats).
- `packages/server/src/test/fixtures.ts:6` — `const TEST_BCRYPT_ROUNDS = 4;` for the cheap seed-insert path, proving 4 rounds is already accepted for tests.
- `packages/server/src/routers/auth-rate-limit.test.ts:22-52` — "blocks login after too many attempts from same IP": one real `register` (line 26-30) then a 10-iteration real `login` loop (line 33-39); cost is real bcrypt, not window waits — no `setTimeout`/`sleep`/`waitFor` anywhere in the file, and the test carries a `{ timeout: 15_000 }` budget.
- `packages/server/src/trpc/rate-limit.test.ts:10,103-121` — `vi.useFakeTimers()` (line 10) and the "resets after window expires" case using `vi.advanceTimersByTime(...)` (line 113) cover window reset/limit logic deterministically and instantly, making the router file's window re-verification redundant for that logic.
- `packages/server/src/services/auth-service.test.ts:24,31,38-39` — the `hashPassword` call sites (inside the three `it()` blocks that begin at lines 22, 30, 36) each generate a real 12-round hash; the distinct-salt test makes two calls (38-39).
- `packages/server/src/seed/seed-users.ts:5` — production seed users are also hashed at 12 via a separate `const SEED_BCRYPT_ROUNDS = 12;`; this is a distinct const (production-shaped seed) and is NOT affected by the proposed `config/auth.ts` change.
- `packages/server/src/routers/auth.ts:144,150` — `authRateLimiter.check()` (line 144) runs before `verifyPasswordOrDummy` (line 150), confirming the 11th 429 request never reaches bcrypt.

## Proposed direction
Derive `BCRYPT_SALT_ROUNDS` from the environment so production keeps 12 rounds while test hash-*generation* runs at 4 — e.g. `serverEnv.nodeEnv === "test" ? 4 : 12`, or an optional env var clamped to a safe floor. `bcrypt.compare` cost follows the *stored* hash's rounds, so existing 4-round fixture hashes still verify and only newly generated hashes get cheaper. This cuts each hash-generation op in the real-auth-path tests from ~150ms to ~5ms; biggest beneficiaries are `auth-rate-limit.test.ts` and the `auth-service` / `auth.test.ts` register/login cases — plausibly 2-4s of server wall, biggest single win on `auth-rate-limit.test.ts`.

CRITICAL coverage caveat: the login-timing-oracle guard (`auth-login.test.ts`, the regression-guard comment block at lines 80-94, the `it.skipIf(!process.env.RUN_TIMING_TESTS)` block at line 95, `MIN_MISSING_USER_ELAPSED_MS = 30` at line 98, assertion at line 125) *relies* on the dummy missing-user hash (`auth-service.ts:35`, same const) staying at ~12 rounds / ~150ms while real users hash at 4 rounds — that is what enforces the 30ms floor and the `missing >= wrong-password` ordering. A naive `nodeEnv === "test" ? 4 : 12` would drop the dummy hash to ~5ms and break that guard. The fix MUST keep the dummy / timing-oracle hash at 12 rounds (or decouple the dummy from the runtime salt const so it can stay high while `hashPassword` drops). Optionally also keep `auth-rate-limit.test.ts` behind a slow tier if it remains heavy after the round reduction.

Coverage is preserved: keep at least one true end-to-end register/login/429 assertion through the real flow, and lean on the deterministic `trpc/rate-limit.test.ts` for exhaustive window/limit logic. No assertions are deleted; only hash-generation cost drops.

## Scope / caveats
This is a **production** code change (`config/auth.ts`) gated on environment, not a test-only edit — review carefully and keep production at 12 rounds. The single biggest risk is silently breaking the login-timing-oracle test, since the dummy missing-user hash shares the const; the env override must NOT lower the timing-oracle path, and `compare`-cost expectations elsewhere must not be relaxed. Note the timing-oracle blocks in both `auth-login.test.ts` and `auth.test.ts` are `skipIf(!process.env.RUN_TIMING_TESTS)`, so they do not run by default — but they DO run in CI when `RUN_TIMING_TESTS=1`, so the dummy-hash invariant still matters. Some original impact claims were inflated: `auth.test.ts` runs ~11 register/login ops by default (not 18; the heaviest timing-oracle ops are env-gated). Distinct from the HTTP-login-vs-token-mint finding (`07-test-setup-http-login-vs-token-mint.md`) — that swaps setup logins for direct token mints, whereas this lowers hash cost on tests that genuinely exercise the auth procedures; the two are complementary, not overlapping. Merged from a second observation that the fake-timer unit test is fast while its router sibling pays real bcrypt; adversarial re-verification confirmed the router slowness is bcrypt, not window sleeps. Low severity because the cost concentrates in a handful of files.
