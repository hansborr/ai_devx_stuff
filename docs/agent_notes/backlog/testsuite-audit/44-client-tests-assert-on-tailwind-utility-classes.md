# 44. Client tests assert on raw Tailwind utility classes, coupling tests to styling internals

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: client · Severity: low · Size: S · Confidence: high
Theme: brittle-selectors · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
A small cluster of client component tests assert behavior by reaching for raw Tailwind utility classes via `container.querySelector(".<utility>")` or `toHaveClass("<utility>")`. The selector is the literal styling output, not the user-visible contract: a loading skeleton is found by `.motion-safe\:animate-pulse`, a scroll container by `.max-h-64.overflow-y-auto`, a row's display name by `.font-medium`, and a condition-count badge by `.absolute`. These assertions break the moment someone does a cosmetic refactor that leaves behavior untouched — renaming the max-height, swapping the animation utility for a different motion class, restructuring the layout wrapper, or changing the typography weight. The result is a false failure that tells a new developer nothing about what the test actually protects: the test fails because a class string moved, not because the skeleton stopped rendering or the badge stopped counting.

The brittleness is uneven, and that matters for sequencing. The four cosmetic cases above are coupled to pure presentation and have no semantic justification — `.font-medium` is just "this text is bold-ish," and `.absolute` is positioning. The fifth case (`ring-2 ring-amber-500` on `initiative-row`) is more defensible because the ring is a state signal, but it is still asserted as a class string rather than as a semantic attribute — even though the underlying component already exposes the cleaner hook. Notably the raw finding framed this as "active-turn state"; on re-verification it is the **selection** state (`isSelected`), and the row already publishes `aria-pressed` on its select button and `aria-current` for the genuine active-turn case. So the semantic test hook the proposed direction wants already exists for the selection ring; the test just isn't using it.

## Evidence
- `packages/client/src/pages/character-sheet-page.test.tsx:54` — `expect(container.querySelector(".motion-safe\\:animate-pulse")).not.toBeNull()` asserts the SRD loading skeleton; the assertion is the animation utility, not a `role=status` / test-id. (Cosmetic — unambiguously brittle.)
- `packages/client/src/components/common/paginated-result-list.test.tsx:55` — `expect(container.querySelector(".max-h-64.overflow-y-auto")).toBeInTheDocument()` asserts the scroll container by its height+overflow utilities; the container class is itself passed in by the test at line 51, so the assertion only re-checks that a string round-tripped, not any behavior. (Cosmetic.)
- `packages/client/src/components/campaign/homebrew-link/campaign-homebrew-section.test.tsx:161` — `rows.map((r) => r.querySelector(".font-medium")?.textContent)` reads available-collection row names by typography class; the rows are already addressable via `data-testid="available-collection-row"` (source `campaign-homebrew-section.tsx:172`), and the name is plain text inside them. (Cosmetic.)
- `packages/client/src/components/campaign/combat/initiative-tracker-actions.test.tsx:102,104` — `captainBtn?.querySelector(".absolute")` / `thugBtn?.querySelector(".absolute")` read the condition-count badge by its positioning class. The badge is a `<Badge>` at `condition-toggle-popover.tsx:148-153` inside a button labelled `aria-label="Conditions for ${participantName}"` (source line 143). (Cosmetic — `.absolute` is positioning, not the count contract.)
- `packages/client/src/components/campaign/combat/initiative-tracker/initiative-row.test.tsx:108,114` — `toHaveClass("ring-2", "ring-amber-500")` / `not.toHaveClass("ring-amber-500")` assert the **selection** ring (`isSelected`). The source applies `ring-2 ring-amber-500` via `selectedClass` (`initiative-row.tsx:35`) and already exposes `aria-pressed={isSelected}` on the select button (source line 47), which the same tests already assert at lines 109/115. (Semantic state, but class-coupled, and a cleaner hook already exists.)
- Total: 5 representative assertions across 5 client test files (4 cosmetic-class, 1 state-class). A broader sweep (`rg "querySelector(['\"]\." / "toHaveClass("` over `packages/client/src/**/*.test.tsx`) is the way to scope the full migration before starting — the full client suite has 6 `querySelector(".<class>")` hits + 8 `toHaveClass(` hits (14 total). Additional cosmetic candidates beyond the 5 examples above: `dashboard-page.test.tsx:175` (`bg-primary`), `app-header.test.tsx:133` (`sm:hidden`), `form-field-error.test.tsx:10` (`text-sm`/`text-destructive`), `paginated-result-list.test.tsx:35` (`.h-14`) and `:43` (`text-center`/`text-sm`/`text-muted-foreground`). Categorize each as intentional styling-contract vs accidental coupling when scoping.

## Proposed direction
Replace styling-class selectors with role/text/test-id queries that express intent, leaving every behavioral assertion intact:
- Loading skeleton (`character-sheet-page.test.tsx:54`): give the skeleton container `role="status"` (the accessible signal for an in-progress region) or an explicit `data-testid`, and query that instead of `.motion-safe\:animate-pulse`.
- Scroll container (`paginated-result-list.test.tsx:55`): assert via a `data-testid` (or a role) on the list container rather than re-checking the `max-h-64 overflow-y-auto` string the test itself injected; better still, assert the behavior the container exists for (rows render, list is bounded) rather than the wrapper class.
- Row names (`campaign-homebrew-section.test.tsx:161`): read names with `within(row).getByText(...)` / `getByRole` off the existing `available-collection-row` test-id, dropping the `.font-medium` reach.
- Condition badge (`initiative-tracker-actions.test.tsx:102,104`): query the count by text within the already-labelled `Conditions for ${name}` button — e.g. `within(captainBtn).getByText("2")` — instead of `.absolute`.
- Selection ring (`initiative-row.test.tsx:108,114`): assert `aria-pressed` on the select button (the test already does this on the adjacent lines), or add a `data-state="selected"` attribute on the row and assert that. The `ring-amber-500` class can stay in the component as pure styling; the test just stops depending on it. If a class assertion is ever genuinely required, leave a one-line comment that it is a deliberate state contract.

Behavior coverage is unchanged in every case — only the selector strategy changes. Estimated impact: removes a class of false failures on cosmetic refactors (animation-utility swaps, height/typography/layout tweaks) and makes each assertion state the behavior it protects; no measurable runtime change (these are tiny per-file edits, not a perf finding).

## Scope / caveats
Pure test-quality/maintainability change — no coverage stakes and no source-behavior change is required, though three of the five may want a tiny component touch (a `role="status"`, a `data-testid`, or surfacing `aria-pressed`/`data-state`) to migrate cleanly. Sequence the four cosmetic cases first (skeleton, scroll container, row name, condition badge) — they are unambiguously brittle and need at most a test-id. Do the selection-ring case second; it is defensible and only worth migrating because the row already exposes `aria-pressed`, so the change is low-effort and strictly improves the signal. After each migration, confirm the assertion still fails when the underlying behavior regresses (skeleton not rendered, badge count wrong, ring not applied) and not merely when a class string is renamed — that is the whole point. Do not touch `initiative-row`'s `aria-current` test at lines 101-104; it is already the correct semantic-attribute pattern and is the model the other cases should follow. This finding is about selector strategy only; it is not a coverage-gap, dead-code, or duplication finding, and it does not depend on any other item in the pack.
