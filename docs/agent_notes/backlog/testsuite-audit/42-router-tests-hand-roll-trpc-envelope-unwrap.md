# 42. Router tests hand-roll the tRPC `result.data` envelope unwrap 38 times despite the existing `trpcData<T>()` helper; `character.test.ts` mixes both styles

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: server · Severity: low · Size: S-M · Confidence: high
Theme: server-test-boilerplate · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
A typed envelope unwrapper already exists and is the dominant convention across the server suite: `trpcData<T>(body)` (`trpc-helpers.ts:8-11`) does `(JSON.parse(body) as { result: { data: T } }).result.data` once, behind one documented type-assertion boundary, and is re-exported through `injectTrpcMutation<T>` (line 40-42). Yet server router tests still hand-write the full `JSON.parse(response.body) as { result: { data: <large nested literal> } }` block and then reach into `.result.data` themselves — re-declaring a bespoke inline response type at every call site.

`character.test.ts` is the clearest smell: it imports and uses `trpcData` (line 16, called at lines 522 and 800) but *also* hand-rolls the verbose form 10 times in the same file (lines 48, 81, 109, 126, 147, 168, 196, 233, 297, 335). A new contributor reading this file sees two competing idioms side by side and copies whichever they hit first. `srd.test.ts` is the densest offender with 18 hand-rolled blocks, none using the helper.

Each hand-rolled block is noisy, and the inline literal type can silently drift from the real procedure output schema: because it is an unchecked `as` assertion, a stale field shape compiles clean and the test keeps passing against a type that no longer matches reality. Consolidating on `trpcData<T>` does not *fix* that (the helper is itself an unchecked assertion — see caveats), but it removes the duplicated scaffold and stops the suite from teaching two conflicting ways to do the same unwrap.

## Evidence
- `packages/server/src/test/trpc-helpers.ts:8-11` — `export function trpcData<T>(body: string): T` already unwraps `result.data` behind a single documented assertion boundary; re-used by `injectTrpcMutation<T>` at line 40-42. Used across 60+ server test fixtures.
- `packages/server/src/routers/character.test.ts:16,522,800` — imports `trpcData` and calls it twice — while the same file hand-rolls the envelope 10 times (`48, 81, 109, 126, 147, 168, 196, 233, 297, 335`), e.g. line 47-58 declares an inline `{ result: { data: { name; level; classes; stats } } }` literal. Within-file inconsistency.
- `packages/server/src/routers/srd.test.ts:24-26` — representative hand-rolled block (`as { result: { data: {...}[] } }`); 18 such occurrences in this one file, the densest.
- Re-verified counts at HEAD: **48** `JSON.parse(response.body)` occurrences across **12** files (drifted up from the 41/10 captured pre-merge). Of these, **38 are `result.data`-shaped and replaceable**: srd 18, character 10, auth 2, auth-update-profile 2, app 1, auth-change-password 1, auth-delete-account 1, auth-login 1, auth-me 1, health 1.
- `packages/server/src/app.test.ts` has 6 `JSON.parse(response.body)` parses total: 1 replaceable + 5 not. The single replaceable one is `app.test.ts:182` (the "tRPC context exposes a narrow request logger" test, a real `result: { data: {...} }` envelope) — this is the "app 1" in the replaceable breakdown above. Note `app.test.ts` lives at `packages/server/src/app.test.ts`, **not** under `src/routers/`.
- Genuinely NOT replaceable (leave alone): `health.test.ts:40` (raw REST `/health`, no envelope) and `:55` (`{ error: { message } }`); `auth-rate-limit.test.ts:48` and `auth-delete-account.test.ts:131` (`{ error: { message } }`); `app.test.ts:80,91,102,143,258` (OpenAPI spec, REST paths, `as unknown[]`, and `{ error: ... }` envelopes). `trpcData` would yield `undefined` on every one of these.
- `packages/server/src/test/auth-helper.ts:25` — also matches the grep but is the *correct* pattern, not a hand-roll: `const body: unknown = JSON.parse(response.body)` followed by `loginTrpcResponseSchema.parse(body)` (real Zod validation). Excluded from both the replaceable and the cosmetic-smell sets.

## Proposed direction
Replace the 38 `result.data`-shaped hand-rolled blocks with `trpcData<T>(response.body)`, declaring `T` from the shared procedure-output schema type where one exists rather than re-typing an inline literal. Sequence by density: `srd.test.ts` (18) and `character.test.ts` (10) first, then the single-occurrence auth/app files. Assertions are unchanged — only the parse-and-cast scaffold is removed, and `.result.data` indexing collapses into the helper's return. After `character.test.ts` is converted, the file uses one idiom throughout, ending the within-file inconsistency.

Estimated impact: removes ~38 duplicated parse/type blocks and unifies on the established unwrap idiom. No measurable runtime change (same single `JSON.parse` per call); the win is onboarding/readability and one less competing pattern for contributors (and AI agents) to copy. Verify per file with `bun run test -- <file>` — pass counts must be identical before and after, since this is a pure refactor of how the already-parsed body is typed.

## Scope / caveats
This is a cosmetic DRY/consistency cleanup, **not** a type-safety win — be precise about the benefit. `trpcData<T>` is itself an unchecked `JSON.parse(body) as { result: { data: T } }` assertion (see `trpc-helpers.ts:9-10`), so swapping an inline literal for it adds **zero** compile-time drift protection; if real schema-validated unwrap is wanted, that is a separate, larger finding (the `auth-helper.ts` Zod-parse pattern is the model). Do not touch the error/REST-envelope parses listed above (health REST endpoint, `{ error: { message } }` shapes, OpenAPI specs) — they are not `result.data` envelopes and would break under `trpcData`. Do not touch `auth-helper.ts:25` (already correct). No coverage loss, no flakiness risk; low-leverage and safe to do incrementally one file at a time. This is a test-boilerplate/consistency finding only — no source code, no procedure schema, and no assertion logic changes.
