# 34. Ten client combat/sheet tests re-implement `makeParticipant()` when shared `buildParticipant()` already exists

Status: Done — implemented 2026-06-14 (batch 5a)
Lens: maintainability · Area: client · Severity: med · Size: S-M · Confidence: high
Theme: fixture-builder-duplication · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
The client test tree already ships a canonical `EncounterParticipant` builder: `buildParticipant(overrides)` in `packages/client/src/test/fixtures-encounter.ts`, backed by a `PARTICIPANT_DEFAULTS` object that enumerates every non-key field of the participant shape (all 22 defaulted fields plus the 4 required `id`/`encounterId`/`type`/`name`). It is the builder the fixture module itself uses to assemble every `TEST_*_ENCOUNTER` constant, so the sibling test files that import `fixtures-encounter` already depend on it transitively.

Despite that, ten combat- and sheet-area test files re-declare the participant shape by hand (8 with a `makeParticipant`-named builder + 2 `BASE_PARTICIPANT`-constant variants). Six of them spell out an identical inline `function makeParticipant(overrides): EncounterParticipant` that lists all 26 fields literally before spreading `...overrides`; the field set is byte-for-byte the union of `PARTICIPANT_DEFAULTS` plus the four required keys. Four more carry the same hazard in a variant form: `use-monster-hp-update.test.ts` hoists a `BASE_PARTICIPANT` constant and spreads it, `difficulty-indicator.test.tsx` declares a plural `makeParticipants()` over a near-identical `Omit<...>` base, and `monster-hp-control-strip.test.tsx` / `participant-stat-line.test.tsx` each hoist a `BASE_PARTICIPANT` constant (the latter plus a full hand-rolled `CHARACTER_PARTICIPANT`).

This is a live schema-drift hazard, not a cosmetic one. When `homebrewMonsterEntryId`/`homebrewMonsterEntryVersion` were added to `EncounterParticipant`, both fields had to be hand-threaded into every copy (they are present in all ten today, which is exactly the symptom). The next participant-field change forces the same ten-file sweep or those files stop typechecking in isolation. A newcomer reading any one of these files has no signal that a canonical builder exists one directory over, and cannot tell which spelling is authoritative.

(Optionally also `packages/client/src/components/vtt/drawer/monster-stat-block-drawer.test.tsx:27-70,155,258,285,319,361` as an 11th file with its own `PARTICIPANT_DEFAULTS` Pick + builder plus 4 more inline full shapes.)
- Total: `rg -l makeParticipant packages/client/src` returns 8 files, but the broader full-shape grep `rg -l ': EncounterParticipant = \{|\): EncounterParticipant \{' packages/client/src --glob '*.test.*'` returns 10; the two additional files share the identical `homebrewMonsterEntryId`/`homebrewMonsterEntryVersion` drift symptom. Field sets of the inline builders are identical to `PARTICIPANT_DEFAULTS` + required keys; the only divergence is default *values* (see caveats).

## Proposed direction
Replace each local builder with an import of `buildParticipant` from `@/test/fixtures-encounter`, migrating file-by-file. This is **not** a naive find-and-replace, because the shared builder and the local ones disagree on default *values*, not field *names*:

- Shared `buildParticipant` defaults `initiative`, `maxHp`, `currentHp`, `tempHp`, `ac`, and `challengeRating` to `null`.
- The local builders default those to concrete values (`initiative:15`, `maxHp:21`/`10`, `currentHp:15`/`10`, `ac:13`/`15`, `challengeRating:0.25`) that the tests depend on for initiative ordering and HP/AC rendering.

So each call site — including every bare `makeParticipant()` and the `DEFAULT_ACTION_PROPS`/`DEFAULT_*` spreads that feed `participant: makeParticipant()` — must thread the previously-implicit values through `overrides` to preserve identical test inputs. The cleanest shape per file is to keep a thin local default object (e.g. `const PARTICIPANT = (o = {}) => buildParticipant({ id: "p-1", encounterId: "enc-1", type: "npc", name: "Goblin", initiative: 15, maxHp: 21, currentHp: 15, ac: 13, challengeRating: 0.25, ...o })`) that calls the shared builder, removing the 26-line literal while keeping the values the assertions read. Coverage is unchanged: same component under test, same rendered participant data, one fewer hand-maintained shape.

`difficulty-indicator.test.tsx`'s plural `makeParticipants` can map over `buildParticipant` per entry (deriving `challengeRating`/`characterLevel` from its `{cr}`/`{level}` inputs), and `use-monster-hp-update.test.ts` can replace `BASE_PARTICIPANT` with a `buildParticipant({...})` call. Estimated impact: eliminates ~10 copies of a ~30-line builder and turns the next participant-schema change from a ten-file sweep into a single edit in `fixtures-encounter.ts`. No measurable runtime-speed effect — this is a maintainability/onboarding win, not a wall-clock one.

## Scope / caveats
Touch only the ten test files plus, if a shared call-site default helps, `fixtures-encounter.ts` (export only; do not change existing defaults). Do not modify any component source or the `EncounterParticipant` schema. The dominant correctness hazard is the null-vs-non-null default divergence above: the concrete `initiative`/`maxHp`/`currentHp`/`ac`/`challengeRating` values **must** be threaded through `overrides`, and every bare `makeParticipant()` plus `DEFAULT_*_PROPS` spread needs explicit values, or initiative-ordering and HP-display assertions will silently change inputs. Migrate and run one file at a time (`bun run test -- <file>`); confirm pass counts are unchanged after each.

Risk is capped because participant-schema drift here surfaces as loud compile/typecheck failures, not silent coverage loss — the worst regression is a red build, caught immediately. This is test-only fixture duplication inside product test code; it is distinct from the adjacent encounter-fixture/dedup findings (#40 combat/spell encounter fixture + DbClient cast, #41 Zustand store mocks, #43 VTT drawer mutation injection). It does not depend on any other test-suite-audit finding and can land independently.
