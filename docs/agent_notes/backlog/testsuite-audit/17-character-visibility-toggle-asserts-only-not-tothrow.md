# 17. useCharacterActions visibility-toggle tests assert only `not.toThrow()`, leaving the inversion and mutation payload unprotected

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: defect-catching · Area: client · Severity: med · Size: S · Confidence: high
Theme: client-action-payload-unasserted · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
`handleToggleVisibility` is the hook action behind the character-list private↔public visibility control — a DM/player-facing access toggle. Its real job is twofold: (a) compute the inverted visibility from the `VISIBILITY_TOGGLE` map (`public`→`private`, `private`→`public`), and (b) fire the `character.updatePersonality` mutation with `{ id, visibility: newVisibility }`. Both branches are pure plumbing with no UI feedback, so the only thing standing between a correct toggle and a silent regression is a test that inspects the mutation payload.

The two tests that cover this action do not do that. Each one calls the action and asserts only `expect(() => act(() => result.current.handleToggleVisibility(...))).not.toThrow()`. Neither verifies that the mutation was called, with which `id`, or that the visibility was actually inverted. If `VISIBILITY_TOGGLE` returned the input unchanged, dropped the `id`, or were wired to the wrong mutation, both tests would still pass — the entire inversion-and-payload core is unguarded. The test names ("can toggle from private to public without throwing") overstate the guarantee: all that is checked is the absence of an exception, which a no-op also satisfies.

This finding is scoped to the *mutation payload* and the `VISIBILITY_TOGGLE` inversion map that produces it — not to *which* cache keys get invalidated after the toggle. (There is no separate invalidation finding for this hook in the pack; the cache-key behavior is simply out of scope here.)

## Evidence
- `packages/client/src/hooks/use-character-actions.test.ts:171-180` — test "can toggle from private to public without throwing"; the sole assertion is `not.toThrow()` at `:179`, with no mutation/payload check.
- `packages/client/src/hooks/use-character-actions.test.ts:182-191` — test "can toggle from public to private without throwing"; identical shape, only `not.toThrow()` at `:190`.
- `packages/client/src/hooks/use-character-actions.ts:64-78` — `handleToggleVisibility` computes `newVisibility = VISIBILITY_TOGGLE[current]` (`:67`) and calls `updateVisibility({ id, visibility: newVisibility }, ...)` (`:68-75`); `updateVisibility` is the destructured `mutate` of `visibilityMutation` (`:46`), itself `trpc.character.updatePersonality.mutationOptions()` (`:44`).
- `packages/client/src/hooks/use-character-actions.ts:22-25` — `VISIBILITY_TOGGLE = { public: "private", private: "public" }`, the inversion map no test exercises.
- `packages/client/src/test/mock-trpc-helpers.ts:48-56` — `makeMutation`'s `mutationFn` is a nullary resolver that discards variables; `mock-trpc.tsx:148` wires `character.updatePersonality` to `() => Promise.resolve({})`, so no shared spy captures the payload. The fix must therefore override `mutationOptions` per test (cf. `packages/client/src/hooks/vtt-drawer/use-confirm-cast.test.ts:32-44` and `packages/client/src/hooks/character-sheet/use-weapon-masteries.test.ts:10-36`).
- `packages/client/src/hooks/use-character-actions.test.ts:14-39` — the `TEST_CHARACTERS` fixtures confirm `char-1` is `private` and `char-2` is `public`, so the toggle-direction assertions below use real fixture state.

## Proposed direction
Override `trpc.character.updatePersonality.mutationOptions` so its `mutationFn` is a per-test `vi.fn()` (`mutationFn: mockUpdatePersonality`) — the mutation passes its variables to `mutationFn` as the first argument, so the spy captures the `{ id, visibility }` payload directly. This is the established pattern in `vtt-drawer/use-confirm-cast.test.ts` (`:32-44`, spread the real `mutationOptions(opts)` then replace `mutationFn`) and `character-sheet/use-weapon-masteries.test.ts` (`:10-36`, a `vi.hoisted` `mockSetMasteries` swapped into the `set.mutationOptions` override and asserted via `mock.calls[0][0]`). Then make each toggle test `async` and wrap the payload assertion in `await waitFor(...)`, because TanStack Query's `mutate()` runs the `mutationFn` on a microtask — the spy will not have fired by the time the synchronous `act()` returns:
- private→public (`char-1`): `await waitFor(() => expect(mockUpdatePersonality).toHaveBeenCalledWith({ id: "char-1", visibility: "public" }))`.
- public→private (`char-2`): `await waitFor(() => expect(mockUpdatePersonality).toHaveBeenCalledWith({ id: "char-2", visibility: "private" }))`.

Keep the `not.toThrow()` expectation if desired; the added payload assertion is what makes the inversion map and `id` plumbing actually protected. Assert the exact object (`toHaveBeenCalledWith({ ... })`), not a bare `toHaveBeenCalled()`, so a dropped-`id` or non-inverting regression fails; optionally add `expect(mockUpdatePersonality).toHaveBeenCalledTimes(1)` to catch a double-fire regression. This strengthens coverage from "no exception thrown" to "correct mutation fired with the correctly inverted payload." Both reference tests cited above already assert inside `await waitFor(...)`, so the `async` + `waitFor` requirement is the established convention, not new overhead; run-time impact remains negligible.

## Scope / caveats
Touch only `packages/client/src/hooks/use-character-actions.test.ts`; no source change. The fix is a few lines more involved than a one-line spy because the default mock `mutationFn` discards variables — use the per-test `mutationOptions` override (`vtt-drawer/use-confirm-cast.test.ts:32-44` / `character-sheet/use-weapon-masteries.test.ts:10-36`) rather than spying on `.mutate`. No flakiness risk: the `await waitFor(...)` resolves as soon as the microtask-scheduled `mutationFn` fires, deterministically, in the jsdom environment. This finding merges a duplicate report of the same gap (folded in here). It is scoped to the mutation payload plus the `VISIBILITY_TOGGLE` inversion; the post-toggle cache-key invalidation is out of scope (and has no separate finding in the pack). Low risk, no sequencing dependency on other findings.
