# 2. Type-heavy client dialog tests use the default `userEvent.setup()` (per-keystroke macrotask) instead of `{ delay: null }`

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: speed · Area: client · Severity: med · Size: M · Confidence: high
Theme: jsdom-typing-cost · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
Type-heavy client component tests create their `userEvent` instance with the default `userEvent.setup()` and no delay override. In user-event v14 the keyboard handler awaits a `wait()` per keystroke; for the default numeric delay, `wait()` returns `Promise.all([new Promise(resolve => globalThis.setTimeout(() => resolve(), delay)), config.advanceTimers(delay)])` — i.e. it schedules a real `setTimeout` macrotask between every simulated keystroke (verified in the installed `@testing-library/user-event@14.6.1` source at `utils/misc/wait.js`). Passing `{ delay: null }` makes that same function short-circuit on `if (typeof delay !== 'number') return;`, eliminating the inter-keystroke macrotask entirely. Every keystroke event still fires and each React re-render still happens; only the *waiting between* keystrokes is removed, so the event sequence the tests assert on is byte-for-byte unchanged.

Form/dialog tests that fill multi-character strings pay this macrotask per character on top of one React re-render each. The two highest-value targets are `edit-item-dialog.test.tsx` (multiple clear/type sequences across several fields, e.g. `"A simple melee weapon"`) and `add-item-dialog.test.tsx` (e.g. `"50 feet of hempen rope"`); `campaign-settings-panel.test.tsx` is a third strong candidate (multiple multi-char confirm-name strings like `"rise of the dragon queen"`). The two heaviest typers in the project — `login-page.test.tsx` and `register-page.test.tsx` — *already* use `userEvent.setup({ delay: null })`, establishing precedent and proving the win; this finding closes the gap on the remaining genuinely type-heavy files.

This is a modest, honest speed finding, not a headline win. Most of any single file's wall time is fixed transform/import/jsdom overhead that `delay: null` cannot touch, and the typed volume in most files is small. It is worth doing because it is mechanical, zero-risk, and aligns the codebase with a precedent already set in its two heaviest files.

## Evidence
- `packages/client/src/components/sheet/edit-item-dialog.test.tsx:43` — `const user = userEvent.setup();` (no delay override); lines 46-70 run clear/type sequences typing multi-char strings including `"Greatsword"`, `"Dagger"`, and `"A simple melee weapon"` (line 70). Strongest target.
- `packages/client/src/components/sheet/add-item-dialog.test.tsx:47` — `const user = userEvent.setup();` then `user.type(..., "Rope")` (line 50) and `user.type(..., "50 feet of hempen rope")` (line 55). Second strongest target.
- `packages/client/src/components/campaign/settings/campaign-settings-panel.test.tsx:91` — `const user = userEvent.setup();`; later multi-char `user.type` calls e.g. `"New description"` (line 106), `"rise of the dragon queen"` (line 188), `"Rise of the Dragon Queen"` (line 204). Third strong target.
- `node_modules/.bun/@testing-library+user-event@14.6.1+.../@testing-library/user-event/dist/esm/utils/misc/wait.js:1-10` — `wait(config)`: `if (typeof delay !== 'number') return;` then `return Promise.all([new Promise(resolve => globalThis.setTimeout(() => resolve(), delay)), config.advanceTimers(delay)])`. Confirms the numeric-delay (default) path schedules a per-keystroke macrotask, and `delay: null` short-circuits it. (Installed source; the original finding paraphrased the `setTimeout` as a bare promise — the real form wraps it in `Promise.all` with `advanceTimers`.)
- `packages/client/src/pages/register-page.test.tsx` + `packages/client/src/pages/login-page.test.tsx` — the ONLY two files using `userEvent.setup({ delay: null })` (verified `rg "delay: null" packages/client/src` → exactly these 2 files). These are the heaviest typers and are already optimized — the precedent this finding extends.
- `packages/client/src/components/sheet/roll-context-menu.test.tsx:48` — the one place that customizes `setup()` does so for fake timers: `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })` (10 occurrences). Confirms no project-wide fast-typing convention exists, and flags this file as off-limits (its timing is intentional).
- Counts (verified at HEAD): `userEvent.setup()` appears 398 times across 91 files in `packages/client/src`; 46 `.test.tsx` files contain any `.type(` call; ~29 of those type at least one multi-character (≥4 char, non-numeric) string (verified 29 at current HEAD). Only the multi-char typers are worthwhile targets.

## Proposed direction
Pass `{ delay: null }` to `userEvent.setup()` in the genuinely type-heavy dialog/form tests — `edit-item-dialog`, `add-item-dialog`, and `campaign-settings-panel` first, then the rest of the ~29 multi-char typers (e.g. `add-token-dialog`, the `homebrew/shared` field tests, `personality-panel`, `inventory-panel`) — matching the existing `login`/`register` precedent. (Note: `create-encounter-dialog`, `npc-editor`, and `note-editor` type multi-char strings but use the static `userEvent.type` API with no `setup()` instance — the same disqualifier flagged below for `monster-tab`/`add-participant-dialog` — so they need a `setup()` refactor before `delay: null` applies.) Lower-churn alternative: add a shared `setupUser()` helper under `packages/client/src/test/` that defaults to `delay: null`, and migrate type-heavy files to it; this is the cleaner long-term shape but is optional and higher-touch. Keep the default `setup()` (or the `advanceTimers` variant) wherever a test deliberately exercises debounce/timing.

Coverage is preserved exactly: `delay: null` removes only inter-keystroke waiting. Every keystroke event still fires in the same order, every intermediate re-render still occurs, and no assertion changes. Verify each migrated file's assertions still pass with `bun run test -- <file>`.

Estimated impact (honest): a controlled A/B on the single heaviest file (`edit-item-dialog`) saved on the order of ~2s; the remainder of that file's wall is fixed transform/import/jsdom overhead the change cannot touch. Typed volume in most files is small (tens of characters), so the aggregate across all type-heavy files is on the order of a few seconds, not a headline win. Single-char-input files and click-only `setup()` sites get effectively zero benefit and are not targets.

## Scope / caveats
Target only files with multiple **multi-character** `user.type` calls. Do NOT blanket-change all 398 bare `setup()` sites — most do clicks or single-character/numeric input where `delay: null` saves nothing.

Several originally-named or implied targets are wrong and must be excluded:
- `add-spell-dialog.test.tsx` and `equipment-summary.test.tsx` — verified **zero** `.type` calls; not typing tests at all.
- `monster-tab.test.tsx` — exactly one `.type` call, `userEvent.type(input, "goblin")` at line 76, and it uses the static `userEvent.type` API, not a `setup()` instance, so there is no `setup()` to add `delay: null` to without restructuring; the 6-char type is also dwarfed by the file's debounced-search `waitFor` calls. Skip.
- `add-participant-dialog.test.tsx` — despite appearing in the multi-char grep, it calls the static `userEvent.type(...)` API (no `setup()` instance) and types only short strings (`"Goblin"`, `"7"`, `"13"`); not a clean `delay: null` target without an API change. Treat as out of scope unless a `setup()` refactor is done.
- `ability-scores.test.tsx` — types only short **numeric** strings (`"20"`, `"14"`, `"18"`, `"12"`); negligible benefit. Drop from the strong-target list (the original finding named it as a primary target; re-verification shows it is numeric-only and weak).
- `hp-adjuster.test.tsx` — 18 `.type` calls, all single character (`"5"`, `"3"`); near-zero benefit. Not a target.

Do not touch `roll-context-menu.test.tsx` (intentional fake-timer `advanceTimers` setup) or any test deliberately exercising debounce timing. Risk is essentially nil (mechanical, event sequence preserved); verify each migrated file's assertions still pass.

This finding was merged from two overlapping observations (the broad "default `setup()` types char-by-char" note and the narrower "heavy jsdom dialog tests omit `delay: null`" note); both reduce to the same fix. The shared `setupUser()` helper is the cleaner long-term shape but is optional and can be sequenced later. No dependency on other audit findings.
