# 1. Client jsdom suite spends most of its wall time on per-file isolation that ~100+ tests silently depend on (isolate:false is ~5x faster but red until hygiene lands)

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: speed · Area: client / test-infra · Severity: high · Size: M-L · Confidence: high
Theme: jsdom-isolation-cost · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
The client vitest project declares no pool or isolation overrides, so it inherits vitest's defaults: the `forks` pool with `isolate:true`, meaning a fresh jsdom environment and a fresh module registry are stood up per test **file**. With 265 test files that per-file teardown/respawn dominates wall time, and it is paid on every default `bun run test`, `test:client`, and pre-commit run — the client project is the single largest contributor to suite wall time.

The cost is reclaimable but **gated on test hygiene**. Re-running the identical client suite with `--no-isolate` cuts wall time by roughly 5x — but it currently goes red, because a cluster of files leak state across file boundaries (module-level Zustand store singletons, unreset `vi.fn()` mocks, unrestored global stubs) and today rely on per-file isolation to paper that over. The leakage is concrete and reproducible: under `--no-isolate` the failures cluster in the vtt-drawer, combat, tokens, and realtime-invalidation areas, and the mechanism is a `vi.mock`'d Zustand store object leaking out of one file's module registry into the next — at HEAD this manifests as leaked store state rather than a single fixed error (e.g. `spells-tab.test.tsx` expecting store mode `collapsed-cast-rail` but seeing a leaked `full`, and `features-tab.test.tsx` with a Second Wind button that should be disabled but is not). So the time is real and large, but the suite cannot safely drop isolation until the cross-file leakage is fixed. This pairs with the mock-hygiene finding (client `setup.ts` never calls `vi.clearAllMocks`/`unstubAllGlobals` in `afterEach`); fixing hygiene is the prerequisite, dropping isolation is the payoff.

Measured magnitudes vary by box and by how loaded it is, so treat the exact numbers as approximate and re-measure before acting. The author measured (8-core) ~98s isolated → ~20s with `--no-isolate`, with ~210 tests failing across ~35 files. Re-measuring at HEAD `692b437a` on this (loaded) 8-core box reproduced the same shape with different absolutes: isolated **354s wall / 351s vitest duration, 265 files / 3113 tests, all green except ~9 merge-introduced homebrew/damageType failures that are unrelated to isolation** (see the caveat below); `--no-isolate` **163 tests failed across 36 files** (~5x faster wall). The no-isolate failure absolutes have grown since the audit-HEAD measurement (94/23) because the merge added more leaky vtt-drawer/combat/tokens test files — the qualitative claim ("~100+ tests silently depend on isolation") is strengthened, not weakened. The headline holds robustly under both runs: per-file isolation costs the large majority of client wall time, and well over 100 tests silently depend on it.

**CRITICAL caveat for the no-isolate gate:** at current HEAD the *default isolated* run has ~9 failures in `homebrew-item-tab.test.tsx` / `add-item-dialog` / `edit-item-dialog` that are **isolation-INDEPENDENT** — they fail even when run standalone (introduced by the merge's `damageType` canonical-enum tightening, not by cross-file leakage). An implementer following the "flip `isolate:false` only once `--no-isolate` failures hit zero" gate must exclude or fix these ~9 separately; otherwise the no-isolate count can never reach zero no matter how many leaks are fixed.

## Evidence
- `packages/client/vitest.config.ts:5-22` — `defineProject` sets no `isolate`, `pool`, `poolOptions`, `maxWorkers`, or `fileParallelism`; only `name`, `environment: "jsdom"`, `include`, `exclude`, `setupFiles`, a `resolve.alias` block, and `coverage`. It therefore inherits vitest's defaults (`forks` pool, `isolate: true`). (Unchanged by the merge; the absent-keys enumeration above is still correct — the `resolve.alias` block does not affect isolation.)
- `packages/client/src/test/setup.ts:40-42` — `afterEach(() => { cleanup(); })` only runs React Testing Library `cleanup()`; there is no `vi.clearAllMocks` / `resetAllMocks` / `restoreAllMocks` / `unstubAllGlobals`, so mock and global state persists across files once isolation is removed.
- MEASURED at HEAD `692b437a` (8-core, loaded box): `bunx vitest run --project=client` → 265 files / 3113 tests, 351s vitest duration / 354s wall — all green **except** ~9 merge-introduced `homebrew`/`damageType` failures (`homebrew-item-tab.test.tsx`, `add-item-dialog`, `edit-item-dialog`) that fail even run standalone and are unrelated to isolation. The 265-file count matches the live tree (`find packages/client/src -name '*.test.ts*' | grep -v .slow.test.` → 265).
- MEASURED at HEAD `692b437a`: `bunx vitest run --project=client --no-isolate` → ~5x faster wall, **163 tests failed across 36 files** (up from the audit-HEAD 94/23 because the merge added more leaky files). The source-side store access at `packages/client/src/hooks/vtt-drawer/use-cast-placement.ts:61` (`const drawer = useVttDrawerStore.getState();`) is the kind of `vi.mock`'d Zustand store the cross-file leak corrupts; at HEAD the symptoms manifest as leaked store *state* (wrong store mode, stale pending flags) rather than the earlier `useVttDrawerStore.getState is not a function` TypeError, which no longer reproduces. The mechanism — a mocked store object leaking across the module registry — is exactly the cross-file state dependence the finding predicts.
- The leaking files are concrete proof of latent cross-file order/state coupling. The cited representatives exist and are in the failing set at HEAD: `packages/client/src/hooks/vtt-drawer/use-feature-use.test.ts`, `packages/client/src/hooks/vtt-drawer/use-confirm-cast.test.ts`. Other failing clusters this run: `src/components/vtt/drawer/cast-rail.test.tsx`, `src/components/campaign/combat/initiative-tracker/*.test.tsx`, `src/components/campaign/tokens/*.test.tsx`, `src/hooks/realtime-invalidation-{campaign,encounter,turn-pointer}.test.ts(x)`, `src/lib/{roll-toast,trpc-error}.test.ts`. (Author's earlier run saw ~210 fail / ~35 files; keep the count approximate — it varies by run and merge state.)

## Proposed direction
Treat as a two-step, coverage-preserving program, sequenced **after** the mock-hygiene finding (`vitest clearMocks` unset) — never flip isolation first; it is red today.

1. **Make the suite isolation-clean.** Add global mock/global reset to the client project — `clearMocks: true` + `restoreMocks: true` + `unstubGlobals: true` in the client vitest config, or the equivalent `vi.clearAllMocks()` / `vi.unstubAllGlobals()` in `setup.ts`'s `afterEach` — and fix the ~20-35 files that leak module-level/global state (the dominant pattern is a `vi.mock`'d Zustand store whose mock object does not survive into the next file; hoist/reset those per-file so the store mock is re-established in each file rather than relying on a fresh module registry). This step is mechanical and per-file, and it strengthens coverage by removing hidden order-dependence.
2. **Drop per-file isolation and re-measure.** Once step 1 drives the `--no-isolate` failures to zero, set `isolate: false` (or a scoped pool config) for the client project and re-measure. Expected impact: client wall falls by roughly 5x — on this box ~354s → ~68s, on the author's box ~98s → ~20s — making this the single largest run-time lever in the audit, on par with or exceeding the server-side `cleanDb` reset win. **Validation gate:** run the client suite with `isolate:false` AND with randomized file order (`--sequence.shuffle.files`) and confirm zero failures, to flush any residual order-dependence before committing the flip.

Also worth evaluating as a middle option: `pool: 'threads'` (lighter-weight worker isolation than `forks`) may recover a meaningful fraction of the win without going all the way to `isolate:false`, and is a lower-risk first cut if the hygiene work proves large.

## Scope / caveats
Gated finding: it depends on, and should be promoted together with, the mock-isolation/`clearMocks`-unset hygiene finding, and is reinforced by the cross-test-isolation lens. The leak count must be driven to zero before `isolate` is touched — do not flip the config flag standalone; it fails ~100+ tests today. Risk is real (silent cross-file leakage that per-file isolation currently hides), so stage it strictly: hygiene + per-file leak fixes first (mechanical), then the one-line config change plus a shuffled-order re-measure. Coverage is preserved throughout — no test is deleted or weakened; the leak fixes make existing assertions independent of file order, and the isolation change is purely an execution-environment knob validated by a green shuffled run. This is jsdom/module-registry isolation and is distinct from the server-side `cleanDb` DB-isolation levers (different mechanism, different package); they can land independently. The absolute timings here are box- and load-dependent (this box ran ~3.6x slower than the author's); re-measure on the target CI/dev hardware before quoting savings.
