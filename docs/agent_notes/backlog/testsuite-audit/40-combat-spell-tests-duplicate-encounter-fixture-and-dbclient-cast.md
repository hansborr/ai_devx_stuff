# 40. makeMonsterEncounter fixture and the DbClient cast are copy-pasted across combat/spell service tests instead of reusing existing helpers

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: server · Severity: low · Size: S · Confidence: high
Theme: server-test-fixture-duplication · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
**Step 2 (DbClient cast) is RESOLVED by merge `692b437a`.** The merge added `utils/prisma-types.ts` with a `toDbClient()` factory (the one sanctioned `as unknown as DbClient`), rewrote `test-db.ts` to `export const db = toDbClient(prisma)`, and migrated all the straggler files to `import { db } from "../../test/test-db.js"` — `prisma as unknown as DbClient` now exists nowhere in `packages/server/src` outside the `toDbClient()` boundary. Only **Step 1 (the `makeMonsterEncounter` fixture duplication) remains actionable.** The cast discussion below is retained only as already-landed precedent the implementer can follow for the "one sanctioned place" ethos.

The combat and spell service tests each grow their own private copy of the same "active two-monster encounter" scaffold. The shape is identical every time: `createEncounter` → `addParticipant` ×2 → a `setInitiative` loop → `transitionState` to `active` → a `prisma.encounter.findUniqueOrThrow` reload to recover the post-transition `round` / `currentTurnIndex` → return the participant ids and the row. `combat-actions.test.ts` declares it as `makeMonsterEncounter` plus a local `MonsterEncounter` interface; `spell-casting.test.ts` declares a near-verbatim `makeMonsterEncounter` with its own `MonsterEncounter` interface; and `combat-actions-advance-turn.test.ts` carries a third and fourth copy as `makeThreeMonsterEncounter` / `makeTwoMonsterEncounter`. That is at least three structurally identical scaffolds (four functions), each with its own HP/AC magic constants and its own return type. The copies diverge only in cosmetic field names — `attackerParticipantId` (combat) vs `casterParticipantId` (spell) vs a positional `participantIds: [...]` tuple (advance-turn) — which is exactly the kind of accidental drift that makes the duplication invisible to a reader. A change to the encounter-setup contract (say, a newly required `addParticipant` field, or a second reload to capture a new column) must be hand-applied to every copy, and the next combat/spell service test will copy whichever scaffold happens to be nearest.

Note on drift since capture: `encounter-test-helper.ts` has since grown a `buildActiveBattle` two-monster fixture (line 129) and a `createActiveEncounter` single-monster fixture, but both return only an `EncounterDetail` — neither returns the participant ids or the reloaded `round` / `currentTurnIndex` that the service scaffolds depend on, so they are not drop-in replacements. The service-test duplication therefore still stands; the helper simply needs a participant-id-returning variant.

The cast half of this finding is fully resolved by merge `692b437a`, which migrated all the previously-straggling service tests (and 5 more `utils/*-mutations.test.ts` files) to `import { db } from "../../test/test-db.js"`.

## Proposed direction
One mechanical step (the cast half having already landed via merge `692b437a`).

(1) Fixture. Add a participant-id-returning helper to `encounter-test-helper.ts`, e.g. `makeActiveMonsterEncounter(app, token, { campaignId, count?, overrides? })` that returns `{ encounterId, participantIds, round, turnIndex }` (the superset the four scaffolds need), plus a single exported `MonsterEncounter`-style type. The exported type reconciles the divergent field names: keep the positional `participantIds` tuple as the source of truth and let call sites destructure (`const [attackerParticipantId, targetParticipantId] = participantIds`) rather than baking `attacker`/`caster` naming into the helper. Migrate `combat-actions.test.ts`, `spell-casting.test.ts`, and `combat-actions-advance-turn.test.ts` to import it; keep every behavioral assertion in the migrated tests verbatim — only the setup lines change. Because `buildActiveBattle` already exists and only differs by not returning ids, prefer extending/generalizing it over adding a fourth helper, to avoid trading one duplication for another. Optionally fold the two router-test copies (`createActiveEncounterWithMonsters`, `createActiveEncounterWithCharacterTarget`) into the same helper in a follow-up.

Estimated impact: a single edit point for the encounter-setup contract instead of four, and less to read/copy when the next combat or spell service test is added. No run-time/speed change — this is read-and-write ergonomics, not test count. (The cast half — removing per-file `prisma as unknown as DbClient` declarations in favor of the centralized `db`/`toDbClient` export — has already landed via merge `692b437a` and is the canonical anchor the new fixture helper should follow for the "one sanctioned place" ethos.)

## Scope / caveats
Low-risk, behavior-preserving consolidation within `packages/server` test scaffolding only; no source files and no assertions change. The fixture half (step 1) requires reconciling the `attacker`/`caster`/positional field-name differences in one exported type — do this by destructuring at call sites so no behavioral assertion is touched. Preserve coverage by migrating, not rewriting: each `it()` keeps its exact assertions; only the `make…Encounter` body is replaced by the shared helper, and the helper reproduces the same create→participants→initiative→transition→reload sequence (including the `findUniqueOrThrow` reload that recovers post-transition `round`/`turnIndex`).
