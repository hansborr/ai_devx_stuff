# 13. castCombatSpell never deterministically exercises the spell-attack HIT damage-apply path (no rng seam)

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting. (Line numbers refreshed for merge `692b437a`, which switched both `combat-actions.test.ts` and `spell-casting.test.ts` to `import { db } from "../../test/test-db.js"` — removing their local `prisma as unknown as DbClient` casts and shifting cited lines down; this does not affect the seam gap.)
Lens: defect-catching · Area: server · Severity: med · Size: S-M · Confidence: high
Theme: server-spell-integration-seam · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
`castCombatSpell` is the integration entry point that wires spell-roll resolution → apply-damage-in-tx → persist-HP for combat spells. It resolves the deciding attack roll through `resolveWithDiceErrorWrapping`, which calls `resolveSpellByMode(input, loaded, cryptoRng)` with a **hardcoded** `cryptoRng` (`spell-casting.ts:38`). `CombatSpellOpts` (`types.ts:15`) exposes no rng override, so `spell-casting.test.ts` has no way to force a deterministic spell-**attack** hit. The custom-spell-attack integration test acknowledges this with the comment *"The roll can still critically miss on natural 1 — assert shape, not hit"* (`spell-casting.test.ts:216`) and asserts only result shape (`type` / `spellName` / `slotUsed` / `affectedCharacterIds`), never that the target's HP decreased on a hit.

By contrast the **save** path *is* deterministically verified: it forces `HIGH_DC` (DC math beats any d20, so no rng seam is needed) and then asserts `target.currentHp < INITIAL_HP` (`spell-casting.test.ts:254-255`). The asymmetry is the whole point — the save branch can prove persist-on-effect with a DC trick, but the attack branch genuinely needs an injected rng to defeat the natural-1 crit-miss branch (`packages/shared/src/rules/attack-roll.ts:58`), and that seam does not exist.

This matters because `apply-damage.ts` in the spell-casting module has **no colocated unit test** of its own, so this integration test is the *only* coverage of the attack-hit → damage-applied → HP-persisted wiring — and that branch is never exercised. A regression that resolves an attack hit but fails to apply or persist the damage (or applies the wrong amount) would ship green. Note the gap is specifically the *service-level integration* of a hit: the pure roll/damage math is already covered deterministically in `resolve-spell.test.ts` via injected rng (`sequenceRng` / `fixedRng`, lines 312-343), so this is not a request to re-test the dice.

The sibling attack path already solved exactly this. `executeAttack` threads one optional `rng` (default `cryptoRng`) into both the resolve step and the tx, and its tests inject `midRng` to force a hit and deterministically assert `target.currentHp` dropped (`combat-actions.test.ts:199-217`) plus a concentration-drop case (`combat-actions.test.ts:292-330`). The spell path lacks the production seam that makes that assertion possible.

## Evidence
- `packages/server/src/services/spell-casting/spell-casting.ts:38` — `resolveWithDiceErrorWrapping` calls `resolveSpellByMode(input, loaded, cryptoRng)` with a hardcoded rng. This (not the tx-level `rng: cryptoRng` at `:88`, which only feeds `checkConcentrationOnDamage`) is the seam the spell-attack hit lacks.
- `packages/server/src/services/spell-casting/types.ts:15` — `CombatSpellOpts` declares `prisma`/`input`/`expectedRound`/`expectedTurnIndex`/`isDm` and **no** `rng`, so no caller (test or prod) can override the attack roll.
- `packages/server/src/services/spell-casting/resolve-spell.ts:302-306` — `resolveSpellByMode(input, loaded, rng: RngFn)` already takes and threads an rng to every mode (`customSpellAttack` etc.); the resolver chain is rng-ready, only the `castCombatSpell` call site hardcodes `cryptoRng`.
- `packages/server/src/services/spell-casting/spell-casting.test.ts:216` — comment "The roll can still critically miss on natural 1 — assert shape, not hit"; the test (193-222) asserts only `result.spellResult.type` / `spellName` / `slotUsed` / `affectedCharacterIds`, never target HP after a hit.
- `packages/server/src/services/spell-casting/spell-casting.test.ts:254-255` — the SAVE path forces `HIGH_DC` then asserts `target.currentHp < INITIAL_HP` (30), proving the deterministic persist-on-effect pattern is achievable when a seam (here, DC math) exists.
- `packages/server/src/services/spell-casting/apply-damage.ts` — exists with **no** colocated `apply-damage.test.ts`; this integration test is the only coverage of its hit→persist behavior.
- `packages/server/src/services/combat-actions/types.ts:26-27` — sibling `AttackOpts` declares `readonly rng?: RngFn; /** Override RNG for deterministic tests. Defaults to cryptoRng in production. */` — the precedent the spell path lacks.
- `packages/server/src/services/combat-actions/combat-actions.ts:98` — `const { ..., rng = cryptoRng } = opts;` threads the one optional rng into both the resolve step and the tx (default `cryptoRng`).
- `packages/server/src/services/combat-actions/combat-actions.test.ts:199-217` — `executeAttack` injected with `midRng` forces a hit and asserts `target.currentHp < TARGET_HP` (assertion at :214); the concentration-drop case at `:292-330` (also `midRng`) asserts `concentrationSpellId` cleared. This is the deterministic hit→damage→persist assertion the spell path is missing.
- `packages/server/src/services/spell-casting/resolve-spell.test.ts:312-343` — pure spell-attack roll math is already covered deterministically via `sequenceRng([12,5,6])` (hit) and `fixedRng(3)` (miss), so closing this gap does not duplicate the dice math.

## Proposed direction
Thread an optional `rng` through `CombatSpellOpts` (default `cryptoRng`) all the way to the `resolveSpellByMode` call at `spell-casting.ts:38`, mirroring exactly how `executeAttack` already destructures `rng = cryptoRng` and feeds it to resolve+tx (`combat-actions.ts:98`). Concretely: add `readonly rng?: RngFn` to `CombatSpellOpts`, destructure `rng = cryptoRng` in `castCombatSpell`, and pass it into `resolveWithDiceErrorWrapping` → `resolveSpellByMode` (the resolver chain in `resolve-spell.ts:302` already accepts it, so no signature change is needed below the call site). Then add a `spell-casting.test.ts` case that injects a high-roll rng to force a spell-**attack** HIT and asserts `target.currentHp` decreased and that `slotUsed`/`affectedCharacterIds` are correct — the attack-side analogue of the existing save-path persist assertion. Keep the existing shape-only test as the explicit crit-miss edge case.

Net: strengthens coverage (adds the one missing deterministic assertion on the attack-hit persist branch), adds a production seam already proven on the attack side, and removes no coverage. Estimated impact: closes a defect class (spell-attack damage not persisted/mis-persisted on hit) that currently slips through the only integration-level spell test, with a bounded blast radius — the pure roll math is covered in `resolve-spell.test.ts` and the save-path persist is already covered, so this is one new assertion on a narrow integration branch. No measurable runtime cost: the new test is one more in-tx cast, comparable to the existing save cases.

## Scope / caveats
Touch `CombatSpellOpts` (`types.ts:15`), the `castCombatSpell` destructure, and the `resolveSpellByMode` call site at `spell-casting.ts:38` plus passing `rng` through `resolveWithDiceErrorWrapping`; the resolver chain (`resolve-spell.ts:302`) already accepts an rng and needs no change. Do **not** confuse this with the tx-level `rng: cryptoRng` at `spell-casting.ts:88` — that only feeds `checkConcentrationOnDamage` and will not make the attack roll deterministic. Default the new param to `cryptoRng` so production behavior is unchanged. Keep the existing shape-only crit-miss test (do not delete it). Risk is low: additive seam mirroring an existing production pattern. Before writing the assertion, verify the injected rng actually reaches the d20 consumed in `attack-roll.ts` and that a forced high roll defeats the natural-1 crit-miss branch (`packages/shared/src/rules/attack-roll.ts:58`, where `criticalMiss = naturalRoll === NATURAL_MISS`). Sequence after confirming `resolve-spell.test.ts:312-343` already covers the pure math so you do not duplicate it.
