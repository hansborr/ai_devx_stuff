# 27. Seven bare `message: /regex/` eslint-rules assertions are brittle and inconsistent with the dominant messageId convention

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: defect-catching · Area: eslint-rules (tooling/dogfood) · Severity: low · Size: XS · Confidence: high
Theme: assertion-precision · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
Seven `RuleTester` invalid cases across five eslint-rules test files assert against the diagnostic via `errors: [{ message: /<doc-path-or-prose-fragment>/u }]` — matching the static tail of the message (a doc path like `docs/guides/add-trpc-procedure.md`, or prose like ``Rename to `<feature>.test.ts` ``). Every one of these rules already defines a distinct `messageId`, and sibling invalid cases in the very same files assert with the `messageId` form. So the regex form is a gratuitous deviation from the dominant convention, and it is brittle in exactly the wrong way: it couples the test to the message's prose/doc-path, so any guide rename or wording tweak fails the rule's own test for a reason that has nothing to do with the rule's logic.

The honest framing is brittleness + inconsistency, not redundancy. The central `eslint-rules/message-guidance.test.js` validates each message's Why/How shape, action word, and length, but it does *not* assert these doc-paths or prose into the message string: `test-file-location`'s two messages are in `EXEMPT_MESSAGE_IDS` (so their prose is never structurally checked at all), and for the doc-path rules the central test only `existsSync`-checks `meta.docs.pairedGuide` — it never asserts that the guide path appears in the emitted message. That means these seven regexes are the *only* tests coupling the doc-path/prose into the message. The fix must therefore keep covering the same diagnostic branch, which `messageId` does — more precisely than a substring match, since `messageId` pins the exact message key and the `context.report` branch that produced it.

## Evidence
- `eslint-rules/strict-trpc-input.test.js:43` — `errors: [{ message: /docs\/guides\/add-trpc-procedure\.md/u }]`; the sibling invalid case at `:48` uses `messageId: "needsStrict"` — the only message the rule defines (`strict-trpc-input.js:67-68`, reported at `strict-trpc-input.js:86`).
- `eslint-rules/strict-shared-schemas.test.js:48` — `errors: [{ message: /docs\/guides\/add-trpc-procedure\.md/u }]`; siblings at `:54`, `:59`, `:66` use `messageId: "needsExplicit"` (defined `strict-shared-schemas.js:99`, reported `:121`).
- `eslint-rules/no-broadcast-in-transaction.test.js:45` — `errors: [{ message: /docs\/guides\/add-socket-broadcast\.md/u }]`; siblings at `:53`, `:63`, `:64` use `messageId: "noBroadcastInTransaction"` (defined `no-broadcast-in-transaction.js:56`, reported `:90`).
- `eslint-rules/test-file-location.test.js:55`, `:61` — `message: /Rename to \`<feature>\.test\.ts\`/u`, and `:67` — `message: /helpers belong outside the test-file naming/u`; these restate the `wrongNaming` (`test-file-location.js:34`) and `missingTests` (`:36`) messages, both distinct messageIds (reported `:70`/`:73`). Both ids sit in `EXEMPT_MESSAGE_IDS` in the central test (`message-guidance.test.js:69-70`), so their prose is *not* structurally validated anywhere else.
- `eslint-rules/concurrency-guard.test.js:44` — `message: /codemod:concurrency-guard -- <file>.*docs\/CONCURRENCY\.md/u`; siblings at `:49`, `:54`, `:62` use `messageId: "noDirectWrite"` (defined `concurrency-guard.js:112`, reported `:130`).
- Total: `rg -n "message: /" eslint-rules/*.test.js` returns exactly **7** assertions across **5** files (concurrency-guard 1, strict-trpc-input 1, strict-shared-schemas 1, no-broadcast-in-transaction 1, test-file-location 3). The central test's only doc-path coupling is an `existsSync` check on `meta.docs.pairedGuide` (`message-guidance.test.js:114-118`) — it never asserts the path appears in the message string.

## Proposed direction
Replace each of the 7 `message: /.../u` assertions with the rule's `messageId` (e.g. `errors: [{ messageId: "needsStrict" }]`), matching the sibling cases already in each file. Where the substituted value in the message is itself the point of the case (it generally is not here — the regexes target the static guide path/prose, not interpolated data), use the `RuleTester` `data:` form (`{ messageId, data: { ... } }`) to pin the substitution explicitly rather than via a substring. Coverage is preserved and strengthened: `messageId` pins the exact diagnostic key and the `context.report` branch that emits it — strictly more precise than a substring regex — while removing the brittle prose/doc-path coupling. After the change, re-run the five rule test suites (`bun run test:scripts:file -- eslint-rules/<rule>.test.js` per file) and confirm the same invalid-case count still fails on the same branch. No assertion is dropped; each is made more robust.

Estimated impact: removes 7 brittle prose/doc-path couplings, so a guide move (`docs/guides/*`, `docs/CONCURRENCY.md`) or message-wording tweak no longer fails unrelated rule tests, and unifies all invalid-case assertions on the messageId convention. Robustness gain with zero coverage loss; negligible runtime effect (this is a precision/maintainability change, not a speed one).

## Scope / caveats
TOUCH: only the 5 cited `eslint-rules/*.test.js` files (7 assertions total). NOT-TOUCH: the rule source, the message text itself, and the central `message-guidance.test.js`. RISK: trivial — `messageId` is strictly more precise than the substring regex it replaces, and the sibling cases already prove the form works in each file.

FRAMING: this is a defect-catching/assertion-precision item filed as "brittle + inconsistent with the messageId convention", **not** "fully redundant with central validation" — the central test does not assert these doc-paths/prose (EXEMPT for `test-file-location`; `existsSync`-only for the paired-guide path), so these regexes are currently the only tests covering that coupling, and the fix must keep covering the same branch (messageId does). This finding merges in the earlier observation that the bare regexes re-encode static prose and could use messageId; that material is folded here under the same precision framing.

SEQUENCING: standalone; complements the RuleTester-config-factory finding (same five files) but does not depend on it. Distinct from the bare-`toThrow`/`expectParseFailure` findings (`dice-notation-error-tests-bare-tothrow`, `seed-parser-*-bare`), which target a different assertion pattern in different files.
