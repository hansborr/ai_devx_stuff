# 35. Five realtime-invalidation socket-hook tests share a byte-identical 29-line mock scaffold with no shared harness

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: maintainability · Area: client · Severity: med · Size: S-M · Confidence: high
Theme: socket-hook-test-scaffold · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
The realtime-invalidation hook suite is the client's contract test for "socket broadcast lands → the right TanStack Query key is invalidated/refetched." It is split into five colocated spec files, one per surface (campaign, map, encounter, character-sheet, turn-pointer), and every one of them opens by re-declaring the same socket-mock plumbing from scratch: a `mockSocket` with `on`/`off`/`emit` `vi.fn()`s, a `vi.hoisted` `mockUseSocket`, `vi.mock("./use-socket", …)`, `vi.mock("@/lib/trpc.js", …)`, and a `beforeEach` that resets the mocks and re-arms `mockUseSocket` to return the connected socket. Across `realtime-invalidation-{campaign,map,encounter,character-sheet}.test.ts` this block is not merely similar — it is byte-identical (lines 8-36 of all four hash to the same sha256 `fa47514a…`). The fifth file, `realtime-invalidation-turn-pointer.test.tsx`, carries the same scaffold verbatim, only pushed down by its regression-guard header comment (and it is a `.tsx`).

The duplication does not stop at the header. Each spec then re-implements the handler-extraction idiom inline — `mockSocket.on.mock.calls.find(call => call[0] === EVENT)?.[1]` — once per event it exercises, for 10 occurrences across the five files. The connected / not-connected / null-socket / wrong-campaign permutations are likewise re-typed per file. The cost is concentrated exactly where it hurts: a developer changing the socket-invalidation contract (e.g. adding a new payload field, or switching `useSocket`'s return shape) must hand-edit the same scaffold in 5+ places, and the copy-paste invites the four mock blocks to silently drift apart over time. Worse, a reusable `getHandler(event)` helper already exists in `use-campaign-presence.test.ts:44-47` but was never promoted, and `use-notifications.test.ts` repeats the same `mockSocket`/`mockUseSocket`/`vi.mock` pattern as a seventh consumer — so the repo has already paid the "write the helper once" cost and then re-paid the "inline it everywhere" cost. This is pure maintainability/onboarding friction; the tests all pass and the coverage is real.

## Evidence
- `packages/client/src/hooks/realtime-invalidation-campaign.test.ts:8-36`, `realtime-invalidation-map.test.ts:8-36`, `realtime-invalidation-encounter.test.ts:8-36`, `realtime-invalidation-character-sheet.test.ts:8-36` — the `mockSocket` / `vi.hoisted mockUseSocket` / `vi.mock("./use-socket")` / `vi.mock("@/lib/trpc.js")` / `beforeEach` scaffold; verified byte-identical (all four hash to sha256 `fa47514a2a005ffd7d174bd04844def92e3564aebb22f6addcfcb05bf7dffe3d`).
- `packages/client/src/hooks/realtime-invalidation-turn-pointer.test.tsx:36-64` — same scaffold, byte-for-byte, with a ~28-line downward offset: a 14-line ux-audit regression-guard comment at lines 9-22, plus extra imports and the `PointerState` constants block at lines 24-34 (the comment alone is not the full offset). This file is `.tsx`, asserts a *live refetch* (`expect(queryFn).toHaveBeenCalledTimes(2)` at line 110, not just an invalidate spy) and uses a custom throw-on-missing `emitEncounterUpdated()` wrapper at lines 66-72.
- `packages/client/src/hooks/use-campaign-presence.test.ts:44-47` — the reusable `getHandler(event)` helper that already exists but was never promoted out of this one file.
- `packages/client/src/hooks/use-notifications.test.ts:8-37` — the same `mockSocket` / `mockUseSocket` / `vi.mock` / `beforeEach` pattern (a seventh consumer; near-identical, with one extra `mockSocket.emit.mockReset()` at line 31).
- 10 inline `mockSocket.on.mock.calls.find(call => call[0] === EVENT)?.[1]` handler extractions across the five realtime-invalidation specs (campaign 2, map 2, encounter 2, character-sheet 3, turn-pointer 1); no socket harness exists under `packages/client/src/test/` (verified: that dir holds fixtures + `mock-trpc*`, but nothing socket-hook related, and no `socket-hook-harness`).

## Proposed direction
Extract a tiny harness — e.g. `packages/client/src/test/socket-hook-harness.ts` — that owns the duplicated surface and nothing else: the `mockSocket` object, the `vi.hoisted` `mockUseSocket`, the `vi.mock("./use-socket", …)` / `vi.mock("@/lib/trpc.js", …)` wiring, a promoted `getHandler(event)` (lifted from `use-campaign-presence.test.ts:44-47`), and `setConnected()` / `setDisconnected()` / null-socket helpers that drive `mockUseSocket.mockReturnValue(...)`.

Path-resolution caveat: a harness living in `packages/client/src/test/` **cannot** simply re-export the hook tests' relative `vi.mock("./use-socket", …)` call — `vi.mock` module specifiers resolve relative to the *importer* (the calling spec file), not the harness, so `"./use-socket"` would resolve against `src/test/` and miss `src/hooks/use-socket`. Either mock via an alias/resolved path (e.g. `@/hooks/use-socket`) from the harness, or keep a tiny top-level `vi.mock("./use-socket", …)` in each spec that delegates its factory body to the harness. Do not assume a single re-exported `vi.mock` covers all five specs.

Each spec keeps its own `describe` and every existing `it()` assertion; it just imports the harness and drops the ~29-line header (the `beforeEach` reset can stay in the harness or be re-exported). Coverage is preserved exactly: every `it()` still renders the same hook against the same mocked socket and asserts the same invalidation/refetch — only the scaffold is centralized, so a future contract change is a one-file edit.

Estimated impact: removes roughly 150 lines of duplicated scaffold across the five realtime-invalidation files (seven consumers if `use-notifications` and `use-campaign-presence` are migrated in the same pass), and collapses the 10 inline `mock.calls.find(...)` extractions into one promoted `getHandler`. This is a readability/maintenance win, not a runtime-speed win — the suites already run in milliseconds, so do not expect a wall-clock change.

## Scope / caveats
Pure test-scaffold maintainability: no defect-class gap, no runtime cost, no flakiness risk — every `it()` keeps running against the same mocked socket. Touch only the test files and the new harness; do not touch `realtime-invalidation.ts` or any hook source.

Preserve the stronger per-file assertions when migrating — they are the whole point of those files and must not be flattened to a generic `getHandler` call:
- `realtime-invalidation-turn-pointer.test.tsx` is a deliberate ux-audit P0-2 regression guard. It asserts a *live refetch* (`queryFn` called twice, the pointer actually moving from `STALE_POINTER` to `FRESH_POINTER`), not just that `invalidateQueries` was spied, and it uses a throw-on-missing `emitEncounterUpdated()` wrapper. Keep both behaviors; the harness's `getHandler` may back the wrapper but the wrapper's throw-on-missing contract must survive.
- `character-sheet` and `encounter` layer null-socket / not-connected / wrong-campaign permutations and an invalidation-count assertion on top of the base scaffold — the harness must expose `setConnected`/`setDisconnected` (and a null-socket mode) so those per-spec assertions stay intact.
