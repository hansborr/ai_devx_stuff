# 25. Cross-field schema refinements verified only with bare `expectParseFailure`, not the failing rule's path/message

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: defect-catching · Area: shared · Severity: low · Size: S · Confidence: high
Theme: schema-refinement-discrimination · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
A handful of `packages/shared` input schemas attach a multi-issue `superRefine` (or a multi-condition `.refine`) that encodes a cross-field business rule with several independent branches. Their co-located tests reject the bad input with a bare `expectParseFailure(result)` and stop there — they assert only that the parse failed, never *which* branch failed. For a single-field constraint that is harmless: there is exactly one way the input can be invalid, so a failure can only mean that rule fired. But a multi-branch `superRefine` driven by an input that violates two or more branches at once is a masking trap: the test passes as long as the input is invalid for *any* reason, so if one branch silently stops emitting its issue (a `===`/`!==` flip, a dropped `addIssue`, a changed `path`), the test stays green because a sibling branch still rejects the same fixture. The broken branch ships unnoticed.

This is the most breakable category of validation in the package — dual-mode inventory inputs (homebrew vs. custom source), the encounter participant discriminated union (monsterId vs. homebrew entry id/version coupling), and the character ASI/level-up coupling rules — and it is exactly where a green test today proves the least. The true multi-issue masking cases are the inventory homebrew-source coupling and the encounter participant union, where one fixture can trip several branches at once; some fixtures (e.g. the empty-ASI case) already isolate a single branch, so there the gain is asserting path/message rather than de-masking. The fix is essentially free: the good pattern already lives in the same scope. `campaign-inputs.test.ts:57` pins `result.error?.issues[0]?.message`, `note.test.ts` and `homebrew.test.ts` pin message/path, and `harness-diagnostics.test.ts:61` uses `issues.some((i) => i.path... )`. The `expectParseFailure` helper already *returns* the `ZodError` (`parse-helpers.ts:29-40`), so chaining a path/message assertion onto an existing call is a one-line, no-new-fixture extension — not a new test.

This is narrower than "every refine in shared." Most single-field value/format refines have near-zero masking risk (one constraint, one failure mode), and several refine-bearing schemas have no co-located test file at all, so they are out of scope for an "extend the assertion" commit. The value is concentrated in the few multi-branch superRefines whose co-located tests use only bare `expectParseFailure`. ## Evidence
- `packages/shared/src/schemas/inventory-inputs.ts:35` — `createInventoryItemInputSchema` `.superRefine((val, ctx) => { ... })`: two independent `addIssue` branches (`sourceId` required and `campaignId` required when `sourceType === "homebrew"`) on paths `["sourceId"]` and `["campaignId"]`. A homebrew item missing both fires two issues at once. `inventory-inputs.test.ts` has 23 `expectParseFailure` calls and 0 `issues[...].path` / `.message` assertions (rg) — no branch discrimination.
- `packages/shared/src/schemas/encounter-inputs.ts:153` — `addParticipantInputSchema` `.superRefine` (the discriminatedUnion members span `:147-152`) over the participant discriminated union: three coupled branches for the monster case (`monsterId`+`homebrewMonsterEntryId` mutually exclusive; `homebrewMonsterEntryId` requires `homebrewMonsterEntryVersion`; version requires id), on paths `["homebrewMonsterEntryId"]` / `["homebrewMonsterEntryVersion"]`. `encounter-inputs.test.ts` has 32 `expectParseFailure` calls and 0 path/message assertions.
- `packages/shared/src/schemas/character-inputs.ts:250` — `asiChoiceSchema.refine` with message `"When choosing Ability Score Improvement, asiIncreases must total exactly 2 points"` and `path: ["asiIncreases"]`. The same file has a second coupled `.refine` at `:295` on `levelUpInputSchema` (`hpRolled` required when `hpMethod === "roll"`, `path: ["hpRolled"]`). `character-inputs.test.ts:75` rejects an empty-ASI fixture with bare `expectParseFailure(result)` (test block `:70-76`); the file has 36 bare calls and 0 path/message assertions.
- `packages/shared/src/schemas/campaign-inputs.test.ts:57` — model of the correct pattern: `expect(result.error?.issues[0]?.message).toBe("Campaign name is required.")`. `note.test.ts` and `homebrew.test.ts` (`expect(result.error.issues[0]?.path).toEqual(["expectedVersion"])`) already do the same; `harness-diagnostics.test.ts:61` uses `expect(error.issues.some((i) => i.path.join(".") === "repairCommand")).toBe(true)`.
- `packages/shared/src/test/parse-helpers.ts:29-40` — `expectParseFailure` already returns the `ZodError` (`return result.error`), so adding a path/message assertion on the returned value is a zero-cost extension of an existing call, not a rewrite.

## Proposed direction
For the multi-branch cross-field refines that already have a co-located test — `inventory-inputs` (homebrew source coupling), `encounter-inputs` participant union, and the `asiChoice` / `levelUp` refines in `character-inputs` — take the `ZodError` already returned by `expectParseFailure(result)` and add one assertion that at least one issue's `path` matches the refinement's declared path (e.g. `issues.some((i) => i.path.join(".") === "sourceId")`, or `issues[0]?.path` where the fixture isolates a single branch). Assert `message` only where it is stable enough not to churn. Where a fixture currently violates several branches, prefer either narrowing the fixture so it trips exactly the branch under test (cleanest), or asserting `issues.some(...)` for the specific path so the test fails when *that* branch stops firing. Coverage is preserved and strengthened: the bad-input rejection still holds, and the test now also fails if the specific refinement breaks rather than passing on collateral validation from a sibling branch.

Estimated impact: closes a real masking risk on the most breakable multi-branch business rules (dual-mode inventory/source inputs, encounter participant union, ASI/level-up coupling) where a broken branch can currently ship green. No measurable runtime change — these are synchronous `safeParse` assertions; the added `path`/`message` checks add no I/O and no new test cases, so suite time is unaffected. The win is defect-catching, not speed.

## Scope / caveats
Scope strictly to refine-bearing schemas that **already have a co-located test** *and* whose refine is multi-branch / cross-field: `inventory-inputs.test.ts`, `encounter-inputs.test.ts`, and the ASI/level-up cases in `character-inputs.test.ts`. Do **not** add discrimination to single-field value/format refines (e.g. the `VALID_CR_VALUES` `.refine` at `encounter-inputs.ts:117`/`:134`, or monster/map value refines) where there is only one way to fail and masking risk is near-zero. This is **not** a write-a-missing-test task: `monster-inputs.test.ts` and `homebrew-inputs.test.ts` do **not** exist, so their schemas are out of scope for an "extend the existing assertion" commit. `monster.test.ts` now exists (added post-audit by merge `df63efaa`), but `monster.ts` carries only a single-field CR refine (no multi-branch `superRefine`), so it stays out of scope under the single-field carve-out above. Authoring brand-new co-located suites for the missing schemas is a separate decision. Exclude `harness-diagnostics.test.ts` — it already uses the `issues.some((i) => i.path...)` pattern (`:61`). Test-only change: no source edits, no migration, no behavior change, so the `shared → server → client` package flow is not engaged. Match `path` (stable) and pin `message` only where the copy is unlikely to churn, to avoid brittle string coupling. Low risk; mechanical. Adjacent to, but distinct from, broader colocation/discoverability findings (e.g. `34-saving-throw-tests-misplaced`) — this one is about *assertion strength* inside correctly-placed tests, not test placement.
