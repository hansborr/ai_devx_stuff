# 20. beforeAll-seeded DB rows would be silently wiped by the global beforeEach cleanDb() — undocumented sharp edge

Status: Proposed — read-only finding from the test-suite audit; NOT implemented. Re-verify file:line before acting.
Lens: defect-catching · Area: server test-infra (setup.ts + clean-db.ts) · Severity: low · Size: S · Confidence: med
Theme: undocumented destructive-fixture sharp edge · Source: Musi test-suite audit 2026-06-13 (multi-agent, adversarially verified)

## Problem
Every server test inherits a global `beforeEach` that runs `cleanDb()` before the test body, and `cleanDb()` deletes every non-SRD row in the database — homebrew, the full campaign tree (chat, notifications, npcs, notes, invites, members, campaign), the full character tree (level choices, features, feats, weapon masteries, spell slots, conditions, proficiencies, stats, classes, character), plus sessions and users. Only SRD reference data (species, classes, etc.), seeded once by global setup, survives. The convention that keeps this safe is entirely invisible and unenforced: a suite may do *app construction* (`createTestApp()`) and other static handle setup in `beforeAll`, but it must seed every per-test row in `beforeEach`/`it` — never in `beforeAll`. The first `beforeEach` of the suite fires *after* `beforeAll` and wipes anything `beforeAll` planted.

The whole server suite obeys this rule today, so there is no live defect — but the rule lives nowhere. A future author who, reaching for speed, seeds a shared user or character in `beforeAll` and references it across `it()` cases will hit one of two bad outcomes: a confusing "row not found" / foreign-key failure on the first test (the row was deleted by `beforeEach`), or a *false pass* if the test happens to re-create the fixture lazily, masking a setup that never actually exercised the shared seed. The trap is pre-baited: nine suites already carry empty `beforeAll(async () => {})` stubs — authors clearly reach for the `beforeAll` slot and leave it empty, which is exactly where this footgun gets loaded. The hazard sharpens materially if the proposed `cleanDb`-as-`TRUNCATE` speed lever (sibling slug `08-cleandb-23-sequential-deletemany-round-trips`) lands, since a faster, more total wipe makes the silent destruction both cheaper to trigger and harder to reason about.

## Evidence
- `packages/server/src/test/setup.ts:44-47` — global `beforeEach(async () => { await cleanDb(); authRateLimiter.reset(...); })`; this runs before every test in every server suite.
- `packages/server/src/test/clean-db.ts:12-42` — `cleanDb()` deletes all non-SRD tables: homebrew (`:14-16`), the campaign tree (`:19-25`), the character tree (`:28-37`), then `session`/`user` (`:39-40`); the `:41-42` comment confirms only static SRD reference data is intentionally spared.
- `packages/server/src/routers/inventory.test.ts:19-27` — safe pattern: `beforeAll` builds the app (`createTestApp()`), per-test rows are seeded in `beforeEach` via `setupInventoryTestContext(app)`.
- `packages/server/src/services/spell-casting/spell-casting.test.ts:40-48` — same safe split: `createTestApp()` in `beforeAll`, encounter/character rows seeded in `beforeEach` via `setupEncounterTestContext(app)`.
- `packages/server/src/services/starting-equipment-service.test.ts:11` — empty `beforeAll(async () => {})` stub sitting next to a `beforeEach` (`:13-42`) that recreates the user + character every test; the exact empty slot this trap targets.
- Aggregate (re-verified at HEAD): 171 server `*.test.ts` files; 93 use `beforeAll`. Across 119 `beforeAll` bodies the breakdown is 109 `createTestApp()`, 9 empty stubs, and 1 redundant `cleanDb()`-only body (`packages/server/src/utils/session-cleanup.test.ts:11-13`) — and **zero** `beforeAll` bodies seed a non-SRD row. This confirms there is no live defect today, only an unwritten, unenforced convention.

## Proposed direction
Guard/doc finding — no test-behavior change, coverage unchanged. Land in order:

1. Comment the contract where it is violated. Add a short, prominent block comment to `clean-db.ts` and `setup.ts` stating: the global `beforeEach` deletes every non-SRD row (campaigns, characters, sessions, users, homebrew); seed per-test rows in `beforeEach`/`it`, never in `beforeAll` — only static app/handles (`createTestApp()`) belong in `beforeAll`, because the suite's first `beforeEach` wipes anything `beforeAll` seeds.
2. Make the rule discoverable before a failure, not just after. No dedicated server-unit-test guide exists under `docs/guides/` today (only `add-e2e-test.md`, the `lint-ratchet*` guides, `biome-lint-adoption.md`, and `local-eslint-rules.md`), so treat the `clean-db.ts` / `setup.ts` comments from step 1 as the primary home for the contract; optionally seed a new `docs/guides/add-server-test.md` (or similar) and cross-link it, rather than editing a guide that does not yet exist.
3. Optional (tooling, weighted above product code): add a lightweight in-house ESLint rule under `eslint-rules/` (see `docs/guides/local-eslint-rules.md`) that flags Prisma `.create`/`.createMany`/`.upsert` (and fixture-helper) calls against non-SRD models inside a `beforeAll` body in `*.test.ts`. This makes the convention machine-checked. It is best sequenced *with* any `cleanDb`-as-`TRUNCATE` work, since that is when the trap gets sharper.

Estimated impact: prevents a hard-to-diagnose class of silently-wiped-fixture failures (or false passes) across the 93 `beforeAll`-using server suites; the prevention value rises sharply if `cleanDb` becomes a `TRUNCATE`. No runtime speed effect — this is purely defect-prevention and onboarding clarity, not a perf lever.

## Scope / caveats
Docs/comments are zero-risk and touch no test behavior; coverage is unchanged because nothing about what the tests assert or seed moves. This is purely preventive with zero current incidence — hence low severity and med confidence. It is distinct from the sibling slug `08-cleandb-23-sequential-deletemany-round-trips` (that finding is about `cleanDb`'s sequential `deleteMany` round-trip cost, a performance concern; this one is about the `beforeAll`-seeding silent-wipe trap) and from `06-router-tests-double-cleandb-per-test` (redundant double-clean, not the seeding hazard) — though all three live on the same `cleanDb` surface and should be read together if that surface is reworked. The optional lint guard would *not* flag the nine existing empty `beforeAll` stubs or the lone redundant `cleanDb()`-only `beforeAll` in `session-cleanup.test.ts` (none write a model), so it pairs only thematically with any dead-stub cleanup; do not bundle them. Sequence: land the docs/comments first; pursue the lint guard only if/when the `cleanDb`-`TRUNCATE` lever is taken up.
