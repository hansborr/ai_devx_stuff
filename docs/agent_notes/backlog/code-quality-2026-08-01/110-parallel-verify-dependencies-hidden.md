# 110. The generated verify slot data looks like the complete execution contract, but dependency and producer semantics live only in hand-coded Bash

Status: Landed on fix/cq-110
Theme: single-sourced slot scheduling semantics · Area: harness · Severity: high · Size: L

Source: codebase quality audit 2026-08-01 · Confidence: high

## Problem

The verify gate is single-sourced by design: `harness.controls.json` declares
each consumer's slots, `scripts/harness/generate-verify-steps.ts` emits
`scripts/verify/steps.generated.sh`, and that file opens with "Do not edit by
hand" — an affirmative signal that slot registration is complete there. It is
not. The generated file carries commands, per-consumer step lists, the
fast-commit skip set, and dynamic-resolver bindings, but **no dependency,
producer, or output semantics at all**. The one real ordering relationship in
the system — typecheck produces `packages/{shared,server}/dist`, which lint and
ratchet need — exists only as hand-coded Bash in
`scripts/verify/steps-lib.sh`: a hard-coded `lint | ratchet` case, a literal
`typecheck` slot-name match inside a 121-line parallel scheduler, and a
three-way failure taxonomy reconstructed inline. The same relationship is
restated as prose in three manifest `principle` fields, where no tool can read
it.

The cost is a silent registration trap in the single most-copied harness
surface. A contributor who adds a slot whose command needs `dist` follows the
documented path — declare it in the manifest, regenerate, watch
`verify:steps:check` pass — and gets a slot that *looks* fully registered but
races typecheck in parallel runs, because deferral is granted only to the two
slot names the scheduler hard-codes. Nothing fails at generation time; the
failure arrives later as a flaky parallel gate. For a repo whose harness is
meant to be copied, the gap also means an adopter cannot see the dependency
contract by reading the declared data, and the scheduling arm of the runner is
the one part they cannot regenerate.

## Proposed direction

Extend the existing `harness.controls.json` →
`scripts/harness/generate-verify-steps.ts` → `steps.generated.sh` pipeline
with named-artifact slot fields — an artifact-edge extension of what is
already there, not a new artifact. Do **not** build a standalone typed
slot-graph file or a general DAG scheduler: there is exactly one conditional
dependency edge in the system, and `fastCommitSkip` already sets the
declare-in-manifest / generate / consume-generically precedent this follows.

1. **Pin the current dist-deferral behavior first (TDD).**
   `scripts/tests/test-verify.sh:1696-1706` covers the no-producer arm; add
   companion cases for the `NOT_RUN` passthrough arm
   (`steps-lib.sh:403-410` — typecheck admitted-but-never-launched propagates
   exit 300 to the deferred slots) and the producer-failed arm (`:432-439` —
   deferred slots exit 1 with the "skipped … because typecheck failed before
   required dist outputs were available" per-slot log line). Exit codes and
   log messages must be preserved verbatim through every later step. Run the
   suite directly with `bash scripts/tests/test-verify.sh`.
2. **Add named-artifact fields to the slot schema and manifest.** In
   `scripts/harness/verify-step-schema.ts` (extending `VerifyStepSlot`,
   `:30-40`, and `SLOT_KEYS`, `:45-53`) and in the slot entries of
   `harness.controls.json`: typecheck declares `produces: "dist-outputs"`;
   lint and ratchet declare `requiresArtifact: "dist-outputs"` with
   defer-only-when-missing semantics. Model the relationship as named
   artifacts, **not** slot-to-slot edges (no `dependsOn: ["typecheck"]`).
   Bind artifact ids to hand-written probe functions
   (`musi_lint_dist_outputs_present`, `scripts/lib/lint-dist-preflight.sh:36`)
   via a binding table in the schema module mirroring
   `VERIFY_STEP_DYNAMIC_RESOLVER_BINDINGS` (`verify-step-schema.ts:4-13`) —
   not a declarative `probePaths` data format.
3. **Generate the maps; delete the hand-coded scheduling literals.**
   `generate-verify-steps.ts` emits `MUSI_VERIFY_SLOT_PRODUCES`,
   `MUSI_VERIFY_SLOT_REQUIRES_ARTIFACT`, and
   `MUSI_VERIFY_ARTIFACT_PROBE_FUNC` alongside the existing arrays (the
   `MUSI_FAST_COMMIT_SKIP_SLOTS` emission at `generate-verify-steps.ts:300`
   is the template). `steps-lib.sh` consumes them generically, deleting the
   hard-coded `lint | ratchet` case (`musi_defer_dist_slot`, `:205-211`) and
   the literal `typecheck` matches in `musi_run_parallel_verify_steps`
   (`:386`, `:399-440`), with the step-1 tests staying green.
4. **Close the trap with closure validation.** Extend the checks behind
   `bun run verify:steps:check` (and surfaced through `bun run harness:check`)
   so generation fails when a slot names an unknown artifact id, an artifact
   id has no probe binding, a consumer's slot list contains a
   `requiresArtifact` slot with no producing slot in that same list, or more
   than one slot declares `produces` for one artifact. This is the piece that
   converts "looks registered but silently mis-schedules" into a
   generation-time failure.
5. **Degrade cleanly for adopters.** A manifest with no artifact declarations
   must generate empty maps guarded with the `${arr[@]+}` bash-3.2 convention
   (`steps-lib.sh:163` is the in-tree exemplar) so the dependency branch
   vanishes entirely for copiers without a dist step.
6. **Move the prose to policy altitude.** Shrink the dependency sentences in
   the `principle` fields at `harness.controls.json:2078`, `:711`, and `:791`
   to policy statements now that the mechanism is declared data (regenerate
   the agent-facing doc with `bun run docs:harness-controls`), and document
   the produces/requiresArtifact pattern in
   `docs/guides/verify-gate-lifecycle.md`, which already walks
   `steps.generated.sh` at `:72`.

The sequential runner consumes nothing at runtime and `MUSI_VERIFY_STEPS` is
**not** topologically reordered at generation time: lint's own dist preflight
(`scripts/lib/lint-dist-preflight.sh:87`) already makes sequential order
correct, and reordering would change fail-fast/log ordering for no correctness
gain. The manifest declaration simply documents that path too.

## Scope / caveats

- **Binding rulings** (each "do not" below is a hard constraint on this
  leaf, not a preference):
  - No standalone typed slot-graph artifact, no general DAG scheduler — only
    the produces/requiresArtifact extension of the existing pipeline.
  - No slot-to-slot dependency edges; named artifacts with
    defer-only-when-missing semantics and probe functions bound via a
    generated id-to-function map only.
  - The sequential runner must not consume dependency data at runtime, and
    `MUSI_VERIFY_STEPS` must not be reordered; lint's dist preflight stays
    untouched.
  - The dist-deferral failure taxonomy (`steps-lib.sh:396-440`) must not be
    rewritten before step 1's behavior-pinning tests exist; the three exit
    behaviors and per-slot log messages are preserved verbatim.
  - The new fields must not ship without step 4's closure validation, and
    empty adopter declarations must generate empty maps that disable the
    dependency branch entirely.
- **Out of scope — split leaf:** refactoring `musi_drain_memory_pending_slots`'s
  13 positional parameters (`steps-lib.sh:234-243`) into a name-prefix
  nameref record (~4 params). That is Bash hygiene, not graph data; do not
  bundle it here.
- **Out of scope — optional follow-on:** folding `expectedPeakMb`
  (`scripts/verify/memory-budget.sh:53`) into the manifest. The memory
  surface fails soft (default-peak fallback at `memory-budget.sh:117`) and is
  not part of the trap this leaf closes. If pursued later, peaks must be
  declared in a top-level per-slot-name table — never per-consumer slot
  entries, since typecheck appears in all four consumers and would be
  declared four times — and the measurement-provenance comments inside the
  current map must migrate with the values.
- **Do not reopen the refused pre-commit dispatcher split.** The live
  2026-07-25 pack's
  [HARNESS-CLUSTER-PLAN.md](../code-quality-2026-07-25/HARNESS-CLUSTER-PLAN.md)
  (`:402`) ruled out splitting the `.husky/pre-commit` body behind a
  dispatcher; every change here stays in `steps-lib.sh`, the generator, the
  schema module, and the manifest — hook shim bodies are untouched. Prior-pack
  leaf [32-git-hook-shims.md](../code-quality-2026-07-25/32-git-hook-shims.md)
  is the record of what did land on that surface.
- **Coordinate with [125-manifest-copies-verify-slot-programs-across.md](./125-manifest-copies-verify-slot-programs-across.md).**
  It edits the same `harness.controls.json` slot entries and
  `generate-verify-steps.ts` from the duplication angle; the two directions
  are compatible but must not be worked concurrently, and a shared plan
  should decide which lands first.
  [116-generated-surface-dependencies-manually.md](./116-generated-surface-dependencies-manually.md)
  also edits the manifest (generated-surface facets) — different problem,
  same file; avoid concurrent edits.
- Prior art, not coverage: the 2026-07-25 pack's bash-facade-over-TS-core
  precedent (its leaf 29) supports putting new validation logic in
  TypeScript with thin Bash consumption, which is exactly what steps 2-4 do;
  this pack's
  [117-verify-metadatash-second-kitchen-sink-shell.md](./117-verify-metadatash-second-kitchen-sink-shell.md)
  continues that line on a sibling shell surface.
- After manifest or generator edits, the check-mode loop is
  `bun run verify:steps` to regenerate, `bun run verify:steps:check` and
  `bun run harness:check` to validate. `steps-lib.sh:46-48` prints the
  regeneration and `verify:steps:check` commands; `harness:check` is the
  additional closing gate.
