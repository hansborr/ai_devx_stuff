# 20. pages/ has no orientation doc for the page-as-composition-root pattern, despite 28 MODULE.md docs deeper in the tree

Status: Proposed — codebase maintainability/onboarding audit 2026-06-13. Not yet started.
Theme: discoverability / onboarding orientation · Area: client · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: client-architecture); evidence independently re-verified. · Confidence: high

## Problem
`packages/client/src/pages/` holds the top-level composition roots — the place where each route stitches together tRPC queries, presence/socket hooks, sheet state, dialog state, and feature panels — yet it has **zero** orientation doc, while 28 `MODULE.md` files exist deeper in `client/src` (and 34 repo-wide). A new developer asked to "add a tab to the campaign page" or "wire a new dialog into the character sheet" lands in `pages/` first, finds no map, and must reverse-engineer a non-obvious multi-hook composition order by reading the code. The character-sheet flow in particular is split across four files (`sheet-layout.tsx`, `sheet-state.ts`, `sheet-dialogs.tsx`, `sheet-sections.tsx`) and threads `useSheetState -> useDmStatsCallbacks -> useSheetDialogState` in a specific order, and the one MODULE.md that would seem relevant — `hooks/character-sheet/MODULE.md` — **explicitly disclaims** rendering the UI, so the composition layer is documented nowhere.

## Evidence
- `packages/client/src/pages/` — `find packages/client/src/pages -name "*.md"` returns **0 files**; no `MODULE.md`, no README. By contrast `find packages/client/src -name MODULE.md | wc -l` = **28** (34 repo-wide), all sitting under `hooks/`, `components/`, etc. — i.e. orientation docs stop one level above the composition roots.
- `packages/client/src/pages/character-sheet/sheet-layout.tsx:108-130` — the non-obvious composition order: `sheetCampaignId` fallback (108) -> `useCampaignPresence` / `useCharacterSheetSocket` (109-110) -> `useCampaignContext` / `useRollPermission` (112-113) -> `useSheetState` (114) -> `useDmStatsCallbacks` fed from `s.updateStats`/`s.updateStatsAsync`/`s.adjustHpAsync` (115-120) -> `useSheetDialogState` (121). The `s.` (sheet state) and `d.` (dialog state) split is a convention with no written rationale.
- `packages/client/src/pages/character-sheet/` — the sheet "page" is actually 4 files: `sheet-layout.tsx`, `sheet-state.ts`, `sheet-dialogs.tsx`, `sheet-sections.tsx` (plus `sheet-state.test.ts`); `pages/character-sheet-page.tsx` is a thin wrapper that only does the `character.get` query and delegates to `CharacterSheetContent`. Where state-vs-dialogs-vs-sections belongs is non-obvious from filenames alone.
- `packages/client/src/hooks/character-sheet/MODULE.md:11-12` — "This module does not render the sheet UI; `pages/character-sheet-page.tsx` and sheet components consume these hooks." So the nearest MODULE.md deliberately hands off to `pages/`, which then has no doc of its own — the handoff dead-ends.
- `packages/client/src/pages/campaign-detail-page.tsx:154-188` — wires **8** tab panels (overview, members, chat, notes, npcs, encounters, maps, DM-only settings) inside `CampaignTabs`, threading derived `userCharacterIds` (computed 135-144) and `isDm` (derived 204) into `EncountersPanel`/`MapsPanel`. The "where do I register a new campaign tab" answer spans this file plus `lib/campaign-tabs.ts` (`CampaignTab`, `isCampaignTab`, `DEFAULT_CAMPAIGN_TAB`) and is undocumented.

## Proposed direction
Add a single `packages/client/src/pages/MODULE.md` (the established orientation-doc format, matching the 28 existing ones) describing the page-as-composition-root pattern. It should answer the recurring "where does X go" questions: (1) the page/route -> thin wrapper (`*-page.tsx` does the entry query + loading/error) -> composition root (`CharacterSheetContent`, `CampaignTabs`) layering; (2) the character-sheet four-file split (`sheet-state.ts` = data/mutation hooks via `useSheetState`, `sheet-dialogs.tsx` = dialog slots, `sheet-sections.tsx` = static sub-blocks, `sheet-layout.tsx` = the wiring), and the `s.`/`d.` state-vs-dialog convention plus the hook-call order; (3) how to add a campaign tab (the `campaign-detail-page.tsx` + `lib/campaign-tabs.ts` pair). Cross-link from `hooks/character-sheet/MODULE.md:11-12` so the existing handoff resolves to a real doc. This is documentation-only and client-local; it does not touch the package-flow order (no shared/server change). TDD-wise this is prose, so there is no unit test to add — but if a `MODULE.md` freshness/index check exists (e.g. `MODULE-INDEX.md` listing), update that index in the same change and re-run the doc gate that validates it. Confirm no `MODULE.md` lint/coverage gate treats a new doc as an unaccounted surface before committing.

## Scope / caveats
Documentation-only; do **not** refactor the pages or rename the `sheet-*` files — the finding is that the composition pattern is undocumented, not that it is wrong. This is **not** a duplication or dead-code finding (those are owned by `drift-ai-findings/`): every file cited is live and reachable, and nothing here proposes deleting or merging code. It is distinct from `storybook-component-catalog.md` (that catalogs `components/ui/` primitives; this documents page-level composition, a different layer) and from the `agent-friction-2026-06/` harness work (this is human-onboarding orientation, not agent-test ergonomics or lint-rule tooling). It is also not a UX/product audit item. Keep the doc to orientation only — do not duplicate the per-hook detail already in `hooks/character-sheet/MODULE.md`; link to it instead. Low risk: a single new Markdown file with no behavior change. If `MODULE-INDEX.md` enumerates docs, add the new entry there to avoid drift between the index and the tree.
