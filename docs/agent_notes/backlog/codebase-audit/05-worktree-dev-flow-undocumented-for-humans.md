# 5. Per-worktree dev flow (worktree:* scripts, MUSI_DEV_DRIFT_GATE) auto-runs on `bun run dev` in secondary worktrees but has no human-facing doc

Status: Done — the human-facing per-worktree dev doc landed at `docs/guides/per-worktree-dev.md` (referenced from AGENTS.md). Problem statement below is retained as the original finding.
Created: 2026-06-13 · Updated: 2026-07-15
Theme: onboarding discoverability · Area: docs · Severity: medium · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: onboarding-setup); evidence independently re-verified. · Confidence: high

## Problem
`bun run dev` runs `scripts/dev.sh`, which on *any* secondary git worktree silently auto-runs `worktree:init` to provision per-worktree databases, ports, Redis index, and `.env` files, then gates the dev startup on residual schema/seed drift via the undocumented `MUSI_DEV_DRIFT_GATE` knob. A new developer who creates a git worktree — a common multi-branch workflow — hits surprising DB-clone and port-reassignment behavior plus `[dev] WARN: residual worktree drift remains...` output with no mental model for what any of it means or how to respond. The only prose explaining this machinery lives in shell-script headers and the agent-facing harness table; README.md and AGENTS.md never mention the word "worktree" and there is no `docs/guides/` entry, so the first-run experience is "the dev server did several alarming database things I did not ask for." That is a direct, repeatable time-to-understanding tax on onboarding and a discoverability gap ("where is the per-worktree dev model documented?") with no answer in human-facing docs.

## Evidence
- `scripts/dev.sh:245-248` — `main()` calls `musi_dev_run_worktree_init` whenever `! is_primary_worktree`, so the provisioning + drift gate fire automatically on the first `bun run dev` in any linked worktree, before the workspaces even start.
- `scripts/dev.sh:146-160` — `musi_dev_run_worktree_init` shells out to `bun run worktree:init` (its own log line warns "dependencies, template build, or DB clone may take a moment") and, on success, calls `musi_dev_warn_or_fail_on_residual_drift`.
- `scripts/dev.sh:54-64` — `musi_dev_drift_gate_mode` reads `MUSI_DEV_DRIFT_GATE` (values `warn` (default), `fail`, `off`); `scripts/dev.sh:100-144` — the gate that compares clone vs. current schema/migration/SRD-seed fingerprints and emits the multi-line `residual worktree drift` warning, including the only place the `MUSI_DEV_DRIFT_GATE=off|fail` escape hatches are described.
- `package.json:19-25` — seven `worktree:*` scripts (`init`, `new`, `drop`, `gc`, `status`, `template-refresh`, `refresh-data`); none is referenced from a human onboarding doc.
- `scripts/worktree-db.sh:1-62` — the authoritative per-worktree DB/port/env provisioner; its full subcommand semantics (DB names it may create, files it writes to the current vs. primary worktree) exist only in this shell header.
- `is_primary_worktree` at `scripts/worktree-db.sh:136-141` — the detection that decides "secondary worktree" (git-common-dir vs. git-dir), the implicit trigger for all of the above.
- README.md and AGENTS.md: `rg -ni worktree` returns no matches (exit 1) in either — zero mentions. `docs/guides/` has no `*worktree*` file (the guides that contain the word use it incidentally, e.g. `docs/guides/add-prisma-migration.md` and `docs/guides/lint-ratchet-merges.md`). `MUSI_DEV_DRIFT_GATE` appears only in `scripts/dev.sh` and `scripts/tests/test-worktree-db.sh` — documented in no prose.
- `docs/ai-harness.md`'s **Sensors** rows for `doctor` and **Worktree drift/status checks** — the per-worktree drift checks are surfaced only in the *agent harness* table (pointing at "`bun run worktree:*` scripts"), not a human-facing onboarding guide; it assumes the reader already knows the worktree model.

## Proposed direction
Documentation-shaped, not a behavior change — do **not** alter `dev.sh` startup semantics. Add a single human-facing guide, e.g. `docs/guides/per-worktree-dev.md`, registered in `docs/guides/` alongside the existing task guides, covering: (1) what happens on the first `bun run dev` in a linked worktree (auto `worktree:init`, per-worktree DBs/ports/Redis/.env), (2) a one-line-each reference for the seven `worktree:*` scripts mirroring the authoritative comments in `scripts/worktree-db.sh:1-62`, (3) the `MUSI_DEV_DRIFT_GATE` `warn|fail|off` knob and when to use each, and (4) the recovery path (`worktree:status` → `worktree:refresh-data [--destructive]`). Then add a short pointer from README.md and from AGENTS.md's "Commands" section so the guide is discoverable from the two docs a newcomer actually opens. Be TDD-aware: the repo gates docs against the module index via `bun run module:index:check` — if the new guide needs an index/MODULE entry, follow `docs/guides/add-module-doc.md` and run that check; otherwise prefer reusing the `scripts/worktree-db.sh` header as the single source so the prose cannot drift from the script. No package-flow ordering concern (shared->server->client) since this is docs-only. Keep the guide's drift-knob description sourced from `scripts/dev.sh:54-64` so it stays accurate if the gate modes change.

## Scope / caveats
Docs-only: do not touch `scripts/dev.sh`, `scripts/worktree-db.sh`, or `package.json` script wiring — the goal is to *explain* the existing flow, not change it. This is explicitly NOT a duplication or dead-code finding (those are owned by `docs/agent_notes/backlog/drift-ai-findings/`): nothing here is redundant or unused — the worktree machinery is live and load-bearing; the gap is purely missing human-facing documentation. It is also distinct from the agent-harness ergonomics work in `agent-friction-2026-06/` (this targets a *human* onboarding a worktree for the first time, not AI-agent harness tooling) and from the existing `docs/ai-harness.md` table (agent-facing, assumes prior worktree knowledge). Caveat: keep the new guide thin and link back to `scripts/worktree-db.sh:1-62` as the authoritative reference rather than re-deriving every subcommand flag, to avoid creating a second source that can rot.
