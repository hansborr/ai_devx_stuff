# 32. Client error contract exposes an unreachable PRECONDITION_FAILED recovery path the server never emits

Status: Done 2026-06-14 — removed `onPreconditionFailed` + the `PRECONDITION_FAILED` branch from `trpc-error.ts`, dropped the phantom code from `toast-messages.ts` and both test files (strengthening the `CONFLICT` cases instead), and corrected the `ux_ui_audit` `VERIFICATION.md`/`SUMMARY.md` premise to branch on the codes the server actually emits (`FORBIDDEN`, `CONFLICT`, `BAD_REQUEST`).
Theme: dead error-code branch / misleading contract · Area: client · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: error-observability); evidence independently re-verified. · Confidence: high

## Decision (locked 2026-06-13)
**Remove `onPreconditionFailed` and the `PRECONDITION_FAILED` branch (the leaf's preferred option).** The server emits only `CONFLICT` (`docs/CONCURRENCY.md`); a forward-compat phantom code is not worth the new-developer ambiguity and can be re-added with intent when a real producer exists.

**Cross-audit reconciliation (required, not optional):** the `ux_ui_audit` items (`VERIFICATION.md:92`, `SUMMARY.md:101`) ask to branch on `PRECONDITION_FAILED` on the false premise that the server emits it. Do NOT preserve the phantom client branch to satisfy them. Instead, the implementing agent must **patch those two `ux_ui_audit` files to branch on the codes the server actually emits (`FORBIDDEN`, `CONFLICT`, `BAD_REQUEST`)**, so the phantom premise is corrected at the source rather than re-implemented later.

## Problem
The shared `onTRPCError` factory advertises two interchangeable-looking optimistic-lock recovery codes — `CONFLICT` and `PRECONDITION_FAILED` — but the server only ever throws `CONFLICT`. The `onPreconditionFailed` hook and its `PRECONDITION_FAILED` branch (`trpc-error.ts:18,33`) are structurally identical to the `CONFLICT` pair, no client consumer wires `onPreconditionFailed`, and `docs/CONCURRENCY.md` codifies `CONFLICT` as the single race-rejection code. A new developer wiring error recovery for a race-sensitive mutation reads `toast-messages.ts:9-11` ("`CONFLICT` / `PRECONDITION_FAILED` are handled per-consumer"), sees two equally-documented hooks with the same recovery shape, and has no way to tell which to choose — and choosing `onPreconditionFailed` produces a silently dead path, because the server will never deliver that code. This is exactly the "where does X go / which one do I use" surprise the onboarding lens targets: a phantom second code that costs reading-time and invites a no-op wiring.

## Evidence
- `packages/client/src/lib/trpc-error.ts:18` — `OnTRPCErrorOptions` declares `onPreconditionFailed?: RecoveryHook`, a sibling to `onConflict` with identical type.
- `packages/client/src/lib/trpc-error.ts:33-36` — the `code === "PRECONDITION_FAILED"` branch is byte-for-byte the same shape as the `CONFLICT` branch at 29-32 (both call `runHook` and return); the two codes carry the same recovery semantics with nothing distinguishing them.
- `packages/client/src/lib/toast-messages.ts:9-11` — comment states "`CONFLICT` / `PRECONDITION_FAILED` are handled per-consumer via the factory's `onConflict` / `onPreconditionFailed` hooks", implying both are live server codes.
- Server never emits `PRECONDITION_FAILED`: `rg "PRECONDITION_FAILED"` over the repo (excluding `packages/server/src/generated/**`) finds it only in the client lib (`trpc-error.ts`, `toast-messages.ts`) + their tests, and in a separate `ux_ui_audit` doc — never in any `packages/server/src` throw site.
- By contrast `CONFLICT` is the live race code: `code: "CONFLICT"` is thrown at 28 non-test sites across 15 server files, and `CONFLICT` is referenced in 19 non-test server files total (`packages/server/src/utils/{character-class,character-stats,encounter-state,participant-stats,spell-slot}-mutations.ts`, `services/rest-service.ts`, `services/combat-actions/turn-transaction.ts`, `routers/{homebrew,invite,homebrew-campaign,campaign}.ts`, etc.).
- Zero consumers wire `onPreconditionFailed`: `rg "onPreconditionFailed"` outside the lib + its test finds only the `toast-messages.ts:10` comment. By contrast `onConflict` has real consumers — `hooks/vtt-drawer/{use-feature-use,use-monster-hp-update,use-drop-concentration,use-confirm-cast}.ts`, `components/vtt/drawer/cast-rail.tsx`, `cast-rail-concentration.tsx`.
- `docs/CONCURRENCY.md:65,117,139-142` — codifies `CONFLICT` as the single optimistic-lock / state-machine rejection code (`updateParticipantStatsLocked` → `CONFLICT`; `advanceTurnCompound` picks `BAD_REQUEST` vs `CONFLICT`; `setEncounterState` invalid transition → `CONFLICT`); `PRECONDITION_FAILED` is never mentioned.
- `packages/client/src/lib/toast-messages.test.ts:43-46` and `trpc-error.test.ts:45-52` — the only places exercising `PRECONDITION_FAILED`; the factory test asserts the dead branch in isolation, masking that nothing reaches it in practice.

## Proposed direction
Collapse the contract onto the one code the server actually emits, so the factory has a single, obvious "this mutation lost a race → reload" hook. Fix shape (client-only; no shared/server change since `CONFLICT` is already the canonical server code per `docs/CONCURRENCY.md`):
- Remove `onPreconditionFailed` from `OnTRPCErrorOptions` and delete the `PRECONDITION_FAILED` branch in `onTRPCError` (`trpc-error.ts:18,33-36`), leaving `onConflict` as the single optimistic-lock recovery hook.
- Update the `toast-messages.ts:9-11` comment to name only `CONFLICT` as the per-consumer race code, removing the misleading "/ `PRECONDITION_FAILED`".
- TDD: drop the now-obsolete `trpc-error.test.ts:45-57` "runs the onPreconditionFailed hook" case and the `toast-messages.test.ts:46` assertion; keep/strengthen the `CONFLICT` cases (`trpc-error.test.ts:40`, the "falls through to catalog default when CONFLICT arrives without onConflict" case at :59) so the surviving single-code path stays pinned. Run `bun run test -- packages/client/src/lib/trpc-error.test.ts packages/client/src/lib/toast-messages.test.ts`.
- Alternative (if the team wants a forward-compatible second code, e.g. for a future HTTP-precondition surface): keep `PRECONDITION_FAILED` but document at `trpc-error.ts:18` *when* the server would emit it and add a one-line note in `docs/CONCURRENCY.md` distinguishing it from `CONFLICT`. Removal is preferred — it is the cheaper way to remove the new-developer ambiguity, and a code can be re-added with intent when a real producer exists.
- Relevant guide: `docs/guides/add-trpc-procedure.md` (error-code conventions) and `docs/CONCURRENCY.md` (the canonical `CONFLICT`-only contract). Package-flow note: this is client-internal error-presentation plumbing — no `shared` schema or `server` router touches the change.

## Scope / caveats
This is a misleading/unreachable *contract surface* finding (a phantom error code in the client recovery factory), not a duplication or dead-code finding — `onPreconditionFailed` is not unused-symbol cruft to be auto-pruned; it is an advertised public option on `OnTRPCErrorOptions` that actively misleads a reader about which code to handle, and the fix is a contract simplification, not a dead-symbol sweep. It is therefore distinct from the drift-ai-findings work (near-duplicate / dead-code), and distinct from the `ux_ui_audit` items at `VERIFICATION.md:92` / `SUMMARY.md:101`, which ask the *opposite* — to branch on `error.data.code` (incl. `PRECONDITION_FAILED`) for combat-dialog UX — and assume the server emits both codes; that audit's premise is the bug this leaf documents, so reconcile with it (the server does not emit `PRECONDITION_FAILED`) rather than implementing both independently. Do not touch the server `CONFLICT` throw sites or `docs/CONCURRENCY.md`'s `CONFLICT` semantics — those are correct and load-bearing. Risk is low: the branch is unreachable in production, so removing it changes no live behavior; the only churn is two tests and a comment. If keeping the code for forward-compat is chosen instead, do not silently leave it undocumented — the documentation gap is the actual cost.
