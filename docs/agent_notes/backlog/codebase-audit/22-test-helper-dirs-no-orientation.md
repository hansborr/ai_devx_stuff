# 22. No index/README for server and client test/ helper directories, leaving overlapping encounter fixture builders undiscoverable

Status: Proposed — codebase maintainability/onboarding audit 2026-06-13. Not yet started.
Theme: test-helper discoverability · Area: server · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: testing-ergonomics); evidence independently re-verified. · Confidence: high

## Problem
`packages/server/src/test/` holds 27 helper modules and `packages/client/src/test/` holds 25, but neither directory has a `MODULE.md`, README, or barrel that tells a newcomer which helper to reach for. Several entry points overlap by name with no stated guidance: `createEncounter` and `createEncounterWithMonsters` both build a *setup-state* encounter (one bare, one with N monsters), and `createActiveEncounter` / `buildActiveBattle` / `buildActiveBattleWithLog` all build "an active encounter" with deliberately different participant shapes and return types. These are intentionally distinct fixtures — so this is a discoverability/onboarding gap, not a dedup item — but the only way to tell them apart today is to open each file and read the docstring. A new developer writing their first encounter test picks a builder by guessing from its name, then either reinvents a fixture or wires up the wrong one and debugs a confusing failure; multiply that by ~52 undocumented helpers across two packages.

## Evidence
- `packages/server/src/test/` contains 27 helper modules (31 entries minus the 4 colocated `*.test.ts`: `campaign-test-context.test.ts`, `enum-sync.test.ts`, `race-helpers.test.ts`, `test-database-url.test.ts`); `find packages/server/src/test -name '*.md'` returns nothing.
- `packages/client/src/test/` contains 25 helper modules (26 entries minus `fixtures-builders.test.ts`); `find packages/client/src/test -name '*.md'` returns nothing.
- `packages/server/src/test/encounter-test-helper.ts:61,101,141,195` — four builders with overlapping names and distinct shapes: `createEncounter` (61, inactive encounter via `encounter.create`), `createActiveEncounter` (101, single Goblin, rolls initiative, transitions to active), `buildActiveBattle` (141, two Goblins with fixed initiatives 18/10 for stable turn order), `buildActiveBattleWithLog` (195, single Orc, returns `{ encounterId, participantId }` instead of `EncounterDetail`). Each carries a docstring; none states "use this when…".
- `packages/server/src/test/encounter-combat-test-helper.ts:13` — `createEncounterWithMonsters` lives in a *separate* file and reuses `createEncounter`/`addParticipant` to build a setup-state encounter with `count` monsters; its name collides conceptually with `encounter-test-helper.ts`'s builders, and the split between the two files is undocumented.
- Importer skew confirms the discoverability cost: `encounter-test-helper.ts` has 23 importers vs `encounter-combat-test-helper.ts`'s 5 (`rg -l` across `packages/`), yet nothing tells a newcomer that combat-specific setup lives in the smaller, easily-missed second file.
- `MODULE-INDEX.md` (generated by `bun run module:index` from `*MODULE.md` files) has zero rows under either `src/test/` directory; `docs/module-docs.md` is the module-doc contract, and `docs/guides/` has only `add-e2e-test.md` — no guide points at the unit/integration fixture builders.

## Proposed direction
Add a `MODULE.md` to each of `packages/server/src/test/` and `packages/client/src/test/` following the `docs/module-docs.md` charter (these are exactly the "shared helper folders that hide non-obvious data flow / cross-module contracts" the charter calls out). Each should: (1) one-line what each helper file owns; (2) carry a "use when" table for the overlapping encounter builders — `createEncounter` (inactive), `createEncounterWithMonsters` (setup + N monsters), `createActiveEncounter` (single-monster active), `buildActiveBattle` (two-monster stable turn order), `buildActiveBattleWithLog` (single Orc, returns ids) — naming each builder's shape and return type; (3) note the `encounter-test-helper` vs `encounter-combat-test-helper` split rule. Prefer `MODULE.md` over a plain README so `bun run module:index` auto-lists it in `MODULE-INDEX.md`, making the helpers discoverable from the index a newcomer already consults. TDD-aware: this is documentation, so the regression guard is the index generator — after adding the docs, run `bun run module:index` and confirm `MODULE-INDEX.md` gains the two rows (the existing module-docs freshness/index check is the test that pins it); no product or helper code changes. Package-flow note: shared→server→client ordering does not apply (these are sibling test dirs); the server doc is the higher-value one (23 importers on the busiest helper) and can land first.

## Scope / caveats
Documentation-only: do NOT merge, rename, or delete any helper, and do NOT consolidate the four builders — they are intentionally distinct fixtures, so this is explicitly NOT a duplication/dead-code finding (that class is owned by `docs/agent_notes/backlog/drift-ai-findings/`). This is also distinct from `agent-friction-2026-06/` (that pack covers AI-agent harness ergonomics — coverage-map/test ergonomics for agents — whereas this is a human-onboarding orientation doc) and from the planned `storybook-component-catalog.md` (UI primitives, not test helpers). Keep the docs short and behavioural ("use when / returns") rather than re-listing every symbol, per the module-docs charter's "breadcrumbs, not an inventory" guidance; the only sequencing risk is letting the doc drift from the helpers, which is precisely why the `MODULE.md` form (covered by the index freshness gate) is preferred over an unchecked README.
