## Problem
A new server developer wiring a tRPC procedure to its service has to answer two questions with no canonical answer: *how do I call this service* and *who owns auth and the Socket.io broadcast — me (the router) or the service?* Both answers vary per procedure with no stated rule. Request-facing services are called four different ways (`(ctx, input)`, `(prisma, input)`, `(prisma, id)`, and a single `opts` bag), and the auth/broadcast ownership flips between adjacent procedures in the *same* `character.ts` router. The confusion is amplified because the request-facing wrappers and the deeper combat/rest layer reuse the **same function names** (`advanceTurn`, `castCombatSpell`, `executeLongRest`) with different signatures and different ownership, so jumping to a definition lands you in one of two layers with no signal which. `services/README.md` is a careful structural taxonomy (deep module vs flat service vs util) but says nothing about the calling convention or who owns auth/broadcast — exactly the two things a maintainer must get right to add a procedure safely.

## Evidence
- `packages/server/src/services/encounter-combat/attack-action.ts:14-43` — `attemptAttack(ctx, input)`: the request-facing service **owns** auth (`assertEncounterCombatant`, :18) and broadcast (`fanOutBroadcasts`, :40).
- `packages/server/src/services/level-up/level-up.ts:29-32` — `performLevelUp(prisma, input)`: opposite convention; its own doc comment (:26-27) states "*Caller: router owns `assertCharacterOwner` and the `character:updated` broadcast. The module does NOT emit Socket.io events.*"
- `packages/server/src/services/character-delete.ts:24-27` — `deleteCharacterWithCascade(prisma, characterId)`: a third shape, `(prisma, id)`; the router owns auth (`assertCharacterOwner` at `character.ts:118`).
- `packages/server/src/routers/character.ts:138-146` — `updateStats`/`adjustHp` delegate straight to auth-and-broadcast-owning services (`updateLiveStats(ctx, input)`).
- `packages/server/src/routers/character.ts:123-136` and `:158-168` — in the **same router**, `updatePersonality` and `levelUp` do `assertCharacterOwner` + `emitCharacterUpdate` **inline**. Opposite ownership conventions sit a few procedures apart, with no marker explaining which procedures own auth/broadcast and which delegate.
- `packages/server/src/services/spell-casting/spell-casting.ts:65` `castCombatSpell(opts)` and `packages/server/src/services/combat-actions/combat-actions.ts:140` `advanceTurn(opts)` (and `:97` `executeAttack(opts)`) — the deeper layer takes a single options bag; its doc comments read "*Caller: auth + broadcast. Module: everything else.*" (combat-actions.ts:95, :138).
- `packages/server/src/services/encounter-combat/spell-action.ts:14` and `turn-action.ts:11` — request-facing wrappers `castCombatSpell(ctx, input)` and `advanceTurn(ctx, input)` exist with the **same names** as the deeper `(opts)` functions they wrap (imported aliased as `executeSpellCast`/`executeAdvanceTurn` at spell-action.ts:10 / turn-action.ts:7). "Go to definition" on `advanceTurn` is ambiguous between two layers.
- `packages/server/src/services/character-live-state/rest.ts:50` (`longRest(ctx, input)`) calls `executeLongRest(ctx, character, input)` in `packages/server/src/services/rest-service.ts:430` — now `ctx`-first, matching `executeShortRest` and the combat convention. This was previously a **fourth** positional shape, `(character, input, ctx)`, with `ctx` last instead of first; the step-3 reorder (drain leaf 5.2) aligned it, removing the foot-gun. The `getCharacterForRest`-then-`execute*` two-layer split still mirrors combat.
- `packages/server/src/services/README.md:1-95` — documents the structural taxonomy (when a concern earns a folder + `MODULE.md` vs a flat service vs a `util`) and a "before adding a new service" rubric, but never states the calling convention or the auth/broadcast ownership rule.

## Proposed direction
This is a documentation-plus-light-convergence fix, not a rewrite; do not re-plumb working services. Shape:

1. **Write the contract down where it is looked for.** Add an "Calling convention & ownership" section to `packages/server/src/services/README.md` stating the intended rule, e.g.: *request-facing services (those a tRPC procedure calls directly) take `(ctx, input)` and own their auth assertion and broadcast; deeper composition helpers take an `opts` bag or `(prisma, …)` and the **caller** owns auth/broadcast.* Make the two-layer pattern (request-facing wrapper in `encounter-combat/` / `character-live-state/` → deeper `combat-actions/` / `spell-casting/` / `rest-service.ts`) explicit, since it is the source of the same-name ambiguity. Cross-link `docs/authorization.md` (auth-helper choice) and `docs/socket-architecture.md` (broadcast-after-persistence).
2. **Reduce the same-name ambiguity** by either documenting the alias pairs in `encounter-combat/MODULE.md` (it already lists `advanceTurn`/`castCombatSpell` at :27-49 without flagging the two-layer collision) or renaming the deeper functions to a verb that signals depth (e.g. `runAdvanceTurnCore`), so "go to definition" is unambiguous. Prefer the doc note first; a rename touches imports across `encounter-combat/` and the combat tests.
3. **Converge the lowest-friction outlier** toward the documented convention — chiefly `executeLongRest`, which put `ctx` last. Landed (drain leaf 5.2): both rest cores now take `(ctx, character, input)`, matching `executeShortRest`/the combat `opts` shape and removing the only `ctx`-last foot-gun.
4. **TDD:** these are signature/ownership-doc changes, so the guard is mostly type-level + existing behavior tests. If step 2 renames, the encounter/combat service tests (e.g. `combat-actions` and `encounter-combat` suites) re-run unchanged and pin behavior; run `bun run test -- packages/server/src/services/encounter-combat` and the rest/level-up suites. If step 3 reorders `executeLongRest`, the rest-service test must be updated and re-run via `bun run test -- packages/server/src/services/rest-service.test.ts` (confirm exact path before editing). Add no new product behavior. Package-flow order is server-only; no shared/client changes.
5. Before touching combat or character-live-state services, read the nearest `MODULE.md` (`encounter-combat/MODULE.md`, `character-live-state/*-MODULE.md`, `rest-MODULE.md`) per the repo rule, and `docs/CONCURRENCY.md` if any mutation helper surface is widened (it should not be — this is convention/docs only).

## Scope / caveats
- **In scope:** the *contract* (a written convention) and at most the smallest signature convergence; the value is onboarding/maintainability — telling a new dev unambiguously how to call a service and who owns auth/broadcast.
- **Explicitly NOT a duplication or dead-code finding.** The same-named `advanceTurn`/`castCombatSpell` pairs are intentional two-layer wrappers with different responsibilities (request-facing auth/broadcast vs pure orchestration), not copy-paste; nothing here is unused. Those categories are owned by `docs/agent_notes/backlog/drift-ai-findings/` and are not what this leaf reports.
- Distinct from existing backlog items: this is not an agent-harness ergonomics item (`agent-friction-2026-06/`), not a lint-debt/ratchet drain, not a UX/infra audit, and not a dep bump. It is a server-layering convention gap.
- **Do not** mechanically rewrite every service to one signature in one pass — `(prisma, …)` shapes (`performLevelUp`, `deleteCharacterWithCascade`) deliberately keep the router owning auth and let the service run inside a caller-controlled transaction; forcing `(ctx, input)` on them could move a `$transaction` boundary. Document the two legitimate shapes (request-facing `(ctx, input)` self-owning; deeper caller-owned) rather than collapsing to one.
- Sequencing: ship the README/MODULE doc note first (zero behavior risk); treat any rename or `executeLongRest` reorder as a separate, test-backed follow-up.
