# 18. packages/server/src/routers/ has no orientation doc despite 29 router files including the largest non-generated server files

Status: Done — added `packages/server/src/routers/routers-MODULE.md` (flat-companion orientation doc): domain-grouped one-line-per-router inventory keyed by `app-router.ts` mount key, partition rules (spell-family split, encounter vs combat vs map boundary, content authorship/typing split), and a "routers stay thin; logic in services/" pointer. Cross-linked from `services/README.md` and `docs/guides/add-trpc-procedure.md`; ran `bun run module:index` so `MODULE-INDEX.md` now lists it. Docs-only; no router/wiring changes (current count is 27 mounted routers + `app-router.ts` aggregator, with `homebrew-campaign.ts` folded into `homebrew`). Theme: router-surface discoverability · Area: server · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: docs-coverage); evidence independently re-verified. · Confidence: high

## Problem
`packages/server/src/routers/` holds 29 non-test router files — including the four largest non-generated server source files (srd.ts 552, homebrew.ts 536, encounter.ts 513, auth.ts 348) — and `app-router.ts` wires 27 sub-routers into one tree, yet the directory carries no README/MODULE.md and no "how the router surface is partitioned / where does procedure X live" map. A newcomer landing here cannot tell why there are separate `srd` / `homebrew` / `monster` / `magicItem` routers (all touch game content), nor why spellcasting fans out across four files (`castSpell`, `characterSpell`, `spellSlot`, `sorceryPoint`), nor where the line falls between `encounter`, `encounterCombat`, and `encounterMap`. The sibling `services/` layer documents exactly this kind of split, so the gap is conspicuous: the question "which router owns this procedure?" has no written answer and must be reverse-engineered by opening files.

## Evidence
- `packages/server/src/routers/` — 29 non-test `.ts` files; a `find ... -iname "*.md"` over the directory returns nothing (no README/MODULE.md). Verified.
- `packages/server/src/routers/srd.ts` (552 lines), `homebrew.ts` (536), `encounter.ts` (513), `auth.ts` (348) — the four largest non-generated files under `packages/server/src/` all live in this undocumented directory (`wc -l`, verified).
- `packages/server/src/routers/app-router.ts:30-57` — `appRouter = router({ ... })` registers 27 sub-routers (`health` through `sorceryPoint`), the single fan-in point a newcomer must hold in their head with no accompanying map.
- `packages/server/src/routers/` content-family split is real and unexplained: `srd.ts` → `srdRouter`, `homebrew.ts` → `homebrewRouter`, `monster.ts` → `monsterRouter`, `magic-item.ts` → `magicItemRouter`; spell-family split: `cast-spell.ts` → `castSpellRouter`, `character-spell.ts` → `characterSpellRouter`, `spell-slot.ts` → `spellSlotRouter`, `sorcery-point.ts` → `sorceryPointRouter`; encounter-family split: `encounter.ts`, `encounter-combat.ts`, `encounter-map.ts` (export names confirmed). Nothing states the boundary rule.
- `packages/server/src/services/README.md` (94 lines) — the sibling layer has a full taxonomy ("Deep module" / "Flat service" / "utils", a promotion rubric, and an Inventory section). There is no router equivalent.
- `docs/guides/add-trpc-procedure.md` (66 lines) — covers authoring *mechanics* only (where the shared contract goes, base-procedure choice, `.input`/`.output`, the `local/trpc-*` lint rules and codemods). It never tells a reader how the existing router surface is partitioned or which router a new procedure belongs in.
- `MODULE-INDEX.md:8-45` — the generated index of every `*MODULE.md` lists client components, client hooks, server `services/`, and server `socket/`, but has zero entries under `packages/server/src/routers/`. A grep for `routers/` across `packages/server/src/**/*.md` hits only `socket/MODULE.md` and `services/spell-casting/MODULE.md` (passing mentions, not a router map).

## Proposed direction
Add a thin orientation doc for the directory — either `packages/server/src/routers/README.md` or, to be picked up by `MODULE-INDEX.md`, a `routers-MODULE.md` (mirror the `services/rest-MODULE.md` flat-companion pattern; see `docs/module-docs.md` for the charter and run `bun run module:index` so the index regenerates). Keep it a *navigation map*, not duplicated procedure docs:
- A one-line-per-router inventory grouped by domain (auth/session, campaign/membership, character & character-state, spell families, encounter/combat/map, content: SRD vs homebrew vs monster vs magic-item, infra: health/dice/notification), each naming the `app-router.ts` key it mounts under so "where does procedure X live" is answerable from the table.
- The partition rules a newcomer cannot infer: SRD = read-only canonical content vs homebrew = user-authored vs monster/magicItem = typed content surfaces; the spell-family responsibility split; the `encounter` vs `encounterCombat` vs `encounterMap` boundary.
- A short "routers stay thin; business logic lives in `services/`" pointer with a cross-link to `services/README.md` and `docs/guides/add-trpc-procedure.md`, so the two layers reference each other.
TDD note: this is a docs leaf with no behavioral code, so no unit test is warranted. If you want it guarded, the existing `app-router.output-coverage.test.ts` already enumerates the router tree; an optional check that every key exported in `app-router.ts` appears in the inventory table could be added later, but is out of scope for a first pass — do not over-engineer a docs file behind a test.
