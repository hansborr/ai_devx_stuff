# 15. AGENTS.md type-assertion guidance omits the lint-enforced marker syntax and the heavily-used interop category

Status: Proposed — codebase maintainability/onboarding audit 2026-06-13. Not yet started.
Theme: type-assertion boundary docs · Area: docs · Severity: medium · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: type-safety-boundaries); evidence independently re-verified. · Confidence: high

## Problem
`AGENTS.md:31` — the canonical "Code Standards" a newcomer reads first — tells developers to avoid type assertions except at "framework, JSON, Prisma, and test boundaries" and to "leave a short reason." But the repo does not accept a prose reason: the `local/type-assertion-boundary` ESLint rule enforces a machine-parseable marker, `// type-assertion-boundary: <category> - <reason>`, whose category must be one of **five** (framework, json, prisma, test, **interop**). AGENTS.md lists only four boundaries, gives no marker syntax, and entirely omits `interop` — which is in fact the 4th most-used category in product code (22 markers), far exceeding the documented `test` boundary (6). A newcomer following AGENTS.md verbatim writes a free-prose comment (no marker → `missingBoundary`) or invents a category like `runtime`/`zod` (→ `invalidCategory`), and hits a confusing lint failure on their very first legitimate cast. The only place the real format and the full category list appear is the rule's own post-failure message — you must trip the gate to learn the rule.

## Evidence
- `AGENTS.md:31` — "Avoid type assertions. Use them only at framework, JSON, Prisma, and test boundaries, or for `as const`; leave a short reason when the boundary is not obvious." Lists only 4 boundaries, no marker syntax, omits `interop`.
- `eslint-rules/type-assertion-boundary.js:8` — `const ALLOWED_CATEGORIES = new Set(["framework", "json", "prisma", "test", "interop"])` — five enforced categories; a marker with any other category yields `invalidCategory` (classifier at :73-75).
- `eslint-rules/type-assertion-boundary.js:210` — the required `// type-assertion-boundary: <category> - <reason>` format and the five categories are spelled out **only** in the `missingBoundary` failure message; `:212` repeats the list in `invalidCategory`. No pre-failure surface states it.
- Measured product usage (`packages/{shared,server,client}/src`): framework 44, prisma 42, json 26, **interop 22**, test 6. `interop` outranks the documented `test` boundary nearly 4×.
- `packages/server/src/services/level-up/asi.ts:83` — a real, substantive `interop` marker (Object.entries widening keys to `string`, narrowing an indexed-access union). `packages/server/src/routers/encounter.ts:98` and `:326` — two more real `interop` markers (Object.keys widening; runtime-predicate narrowing not expressible as a TS type guard). These are the everyday cases AGENTS.md gives the newcomer no category for.
- `docs/generated/local-lint-rules.md:83-93` — the generated rule doc records only description / principle / category / paired guide / repair; it omits the marker format, the five categories, and `interop`. No human-facing doc enumerates the convention.
- `docs/guides/local-eslint-rules.md:142-152` — the rule's `pairedGuide` references `type-assertion-boundary` only as a wiring example for authoring local rules; it does not state the marker syntax or category list either.

## Proposed direction
Doc-only fix; no rule or code change. Two edits, no package-flow ordering concern (docs only):
1. Rewrite the `AGENTS.md:31` bullet to (a) name all five categories including `interop`, and (b) show the exact enforced marker `// type-assertion-boundary: <category> - <reason>`, replacing the misleading "leave a short reason" prose. Keep it terse (one bullet); point to the paired guide for detail.
2. Add a short "Type-assertion boundary marker" subsection to the paired guide `docs/guides/local-eslint-rules.md` (the rule's declared `pairedGuide`): the marker format, the five categories with a one-line meaning each (and a worked `interop` example lifted from `asi.ts:83`), and that the marker may sit same-line after the cast or in the comment block directly above. This is the durable home; AGENTS.md links to it.
3. TDD note: this is documentation, so there is no unit test to add for the prose. The single machine-checkable invariant worth pinning is *doc/rule agreement* — the doc's category list must equal `ALLOWED_CATEGORIES`. If a guard is wanted, extend the existing rule-doc generator/freshness check (the one that emits `docs/generated/local-lint-rules.md`) to surface `ALLOWED_CATEGORIES` into the generated doc so the category list can never silently drift from `eslint-rules/type-assertion-boundary.js:8`; assert the generated block in that generator's test. Generator-surfacing is optional scope — the AGENTS.md + guide edit is the core fix.
