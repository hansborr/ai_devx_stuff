# 11. packages/shared (the contract package) has no schema orientation doc or barrel: 41 schema files reached via 683 deep imports with no map

Status: Done (docs-only first pass, 2026-06-13) — added `packages/shared/src/schemas/MODULE.md` (inputs-vs-entity convention, cross-named/unpaired pairs, `srd.ts` vs `srd-reference.ts` split, high-traffic quick map) and ran `bun run module:index` (shared entry now in `MODULE-INDEX.md`). Leaf item 2 (barrel + `.` export) intentionally DEFERRED per locked decision.
Theme: discoverability of the contract layer · Area: shared · Severity: medium · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: shared-contracts); evidence independently re-verified. · Confidence: high

## Decision (locked 2026-06-13)
**Docs-only first pass: add `packages/shared/src/schemas/MODULE.md` (leaf item 1). Defer the barrel + `.` export (leaf item 2).** The MODULE.md is the high-value, near-zero-risk core and auto-closes the `MODULE-INDEX.md` gap via `module:index`. The barrel drags in tree-shaking (`sideEffects: false`), circular-import, and 683-deep-import-codemod questions that deserve their own separately-sized leaf — do not bundle them here.

## Problem
AGENTS.md tells every new developer that "Shared Zod schemas are the contract; derive types from them" — yet `packages/shared` ships no map to that contract. There is no `schemas/index.ts`, no `src/index.ts`, no `MODULE.md`/`README` anywhere under `packages/shared/src`, and `MODULE-INDEX.md` (which catalogs ~60 module docs across client and server) has *zero* `packages/shared` entries. So a newcomer who needs `characterUpdateSchema` cannot discover which of 41 schema files holds it; they must already know to import `@musi/shared/schemas/character-inputs.js` and not `.../character.js`. The package the entire `shared -> server -> client` flow derives its types from is the single least-navigable corner of the repo, and the 683 deep import specifiers that result are 683 places a reader has to reverse-engineer the file layout.

## Evidence
- `packages/shared/package.json:8-33` — `exports` is per-glob only (`./schemas/*.js`, `./rules/*.js`, `./dice/*.js`, `./map/*.js`, `./test/*.js`, plus a single `./constants`); there is **no** root `.` (aggregate/barrel) export, so consumers can only address individual files by exact filename.
- `find packages/shared/src -name index.ts` returns nothing; `find packages/shared/src -iname 'MODULE.md' -o -iname '*-MODULE.md' -o -iname 'README*'` returns nothing. The only `src` top-level entries are `constants.ts`, `dice/`, `map/`, `rules/`, `schemas/`, `test/`, and two sentinel tests — no orientation file at any level.
- `packages/shared/src/schemas/` holds 41 non-test schema source files (`ls *.ts | grep -v '.test.ts' | wc -l` → 41) and no `index.ts`. Naming carries an undocumented convention: 20 of them are `*-inputs.ts` files (`attack-roll-inputs.ts` … `weapon-mastery-inputs.ts`) that pair with separate entity files (e.g. `character-inputs.ts` ↔ `character.ts`, but also cross-named pairs like `attack-roll-inputs.ts` whose entity counterpart is `combat-action.ts`). Which half holds an input schema vs. an entity/output schema is knowable only by opening files.
- `rg -o "@musi/shared/schemas/" packages/server/src packages/client/src` → **683** deep import occurrences (server 283, client 400). Each one names a specific schema file, so reading or writing any consumer requires already knowing the file→symbol mapping the package never states.
- `packages/shared/src/schemas/srd.ts:4-14` — `srd.ts` re-imports `alignmentSchema`, `conditionSchema`, `damageTypeSchema`, … from `./srd-reference.js`; the `srd.ts` vs `srd-reference.ts` split (and which file is canonical for a given SRD enum) is undocumented anywhere.
- `MODULE-INDEX.md:1-7` declares it "lists every `*MODULE.md` orientation file in the repository," and `rg -in "packages/shared" MODULE-INDEX.md` returns nothing — the contract package is absent from the repo's own discoverability index because it has no module doc to list.

## Proposed direction
Fix the *shape* only; do not reorganize schema files in this leaf.

1. **Add a `packages/shared/src/schemas/MODULE.md`** (per the module-doc contract at `docs/module-docs.md`, the same one `MODULE-INDEX.md` is generated from). It should state: the `*-inputs.ts` (tRPC input / request payload) vs entity-file (canonical entity + derived `z.infer` types) convention; the cross-named pairs (e.g. attack-roll-inputs↔combat-action) that break the obvious `foo-inputs.ts`↔`foo.ts` pattern; the `srd.ts` vs `srd-reference.ts` split; and a "which file holds what" quick map for the high-traffic entities (character, campaign, encounter, homebrew, map). Running `bun run module:index` will then auto-add the shared entry to `MODULE-INDEX.md`, closing the index gap with no hand-edit.
2. **Consider a thin `schemas/index.ts` barrel** re-exporting the public schemas, plus a `.` (or `./schemas`) aggregate entry in the `exports` map, so new code can `import { characterUpdateSchema } from "@musi/shared"` without first learning the file layout. This is additive — leave the existing per-glob exports and the 683 existing deep specifiers untouched; a follow-up could codemod them, but that is out of scope here.
3. **TDD note.** A barrel is the testable surface: add a `packages/shared/src/schemas/index.test.ts` that asserts the barrel re-exports a representative set of schema symbols (so a newly added schema file that is omitted from the barrel fails a test rather than silently being undiscoverable), and a `module:index` freshness check already guards the doc. The MODULE.md itself needs no new test beyond the existing module-index generation gate.

Package-flow order: this is purely within `shared`, the head of the `shared -> server -> client` chain, so it lands as a self-contained first step with no downstream sequencing required.

## Scope / caveats
- In scope, and explicitly **not** a duplication or dead-code finding: nothing here claims any schema file is unused or redundant (those classes are owned by `docs/agent_notes/backlog/drift-ai-findings/`). This is solely about the *absence of orientation/barrel* for files that are all live (683 imports prove they are used). The `*-inputs.ts`/entity split is a legitimate, intentional separation; the finding is that it is undocumented, not that it should be merged.
- Distinct from existing backlog items: it is not a lint-debt drain, not a useEffect/Storybook/dep-bump item, not a UX/infra item, and not an agent-harness ergonomics item (this is human-onboarding discoverability of a product package). It does not overlap `MODULE-INDEX.md` governance per se — the gap is that shared *has no doc to index*, which a single new MODULE.md fixes.
- Do **not** touch the per-glob `exports` entries or rewrite existing deep imports in this leaf; that is a larger codemod with its own review. The barrel/index step (item 2) is optional and can be deferred if the team prefers a docs-only first pass — the MODULE.md (item 1) is the high-value, near-zero-risk core of this finding.
- Risk: if a barrel is added, watch for `sideEffects: false` (set in `package.json:7`) and bundler tree-shaking — a barrel that only re-exports types/schemas stays side-effect-free, so tree-shaking is preserved; verify no circular re-export is introduced (schemas already cross-import, e.g. srd → srd-reference).
