# 13. damageType validated inconsistently across the shared contract: canonical enum in some schemas, free string in others

Status: Done — 2026-06-13. Tightened subspeciesSchema.damageType, equipmentWeaponDataSchema.damageType, weaponPropertiesSchema.damageType, and homebrewWeaponDisplaySchema.damageType to the canonical `damageTypeNameSchema`; collapsed the two private `damageTypeField` copies into one exported `damageTypeInputField` (rules/damage-types.ts) imported by attack-roll-inputs.ts + spell-action-inputs.ts. Normalized the subspecies seed seam (seed-srd.ts lowercases the title-case upstream `damage_type`); equipment seed already lowercases. monster.ts damage arrays kept as open `z.array(z.string())` with a documenting comment — DATA-GATED: the SRD monster seed legitimately carries non-enum prose ("Damage type chosen for the Draconic Origin trait below") and parenthetical condition notes ("Charmed ((with Mind Blank))") rendered verbatim in the stat block; the homebrew *write* validator already uses the enum. Did not touch srd-reference.ts display catalog. srd router uses the existing `narrowDamageTypeName` Prisma-boundary helper.
Theme: shared-contract consistency · Area: shared · Severity: medium · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: shared-contracts); evidence independently re-verified. · Confidence: high

## Decision (locked 2026-06-13)
**Tighten field-by-field to the canonical lowercase `damageTypeNameSchema`, normalizing at the seam — do not just leave the rules-participating fields as free strings.** The data audit is settled: upstream/seeded damage names are uniformly title-case (`"Fire"`, `"Slashing"`, `"Acid"`), the enum is lowercase, so every tightening needs an explicit normalization step.

Decisions:
- **Add `subspeciesSchema.damageType` to the tighten list** (`srd.ts:99`, currently `z.string().nullable()`). It was missing from the leaf's original enumeration and is fed title-case values (`"Acid"`/`"Fire"`/`"Cold"`/`"Lightning"`/`"Poison"`) straight from `5e-SRD-Subspecies.json` — verified.
- Tighten the rules/app-facing damage-type fields to `damageTypeNameSchema` and normalize the seed/import values to the lowercase canonical token at the seam (i.e. map the title-case source to the lowercase token on the way in).
- **Precision (do not over-apply):** do NOT lowercase the SRD *display catalog*. `srd-reference.ts:19` `damageTypeSchema` is the `{id,name,description}` entity that keeps `name: "Fire"` for display, with the lowercase token already in its `index` field — it stays out of scope, as the leaf already states.
- **Collapse the two private `damageTypeField` copies** (`spell-action-inputs.ts:36`, `attack-roll-inputs.ts:48`) into one exported input validator — do this regardless of the per-field tightening calls.
- Where a field genuinely must stay open (ad-hoc combat-log labels), keep it a string but route it through that single exported validator with a one-line comment stating why it is not the enum.

## Problem
The shared package already declares a canonical damage-type contract — `DAMAGE_TYPES` (13-value tuple) and `damageTypeNameSchema = z.enum(DAMAGE_TYPES)` in `rules/damage-types.ts` — and `spell.ts` and `homebrew.ts` correctly use it. But several other `damageType` fields in the same `packages/shared/src/schemas/` directory bypass it and accept an arbitrary string, and two unrelated input-schema files each re-declare their own private `damageTypeField = z.string().trim().min(1).max(MAX_DAMAGE_TYPE_LENGTH)`. So the *same domain concept* is a closed 13-value enum in some files and an open string in others, with no comment explaining the split. A new developer reading the contract cannot tell which form is authoritative, whether `"Fire"`/`"radiantt"`/`"sonic"` is a valid value, or which schema to copy when adding the next weapon/spell field — exactly the "where does X go / what's the rule for X" discoverability cost this audit targets. Because shared Zod schemas are the contract the whole `shared -> server -> client` flow derives from, the inconsistency propagates outward silently.

## Evidence
- `packages/shared/src/rules/damage-types.ts:7` — canonical `DAMAGE_TYPES` tuple (13 lowercase SRD damage types, `as const`); `:25` — `export const damageTypeNameSchema = z.enum(DAMAGE_TYPES)`; `:27` — companion `isValidDamageTypeName` guard. This is the single source of truth.
- `packages/shared/src/schemas/spell.ts:5,80` — imports `damageTypeNameSchema` and uses it (`damageType: damageTypeNameSchema.nullable()`). Correct.
- `packages/shared/src/schemas/homebrew.ts:5,176-178` — imports it and uses it for `damageResistances`/`damageImmunities`/`damageVulnerabilities` (`z.array(damageTypeNameSchema).optional()`). Correct.
- `packages/shared/src/schemas/homebrew.ts:327` — but `homebrewWeaponDisplaySchema.damageType` in the *same file* is a free `z.string().optional()`, not the enum.
- `packages/shared/src/schemas/srd.ts:280` — `equipmentWeaponDataSchema.damageType: z.string().min(1)` — free string, no enum.
- `packages/shared/src/schemas/inventory.ts:34` — `weaponPropertiesSchema.damageType: z.string()` — free string; comment at `:31` says it is "aligned with SRD equipmentWeaponData", so it mirrors the un-validated SRD shape.
- `packages/shared/src/schemas/monster.ts:138-140` — `damageResistances`/`damageImmunities`/`damageVulnerabilities` are each `z.array(z.string())` — free strings for the *same* damage-type concept that `homebrew.ts:176-178` validates with `z.array(damageTypeNameSchema)`. This is the starkest single-concept split: two sibling entity schemas validate monster vs. homebrew damage affinities incompatibly, and `monster.ts` should be included in the canonical-vs-open decision (step 2).
- `packages/shared/src/schemas/spell-action-inputs.ts:9,36` — imports `MAX_DAMAGE_TYPE_LENGTH` and declares a file-private `const damageTypeField = z.string().trim().min(1).max(MAX_DAMAGE_TYPE_LENGTH)` (used at `:52,150,173`).
- `packages/shared/src/schemas/attack-roll-inputs.ts:8,48` — declares a byte-identical file-private `damageTypeField` (used at `:95,146`). Two independent copies of the same ad-hoc validator, neither referencing the canonical enum.
- `packages/shared/src/constants.ts:47` — `export const MAX_DAMAGE_TYPE_LENGTH = 50`, the bound those two copies share.
- Distinct, do-not-conflate: `packages/shared/src/schemas/srd-reference.ts:19` `damageTypeSchema` is an *entity* row `{ id, name, description }` (the SRD catalog object behind `listDamageTypesOutputSchema`, `srd.ts:376`), not a field validator — it is correctly a different thing and is out of scope for this finding.

## Proposed direction
Fix shape only (do not implement here); follow the shared-first package-flow order (`shared -> server -> client`) and the rules/schemas conventions in the nearest MODULE/orientation docs plus `docs/guides/` for any tRPC/Prisma touch points.
1. Decide the authoritative rule explicitly and write it down: the closed `damageTypeNameSchema` enum is the canonical contract for damage-type *names*. Where a field is genuinely required to stay open (e.g. SRD/homebrew display rows that round-trip externally sourced or user-entered strings that may legitimately fall outside the SRD set), keep it a string but add a one-line comment stating *why it is not the enum* so the split is intentional and discoverable rather than accidental.
2. For fields that should be canonical, replace the free `z.string()` with `damageTypeNameSchema` (or `.nullable()/.optional()` as the field requires): candidates are `srd.ts:280`, `inventory.ts:34`, `homebrew.ts:327`, and `monster.ts:138-140` (the `damageResistances`/`damageImmunities`/`damageVulnerabilities` arrays). Validate against seed/SRD data first — these may carry non-enum values today, so this is a data-compatibility decision, not a mechanical swap.
3. Collapse the two private `damageTypeField` copies (`spell-action-inputs.ts:36`, `attack-roll-inputs.ts:48`) into one shared definition. If they must stay permissive (free string with a length cap) for combat-log inputs, export a single named `damageTypeInputField` from one place (e.g. alongside `MAX_DAMAGE_TYPE_LENGTH` or in `rules/damage-types.ts`) and import it in both, eliminating the duplicate declaration while keeping behavior identical.
4. TDD: add a focused shared test (e.g. `packages/shared/src/rules/damage-types.test.ts` or beside each touched schema) asserting that each now-canonical schema rejects a bogus damage type (`"sonic"`, `"Fire"`) and accepts a canonical one (`"fire"`); for any field intentionally left open, add a test documenting that it accepts a non-enum string, pinning the deliberate choice. Run with `bun run test -- <file>`. Then `bun run verify:changed` with the shared edits staged.

## Scope / caveats
This is a shared-contract *consistency* finding (one domain concept validated two incompatible ways) — it is explicitly NOT a duplication/dead-code finding. The `damageTypeField` copies are mentioned only as evidence of the inconsistency and as a tidy-up rider; the core ask is "make the validation contract for damage types coherent and self-documenting", which is owned by this `shared-contracts` track, not by `drift-ai-findings/` (whose remit is near-duplicate and dead code). It is distinct from existing backlog items (no overlap with the lint-coverage, useEffect, Storybook, dep-bump, UX, or test-tier leaves). Do NOT touch `srd-reference.ts:19` `damageTypeSchema` — it is a different entity (catalog row, not a name validator). Treat any swap of a free string to the enum (step 2) as data-gated: confirm seed/import data only ever contains canonical lowercase values before tightening, or the change will reject real rows; where it would, leave the field open with an explanatory comment rather than forcing the enum.
