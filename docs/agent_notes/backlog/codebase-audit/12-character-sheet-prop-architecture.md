# 12. Character-sheet prop architecture: ~25-field prop bag hand-duplicated across 4 interfaces, parallel self/DM handlers drilled to leaves, opaque sheet god-object slots

Status: Done — implemented 2026-06-14 (batch 5a)
Theme: prop-drilling / lockstep prop interfaces · Area: client · Severity: medium · Size: M

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: client-architecture); evidence independently re-verified. · Confidence: high

## Problem
The character-sheet composition forces a newcomer to edit the same prop list in lockstep across four hand-maintained interfaces just to thread one field to a leaf. `useSheetState` aggregates 11 feature hooks into a 23-field return object; `CharacterSheetContentBody` spreads ~26 explicit props into `SheetBody`, which re-bundles them (plus `stats`) into a single `shared` object spread verbatim into *both* `DesktopSheetLayout` and `MobileSheetTabs`. The ~25-field props interface is then **hand-duplicated standalone** in `sheet-body.tsx`, `desktop-sheet-layout.tsx`, and `mobile-sheet-tabs.tsx` (the mobile copy re-narrows it again per tab via `Pick`). Adding or renaming a single sheet field means touching at least four prop interfaces by hand, with nothing keeping them in sync — a classic "where do I even add this?" tax that hits exactly the file a new contributor reaches for first. Two further smells compound it: the tree carries **parallel self/DM handler pairs** (`onAdjustHp`/`dmAdjustHp`, `onUpdateStats`/`dmUpdateStats`/`dmUpdateStatsAsync`) drilled all the way to leaves that re-resolve the `isDm` discriminator locally, so the same branch is re-decided in multiple places; and `LevelUpDialogSlot`/`WeaponMasterySlot` accept the entire `useSheetState` aggregate as one opaque `sheet` prop, hiding their real (small) dependency surface — unlike the sibling `RestDialogs`/`SpellDialogs` in the same file, which list explicit props.

## Proposed direction
Fix the *shape*, not just symptoms; do not rewrite sheet behaviour. Read the nearest `*MODULE.md` for the character-sheet area first (check `MODULE-INDEX.md`), and `docs/guides/client-effects.md` is not implicated (no effects added). This is client-only — no `shared`/`server` change, so no package-flow ordering concern.

1. **Collapse the duplicated interface to one source.** Export a single `SheetSharedProps` type (e.g. from `sheet-body.tsx` or a small `sheet-props.ts`) and have `DesktopSheetLayoutProps`/`MobileSheetTabsProps` derive from it (`type DesktopSheetLayoutProps = Omit<SheetSharedProps, "campaignId" | "currentUserId"> & { stats: CharacterStats }`), rather than re-typing the field list three times. Per-tab narrowing via `Pick` can keep pointing at the one shared type. Net: adding a sheet field edits one interface, and TypeScript propagates the requirement.
2. **Resolve the self/DM branch once.** Have `useDmStatsCallbacks` (already present at `sheet-state.ts:135-156`) own the `isDm`-based selection and pass a *single* resolved `adjustHp`/`updateStats` down, so `hp-adjuster.tsx:135` and `ability-scores-state.ts` stop re-deciding `isDm`. Keep the existing `NOT_FOUND`/auth semantics untouched (`docs/authorization.md`); this is a client wiring change only.
3. **Give the two slots explicit props.** Change `LevelUpDialogSlot`/`WeaponMasterySlot` to accept the named fields they use (matching `RestDialogs`/`SpellDialogs`), removing the opaque `sheet: ReturnType<typeof useSheetState>` dependency so a reader sees each dialog's true inputs.

TDD: this area is render-prop wiring, so lean on component/RTL tests — add/adjust tests asserting (a) a DM `onAdjustHp` routes through the campaign-scoped path and a non-DM one does not (pinning the single-resolution behaviour before the refactor), and (b) `LevelUpDialogSlot`/`WeaponMasterySlot` render correctly given only their explicit props. Run focused via `bun run test -- <file>`. The interface-collapse step is type-level — `bun run typecheck` is the guard there.

## Scope / caveats
In-scope and explicitly **not** a duplication/dead-code finding: the duplicated *prop interfaces* are a maintainability/onboarding smell (lockstep edits, lower discoverability), not duplicated runtime logic or unused code — those classes are owned by `docs/agent_notes/backlog/drift-ai-findings/` and are not what this leaf reports. Distinct from the planned Storybook UI-primitive catalog (`storybook-component-catalog.md`), which targets `components/ui/` primitives, not the sheet composition layer; and distinct from the useEffect guardrail program (no effects involved). Do **not** touch the leaf panels' own logic (`combat-stats`, `equipment-summary`, etc.), the socket/presence wiring (`useCharacterSheetSocket`), or the auth `NOT_FOUND` semantics; keep this to prop plumbing. Sequencing: the interface-collapse (step 1) is the safe, highest-leverage first move and can land independently; steps 2-3 are separable follow-ons. Risk is moderate because the `shared`-object spread means a missed prop fails at type-check rather than silently — lean on `typecheck` after each step.
