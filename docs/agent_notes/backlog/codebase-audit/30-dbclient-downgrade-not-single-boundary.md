# 30. "single trust boundary" DbClient downgrade comment is contradicted by identical casts in production + test code, with no sanctioned factory

Status: Done — codebase maintainability/onboarding audit 2026-06-13. Added the sanctioned `toDbClient()` factory in `utils/prisma-types.ts` (the one `as unknown as DbClient` boundary, with its reason comment); routed `trpc/context.ts`, `routes/upload-routes.ts`, and `test/test-db.ts` through it; corrected the context.ts "single boundary" comment; replaced the 13 per-test `prisma as unknown as DbClient` casts with `import { db } from test/test-db` (the `broadcast-helpers.test.ts` mock cast stays as a test-boundary mock); added `utils/prisma-types.test.ts` pinning the runtime identity + the compile-time `never` write gate.
Theme: type-assertion boundaries · Area: server · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: type-safety-boundaries); evidence independently re-verified. · Confidence: high

## Problem
`packages/server/src/trpc/context.ts:47-52` documents its `prisma as unknown as DbClient` cast as "the **single** trust boundary where the raw `PrismaClient` is downgraded to the restricted `DbClient` shape." That invariant is false: the identical double-cast is independently re-created in 14 other places, including a real production downgrade in `upload-routes.ts:11` that is built entirely outside the tRPC context. `DbClient` is defined as a bare `type` in `prisma-types.ts:132` with no exported factory, so every site hand-copies the `prisma as unknown as DbClient` incantation (and, separately, a long hand-copied boundary comment). For a new developer, the "single boundary" claim is actively misleading — they will trust it, then discover the safety narrowing is re-asserted ad hoc in production upload handling and a dozen test files, with no single function to grep for or to harden if the downgrade rule ever changes.

## Evidence
- `packages/server/src/trpc/context.ts:47-54` — comment asserts "single trust boundary where the raw `PrismaClient` is downgraded"; the cast itself is `prisma: prisma as unknown as DbClient` (line 54).
- `packages/server/src/routes/upload-routes.ts:10-11` — an independent **production** downgrade `const db = prisma as unknown as DbClient`, outside `createContext`, with its own near-identical hand-copied `type-assertion-boundary` comment. This is the clearest contradiction of "single."
- `packages/server/src/test/test-db.ts:8-9` — a third hand-written downgrade (`export const db = prisma as unknown as DbClient`) with yet another copy of the boundary comment; it is the shared test helper, so the duplication then fans out further.
- `rg 'as unknown as DbClient'` returns **15** occurrences total: the two above plus `test-db.ts` plus 12 more in `*.test.ts` files (e.g. `services/combat-actions/combat-actions.test.ts:20`, `services/spell-casting/spell-casting.test.ts:25`, `utils/concentration-helpers.test.ts:12`). Of the 14 non-context sites, 13 cast `prisma` directly and one (`services/encounter-combat/broadcast-helpers.test.ts:68`) casts a mock object via the same `as unknown as DbClient` shape.
- `packages/server/src/utils/prisma-types.ts:127-147` — `DbClient` is defined as a `type` (line 132) and is the only `DbClient` export; there is no `toDbClient`/`asDbClient`/downgrade factory anywhere in the file, so the cast cannot be centralized today and is necessarily re-written per call site.

## Proposed direction
Fix shape (do not implement here):
1. Add a single sanctioned downgrade factory in `packages/server/src/utils/prisma-types.ts` (e.g. `export function toDbClient(client: PrismaClient): DbClient`), with the `as unknown as DbClient` cast and the canonical boundary comment living *only* inside it. This makes the type-assertion boundary a real, greppable, single function — matching the "single trust boundary" language the codebase already wants to be true.
2. Route the real boundaries through it: `context.ts:54` and `upload-routes.ts:11` call `toDbClient(prisma)`; `test/test-db.ts:9` does too (so test fan-out collapses to the shared helper). Per-test files that build mocks (`broadcast-helpers.test.ts:68`) are a test-boundary cast and can stay, but most `*.test.ts` sites should import `db` from `test/test-db.ts` rather than re-cast `prisma`.
3. Correct the `context.ts` comment from "single trust boundary" to "the production-context entry point; all downgrades go through `toDbClient` in `utils/prisma-types.ts`" so the prose stops over-claiming.
4. TDD: add a focused unit test beside the factory, e.g. `packages/server/src/utils/prisma-types.test.ts`, asserting `toDbClient(prisma)` returns a value whose race-sensitive direct writes are typed `never` (compile-time assertion via a `@ts-expect-error` on `db.characterStats.update(...)`), pinning the narrowing contract to the one factory. Optionally add a lint/grep guard (or extend the type-assertion-boundary doc) so new `as unknown as DbClient` casts outside the factory/test-mock boundary are flagged. Run `bun run test -- packages/server/src/utils/prisma-types.test.ts`. Package-flow order is server-only (no shared/client change). Cross-reference `docs/CONCURRENCY.md` (which the existing boundary comments already cite) for why the narrowing exists.

## Scope / caveats
- Server-only; do not touch `packages/server/src/generated/prisma/**` (generated) or the `DbClient`/`TxClient` *shape* itself — the finding is about where the downgrade is performed and documented, not about the narrowed delegate definitions.
- This is **not** a duplication or dead-code finding: it is not filed as "these casts are near-duplicates, dedupe them" (that class is owned by `docs/agent_notes/backlog/drift-ai-findings/`). The defect is a **false documented invariant** at a type-assertion trust boundary plus the absence of a sanctioned factory — a type-safety-boundaries / onboarding-correctness issue. The dedup of the copied comment is incidental, not the thesis. Distinct from the lint-coverage / agent-friction and lint-ratchet backlogs.
- Test-boundary casts (mock construction) are legitimately allowed by `AGENTS.md` ("type assertions … only at framework, JSON, Prisma, and test boundaries"), so the goal is not to eliminate every cast — it is to make production downgrades flow through one factory and to fix the over-claiming comment. Low risk: behavior is unchanged (the factory's body is the same cast); the only runtime touch is wrapping two production sites in a call.
