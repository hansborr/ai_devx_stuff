# 26. Homebrew EDITOR_REGISTRY boundary erases all per-entry-type form typing to `unknown`, so a handler/formState mismatch only fails at runtime Zod parse

Status: Done — implemented 2026-06-14 (batch 5a)
Theme: type-safety-boundaries · Area: client · Severity: low · Size: M

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: type-safety-boundaries); evidence independently re-verified. · Confidence: high

## Problem
The `EditorHandler` interface that every homebrew entity form is funneled through types its form value, `onChange` argument, `getDefault`/`build` return, and the `Component`'s `form` prop entirely as `unknown`, and `defineEditor` bridges each concrete `TForm` handler to it with `handlers as unknown as EditorHandler`. `entry-dialog.tsx` then threads `formState: unknown` through its hook, its body component, and the submit path, calling `handler.getName(formState)` and `handler.build(formState)` with **no compile-time link** between the selected `entryType` and the `formState` actually held. Type safety is recovered only at submit, where `createEntryInputSchema`/`updateEntryInputSchema.safeParse` rejects a bad shape at runtime. This costs a new developer directly: `entries/MODULE.md` advertises `EDITOR_REGISTRY` as *the one place that knows about every entity type* and the literal copy-this checklist for adding one ("Add an import block here + one entry... Nothing else changes"). A contributor who wires a new entity's `build`/`Component` against a mismatched form shape gets a green compile and a silent runtime failure — exactly the surprise the orientation doc is supposed to remove.

## Evidence
- `packages/client/src/components/homebrew/entries/entry-editor-registry.ts:39-48` — `EditorHandler` types `getDefault` return as `unknown`, `build: (form: unknown)`, `getName: (form: unknown)`, and `Component: FC<{ form: unknown; onChange: (f: unknown) => void; ... }>` — all per-type form typing is erased at this boundary.
- `packages/client/src/components/homebrew/entries/entry-editor-registry.ts:50-62` — `defineEditor<TForm>` takes a fully-typed `TForm` handler set but returns `handlers as unknown as EditorHandler` (the `type-assertion-boundary: framework` comment at :60). Each of the nine `defineEditor<ReturnType<typeof getDefaultXData>>({...})` entries (:65-118) therefore registers a handler whose concrete form type is discarded the moment it lands in `EDITOR_REGISTRY`.
- `packages/client/src/components/homebrew/entries/entry-dialog.tsx:108-118` — `EntryFormBody` receives `formState: unknown` and `setFormState: (f: unknown) => void` alongside the `entryType`, but the two are unrelated types; it passes `form={formState}` straight into the looked-up `Component` (:127-128).
- `packages/client/src/components/homebrew/entries/entry-dialog.tsx:138-159` — `useEntryFormState` holds `formState` as `useState<unknown>`, seeded by `handler.getDefault(entry?.data)`; the entry's `type` and the form value are stored as independent state with no type relationship.
- `packages/client/src/components/homebrew/entries/entry-dialog.tsx:174,190-195` — at submit, `handler = EDITOR_REGISTRY[entryType]` then `handler.getName(formState)` / `handler.build(formState)` are called with no compile-time guarantee `formState` matches the `entryType`'s handler.
- `packages/client/src/components/homebrew/entries/entry-dialog.tsx:196-214` — type safety is recovered **only here**, at runtime, via `updateEntryInputSchema.safeParse(...)` / `createEntryInputSchema.safeParse(...)`; a shape mismatch surfaces as `fieldErrors`, not a type error.
- `packages/client/src/components/homebrew/entries/MODULE.md:11-17` — the "The entity-type registry" section names `entry-editor-registry.ts` / `EDITOR_REGISTRY` as the single place that knows every entity type and gives the copy-this onboarding checklist for adding one.

## Proposed direction
Fix the *shape* only; do not rewrite the dialog flow. Make `entryType` and `formState` co-vary through a discriminated union so a mismatch is a compile error instead of a runtime `safeParse` failure:
- Introduce a per-type form map (e.g. `type EntryFormByType = { feat: FeatFormData; spell: SpellFormData; ... }` keyed by `HomebrewEntryType`), sourced from each sibling module's existing exported `FormData` type (e.g. `FeatFormData` in `feat/feat-form-fields.tsx:8-16`) rather than re-deriving via `ReturnType`. Type `EditorHandler<T extends HomebrewEntryType>` against `EntryFormByType[T]` and make `EDITOR_REGISTRY` a `{ [T in HomebrewEntryType]?: EditorHandler<T> }`, so `defineEditor` no longer needs `as unknown as`.
- In `entry-dialog.tsx`, narrow at the dispatch site: hold `formState` as a discriminated `{ type; data }` (or read the handler under a `switch`/narrowing on `entryType`) so `handler.build(formState)` typechecks per branch and the `unknown` threading at :115-116, :141, :158 collapses.
- TDD: this is a type-level guarantee, so the regression guard is a compile-time fixture (a `// @ts-expect-error` asserting that pairing a wrong `formState` with an `entryType` no longer typechecks) plus extending the existing runtime suite `entry-dialog.test.tsx` to keep the per-type render/submit paths green. Add a new entity-type stub in a test to prove the registry still rejects shape drift at the type boundary, not just at `safeParse`.
- Package-flow note: the `FormData` types live client-side already; this is a client-only change (no `shared`→`server` ripple). Read `entries/MODULE.md` and follow `docs/guides/add-client-feature-module-cache-socket.md` conventions for where the per-type form contract should live. After the change, update the MODULE.md checklist to note that the registry entry is now type-checked against the entity's `FormData`.

## Scope / caveats
- Touch only `entry-editor-registry.ts` and `entry-dialog.tsx` (plus the new type map and tests). Do **not** alter the entity form modules' runtime behavior or their `buildX`/`getDefaultX` signatures, and do not touch the genuine framework boundaries (Radix `Select` `onValueChange` cast at `entry-dialog.tsx:89-90` is legitimately a string→enum narrowing and stays).
- This is a **type-safety / onboarding** finding, not duplication or dead code — every cited symbol is live and exercised by `entry-dialog.test.tsx`; it is therefore distinct from the drift-ai-findings backlog (which owns near-duplicate and dead-code items). It is not a lint-debt drain, not a useEffect guardrail, and not a dependency bump, so it does not overlap the out-of-scope packs.
- Risk is low and self-contained, but the nine `ReturnType<typeof getDefaultXData>` derivations must be reconciled with each module's exported `FormData` type (confirm they are identical before swapping); if any drift exists, treat that reconciliation as the first, smallest commit. Keep the runtime `safeParse` at submit as defense-in-depth — the goal is to add a compile-time guard ahead of it, not remove it.
