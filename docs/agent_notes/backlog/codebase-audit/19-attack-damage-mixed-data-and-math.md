## Problem
`packages/shared/src/rules/attack-damage.ts` is named for weapon attack/damage *math*, but 278 of its 501 lines are the static `SRD_WEAPONS` reference table — a pure data catalog of every SRD weapon's dice, type, category, and properties. The same file then also owns `WEAPON_PROPERTIES`, attack-ability resolution, spell save DC / spell attack math, inventory→weapon conversion, the proficiency check, and display formatting. Two test files compound the discoverability problem by naming modules that have **no matching source file**: `srd-weapons.test.ts` reaches into `attack-damage.ts` for the weapon table, and `armor-class.test.ts` reaches into `character-rules.ts` for `SRD_ARMOR`/`calculateArmorClass`. A new developer who opens `srd-weapons.test.ts` and naturally looks for `srd-weapons.ts`, or who greps for an armor bug starting from `armor-class.test.ts` and looks for `armor-class.ts`, finds nothing — they must already know that the weapon data lives in a math file and that armor lives in `character-rules.ts`. That is exactly the "where does X live?" tax this audit is meant to reduce, in the single most-edited rules surface (a complexity hotspot at 501 lines).

## Evidence
- `packages/shared/src/rules/attack-damage.ts:50-328` — `export const SRD_WEAPONS: Record<string, WeaponData>` is a 278-line static data table (Club through Pistol), the bulk of a 501-line file (confirmed `wc -l` = 501) whose name advertises damage math, not a weapon catalog.
- `packages/shared/src/rules/attack-damage.ts:16-29` — `WEAPON_PROPERTIES`/`WeaponProperty` (reference data) also live here; `:390`/`:394` add spell save DC and spell attack bonus (unrelated to weapons); `:416` `getWeaponDataFromItem` (inventory conversion); `:482` `isWeaponProficient`; `:497` `formatWeaponDamage` (display) — six distinct concerns under one "attack-damage" name.
- `packages/shared/src/rules/srd-weapons.test.ts:3` — `import { SRD_WEAPONS, WEAPON_PROPERTIES } from "./attack-damage.js";`; the test is named `srd-weapons` but there is no `srd-weapons.ts` (confirmed: `ls packages/shared/src/rules/srd-weapons.ts` → no such file). The whole suite (`:329-359`) is a data-conformance check on the table, not a math test.
- `packages/shared/src/rules/armor-class.test.ts:4-12` — imports `calculateArmorClass`, `SRD_ARMOR`, `getArmorDataFromItem`, `computeCharacterAc`, `SHIELD_AC_BONUS`, `UNARMORED_BASE_AC` from `./character-rules.js`; there is no `armor-class.ts` (confirmed via `ls`). `SRD_ARMOR` is defined at `packages/shared/src/rules/character-rules.ts:183`; `calculateArmorClass` at `:224`.
- `packages/shared/src/rules/` directory listing — `attack-damage.test.ts` correctly co-locates with `attack-damage.ts`, and `weapon-mastery.test.ts` with `weapon-mastery.ts`, so the two orphans (`srd-weapons.test.ts`, `armor-class.test.ts`) stand out as the only test files in this directory whose basename has no source twin. No `MODULE.md`/`*-MODULE.md` exists under `packages/shared/src/rules/` to compensate.

## Proposed direction
Fix the discoverability, not the rules. Shape only — do not implement here.

1. **Extract the data tables into source files whose names match the test names.** Create `packages/shared/src/rules/srd-weapons.ts` and move `SRD_WEAPONS`, `WeaponData`/`WeaponCategory`, `WEAPON_PROPERTIES`/`WeaponProperty`, and `normalizeWeaponProperties` there; re-export from `attack-damage.ts` (or update importers) so no caller breaks. Move `SRD_ARMOR`/`ArmorData` out of `character-rules.ts` into a new `armor-class.ts` alongside `calculateArmorClass`/`getArmorDataFromItem`/`computeCharacterAc` (or, minimally, point `armor-class.test.ts`'s imports at the module the symbols actually live in once that module is named for them). After the moves, `srd-weapons.test.ts:3` and `armor-class.test.ts:4` import from the file their own name implies.
2. **TDD / test impact.** This is a pure relocation: keep `srd-weapons.test.ts` and `armor-class.test.ts` green by updating only their import paths to the new source files — the assertions (the SRD conformance table at `srd-weapons.test.ts:15-358`, the AC suites at `armor-class.test.ts`) are unchanged and become the regression guard for the move. Re-run `bun run test -- packages/shared/src/rules/srd-weapons.test.ts` and `…/armor-class.test.ts`. Because `attack-damage.test.ts` exercises the math, it pins the remaining math in `attack-damage.ts`.
3. **Follow the rules-change guide and package flow.** Read `docs/guides/change-rules-logic.md` first. This is `shared`-only; per the `shared -> server -> client` flow, keep barrel/`@/*`-alias re-exports stable (or use `bun run code:intel -- dependents …` to find every importer of `SRD_WEAPONS`/`SRD_ARMOR`/`WEAPON_PROPERTIES` in `server`/`client` and update them in the same change) so downstream packages compile unchanged. Consider a short `packages/shared/src/rules/MODULE.md` (one orientation doc, indexed in `MODULE-INDEX.md`) mapping each rules concept to its file, since none exists today.
