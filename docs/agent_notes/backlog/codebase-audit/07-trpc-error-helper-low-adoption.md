# 7. Code-aware error helper (onTRPCError / TOAST_MESSAGES) adopted by only 5 hooks; 18 mutation files hardcode generic "Failed to X" toasts

Status: Done — 2026-06-14. TDD: added/extended catalog-message assertions for representative seams (the factory itself, both roll hooks, the shared layer hook, token/map-detail/combat-map mutations, and collection-card) asserting a coded error (FORBIDDEN) surfaces the catalog copy not the generic string, plus the generic fallback on opaque errors. Source: codebase maintainability/onboarding audit 2026-06-13 (lens: error-observability); evidence independently re-verified. · Confidence: high

## Problem
The client ships a well-designed `onTRPCError` factory backed by a `TOAST_MESSAGES` catalog that maps tRPC error codes (`FORBIDDEN`, `NOT_FOUND`, `UNAUTHORIZED`, `TOO_MANY_REQUESTS`, `BAD_REQUEST`) to accurate user copy, plus per-consumer `onConflict`/`onPreconditionFailed` recovery hooks. Only 5 production files use it — all in `packages/client/src/hooks/vtt-drawer/` — while 18 other mutation files hardcode `toast.error('Failed to X')` inside `onError` handlers that do not even receive the `error` argument, so they *cannot* branch on the code. The result is a real correctness gap a player can hit: a non-DM who edits someone else's note, sets DM-only visibility, or acts after their session expires gets a misleading generic "Failed to X" instead of the catalog's "You don't have permission to…" / "Your session expired…". For a new developer the gap is worse than a missing helper: the right pattern *exists and is documented in a MODULE.md*, but copying any of the 18 nearby examples teaches the wrong one, so the inconsistency self-propagates and there is no single discoverable answer to "how do I surface a mutation error here".

## Evidence
- `packages/client/src/lib/trpc-error.ts:26-43` — `onTRPCError` reads `error.data?.code`, dispatches `CONFLICT`/`PRECONDITION_FAILED` to consumer recovery hooks, then falls through to `TOAST_MESSAGES.codes[code](action)` when the catalog has the code, else `TOAST_MESSAGES.default(action)`. It takes the `error` arg the hardcoded handlers omit.
- `packages/client/src/lib/toast-messages.ts:1-23` — catalog maps `FORBIDDEN` → "You don't have permission to ${action}." (:3), `NOT_FOUND` (:4), `UNAUTHORIZED` → "Your session expired. Please sign in again." (:5), `TOO_MANY_REQUESTS` (:6); `default` is "Failed to ${action}" (:15). The comment at :7-8 confirms the generic copy is intentional *only* for opaque `INTERNAL_SERVER_ERROR`, not for code-bearing errors.
- Adoption (verified via `rg`): exactly 5 production files use `onTRPCError`, all under `packages/client/src/hooks/vtt-drawer/` (`use-confirm-cast.ts`, `use-drop-concentration.ts`, `use-feature-use.ts`, `use-weapon-attack.ts`, `use-monster-hp-update.ts`); the only other matches are the helper itself and the module doc.
- 18 production files hardcode a generic `Failed…` toast (verified via `rg`), e.g. `components/campaign/{chat/chat-panel,combat/combat-map-mutations,encounters/*,maps/*,members/members-panel,notes/notes-panel,npcs/npc-panel,tokens/map-token-mutations}`, `components/homebrew/collections/collection-card`, and `hooks/{use-ability-roll,use-drawing-actions,use-weapon-roll}`. (A repo-wide `rg "toast\.error\(.*Failed"` returns **19** files; the 18 here are the generic hardcoded handlers, and the 19th — `hooks/character-sheet/use-character-spells.ts` — instead surfaces the raw `error.message`, which is leaf #31, not a generic-copy site. So 18 generic + 1 raw-message = 19.)
- `packages/client/src/components/campaign/notes/notes-panel.tsx:194-196,207-209,218-220` — three `onError: () => { toast.error("Failed to … note"); }` handlers, none receiving `error`, so none can branch on code.
- `packages/server/src/routers/note.ts:35-44` — `assertCanEditNote` throws `FORBIDDEN` "You can only edit your own notes" (:37) and `assertDmOnlyVisibility` throws `FORBIDDEN` "Only the DM can set dm-only visibility" (:43): concrete codes the client flattens to "Failed to create/update note".
- `packages/client/src/hooks/vtt-drawer/MODULE.md:105-107` — documents `onTRPCError` from `lib/trpc-error.ts` as the intended pattern ("Use the `onTRPCError` factory … declare an `action` verb plus `onConflict` recovery"), confirming this is an adoption gap, not a design gap.

## Proposed direction
Treat this as a client-only adoption + discoverability fix; nothing in `shared`/`server` changes (the codes are already thrown correctly), so no package-flow ordering concern.
1. Migrate the 18 hardcoded `onError` handlers to `onTRPCError({ action: "<verb the object>" })`, choosing an `action` verb that reads correctly in every catalog template (e.g. `"create this note"` → "You don't have permission to create this note."). Only add `onConflict`/`onPreconditionFailed` where the corresponding server mutation can actually emit those codes — do not invent recovery hooks (the vtt-drawer hooks already model the right restraint; see `use-weapon-attack.ts`'s no-`CONFLICT` note in the MODULE.md).
2. TDD per the MODULE.md "Test Seams" guidance (`vtt-drawer/MODULE.md:95-101`): for each migrated mutation add/extend a co-located test asserting (a) success-path toast/invalidate unchanged, and (b) a `FORBIDDEN`-coded error surfaces the catalog copy, not "Failed to X". The `notes-panel` hooks (`note.create/update/delete`) are the highest-value first target because `note.ts` throws `FORBIDDEN` on a routine player action.
3. Raise discoverability so the next new developer finds the pattern without reading vtt-drawer: lift the `onTRPCError` guidance out of `hooks/vtt-drawer/MODULE.md` into a short note next to the helper (a `lib/MODULE.md` entry or header comment in `trpc-error.ts`) that says "all mutation `onError` toasts go through `onTRPCError`", since the helper is general-purpose and not drawer-specific.

## Scope / caveats
- This is an error-observability/onboarding consistency finding, explicitly NOT a duplication or dead-code finding — the 18 handlers are not copies of each other to be merged, and the helper is live code used by 5 files; that class is owned by `docs/agent_notes/backlog/drift-ai-findings/` and is not touched here.
- Distinct from the out-of-scope backlog: it is not a useEffect guardrail, not a Storybook/component-catalog item, not a lint-debt drain, not a dep bump, and not the UX/production-readiness audits — it is a behavioral toast-copy gap with a server-side code trigger.
- Do not change the catalog's intentional omissions (`INTERNAL_SERVER_ERROR` stays generic per the :7-8 comment; `CONFLICT`/`PRECONDITION_FAILED` stay per-consumer hooks) and do not alter the server `FORBIDDEN`/`NOT_FOUND` codes or their intentional auth mismatch semantics (`docs/authorization.md`). Migration is mechanical but per-call-site (each needs a correct `action` verb), which is why this is M not S; land it in reviewable batches (notes → encounters → maps → homebrew/rolls) rather than one sweep.
