# 39. AoE template geometry (cone/cube/line) lacks a coordinate model and WHY-comments on its reflection/projection math

## Problem
`packages/shared/src/map/area-template.ts` projects D&D area-of-effect shapes onto a grid using dense vector math, but the file's only prose is a 6-line header banner and zero explanatory comments — `rg -ci 'why|because|note'` over the file returns no matches, and `packages/shared/src/map/` has no MODULE.md or README to orient a reader. A new developer asked to fix a cone that "looks wrong on a diagonal" lands on `addDiagonalConeRing`'s `mainCell.y - p * cfg.dirY * cfg.dirX` with no statement of the coordinate convention (which axis is "along", which is "perp", why the reflection multiplies the two direction signs), and must reverse-engineer the intended geometry from the code before they can safely touch it. The math is live: it backs the map canvas template tool, so an unguided edit risks silently mis-projecting spell areas.

## Evidence
- `packages/shared/src/map/area-template.ts:114-129` — `cubeOffset` is a bare `switch (dir)` over `0/90/180/270` mapping each cardinal to an `{x,y}` offset of `depth`/`perp`; no diagram or sentence states which way `depth` (forward) vs `perp` (sideways) point for each case, so the off-by-sign correctness of e.g. the `case 90` (`x: origin.x - perp, y: origin.y + depth`) is unverifiable by reading.
- `packages/shared/src/map/area-template.ts:172-186` — `addDiagonalConeRing` reflects ring cells across the cone's diagonal via `mainCell.y - p * cfg.dirY * cfg.dirX` and `mainCell.x - p * cfg.dirX * cfg.dirY`; the `dirY*dirX` trick (collapsing the four diagonal quadrants into one expression) has no rationale comment.
- `packages/shared/src/map/area-template.ts:197-221` — `lineCells` is a rotated-rectangle hit test (`along = dx*cosA + dy*sinA`, `perp = |−dx*sinA + dy*cosA|`, kept when `along > 0 && perp <= halfWidth`), but the rotated-rectangle model, the `along > 0` half-open gate (excludes the origin and the back half), and the `scan = lengthCells + 1` over-scan are never stated.
- `rg -ci 'why|because|note' packages/shared/src/map/area-template.ts` → 0 matches; `find packages/shared/src/map -iname 'MODULE.md' -o -iname 'README.md'` → none. Only sibling files are `drawing.ts`, `fog.ts`, `grid-utils.ts` (+ tests).
- Dependents (`bun run code:intel -- dependents …area-template.ts`): 6 total — `packages/shared/src/map/area-template.test.ts` (the one test, which directly exercises `coneCells`/`cubeCells`/`lineCells`/`sphereCells`/`emanationCells`) plus 5 non-test consumers. Of those 5, only `packages/client/src/hooks/canvas-input/tool-handlers.ts:1-6` consumes the geometry (via the `templateCells` dispatcher + `cellAngle`/`snapAngle`); the other four — `packages/shared/src/schemas/spell.ts:4`, `template-toolbar.tsx:1`, `template-overlay.tsx:1`, `map-canvas-overlays.tsx:1` — import only the exported constants/types (`TEMPLATE_SHAPES`, `TEMPLATE_SIZE_PRESETS`, `TemplateShape`), not the math. So the projection math is live but reaches the UI through a single call site, making the undocumented internals the sole place its correctness lives.

## Proposed direction
Documentation-only, contained to one `shared`-layer file — no behavior change, so nothing downstream in the `shared -> server -> client` flow moves.
1. Add a short `packages/shared/src/map/area-template-MODULE.md` (or a section in a `shared/src/map` MODULE.md if one is preferred for the whole dir) stating the one coordinate convention used throughout: origin cell, `depth`/`along` = forward axis, `perp` = signed sideways axis, angles snapped to cardinals (cube) vs compass-45 (cone/line), and the Chebyshev distance rule already noted in the header. Reference it from the file header.
2. Add 1–2 line WHY-comments at the three hard spots: the `cubeOffset` switch (a tiny ASCII note of forward/sideways per cardinal), the `addDiagonalConeRing` `dirX*dirY` reflection (state it folds the four diagonal quadrants into one mirror), and the `lineCells` rotated-rectangle test (name the model and explain the `along > 0` half-open gate + `+1` over-scan).
3. TDD-aware: this is comments/docs, so no new assertions are required, but the existing `area-template.test.ts` already pins the numeric behavior — keep it green as the regression guard (`bun run test -- packages/shared/src/map/area-template.test.ts`) and, where a comment makes a non-obvious claim concrete (e.g. "origin excluded from the line"), add a one-line named test (`lineCells excludes the origin cell`) so the comment and the test agree. Add no source logic.

## Scope / caveats
Touch only `packages/shared/src/map/area-template.ts` comments and a new MODULE.md; do not refactor the math, rename the `no-magic-numbers` eslint-disable bands, or alter any function signature (5 of the 6 dependents bind to the exported constants/types, and `tool-handlers.ts` binds to `templateCells`/`cellAngle`/`snapAngle` — all must stay stable). This is a documentation/discoverability finding, explicitly NOT a duplication or dead-code finding (those are owned by `docs/agent_notes/backlog/drift-ai-findings/`): the code is unique, fully live, and well-tested — the gap is that its coordinate model is unwritten. It does not overlap the agent-friction harness leaves, the useEffect/storybook/lint-debt/dep-bump tracks, or the UX/infra audits. Sequencing: standalone, depends on nothing; safest done by someone who reads the existing test cases first so the prose matches verified behavior rather than guessed intent.
