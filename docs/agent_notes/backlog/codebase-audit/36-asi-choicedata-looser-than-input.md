# 36. Persisted ASI choiceData schema is strictly looser than its validated input (free string/int vs STR..CHA enum + 1|2)

Status: Done — 2026-06-13. Tightened `asiChoiceDataSchema.asiIncreases` element in `packages/shared/src/schemas/character.ts` to reuse `abilityAbbreviationSchema` (shared cycle-free from `srd.ts`) for `ability` and the `1|2` literal union for `amount`, matching the validated input boundary (`asiIncreaseSchema`). Added focused schema tests to `character.test.ts` pinning the two boundaries to agree. Verified no seed/fixture data and no server write path persists a non-abbreviation ability or out-of-range amount (the write path builds from the already-enum-validated input type); full typecheck clean across server + client consumers.
Theme: shared schema contract drift · Area: shared · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: shared-contracts); evidence independently re-verified. · Confidence: high

## Problem
The same "ASI increase" shape is declared twice in `packages/shared/src/schemas/` with two different strictnesses. The input boundary (`asiIncreaseSchema`) validates `ability` against the closed `abilityAbbreviationSchema` enum (`STR`/`DEX`/`CON`/`INT`/`WIS`/`CHA`) and `amount` as the literal union `1|2`. The persisted boundary (`asiChoiceDataSchema`) re-declares the element inline as `{ ability: z.string(), amount: z.number().int() }` — any string, any integer. So the stored contract is strictly looser than what was validated on the way in, and it does so by re-typing the shape by hand instead of reusing the enum. For a new developer this is a discoverability and trust trap: the two schemas look authoritative and sit one file apart, but tell different stories about what an ASI increase legally is, and there is nothing pointing the reader from one to the other or explaining why the stored one is weaker (it reads like an oversight, not a decision).

## Evidence
- `packages/shared/src/schemas/character-inputs.ts:212-216` — `asiIncreaseSchema`: `ability: abilityAbbreviationSchema` (closed enum), `amount: z.union([z.literal(1), z.literal(2)])`. This is the validated input shape (consumed by `asiChoiceSchema` at :228-232).
- `packages/shared/src/schemas/character.ts:211-214` — `asiChoiceDataSchema` re-declares the stored element inline as `z.object({ ability: z.string(), amount: z.number().int() })` — free string, any integer. The `// choiceType "asi"` comment marks this as the persisted level-choice shape.
- `packages/shared/src/schemas/srd.ts:27` — `abilityAbbreviationSchema = z.enum(["STR","DEX","CON","INT","WIS","CHA"])` — the single closed enum both layers could share to close the `ability` gap.
- `packages/shared/src/schemas/character-inputs.ts:15-22` — `character-inputs.ts` imports from `./character.js` (`:21`) and `abilityAbbreviationSchema` from `./srd.js` (`:22`). Because `character-inputs` already depends on `character`, having `character.ts` reuse `asiIncreaseSchema` directly would create a cycle — confirming the canonical note that a circular import blocks the obvious reuse.
- `packages/shared/src/schemas/character.ts:10-11` — `character.ts` already imports `speedSchema` from `./srd.js` (and does NOT currently import `abilityAbbreviationSchema`), so adding `abilityAbbreviationSchema` to that existing `./srd.js` import is a clean, cycle-free way for the persisted schema to share the enum.

## Proposed direction
Fix the shape only; do not restructure the modules. Tighten `asiChoiceDataSchema.asiIncreases` element so its `ability` reuses `abilityAbbreviationSchema` (extend the existing `import { speedSchema } from "./srd.js"` at `character.ts:11` to `import { abilityAbbreviationSchema, speedSchema }`), and tighten `amount` to the same `1|2` literal union the input uses (keep the `no-magic-numbers` disable comment pattern already present at `character-inputs.ts:214`). Do not attempt to import `asiIncreaseSchema` itself into `character.ts` — that is the circular import the evidence confirms; sharing the leaf enum from `srd.ts` is the cycle-free path. This is a pure shared-package change with no server/client follow-on (shared -> server -> client flow stops at shared here). TDD: add a focused schema test beside the persisted schemas (e.g. a `character.schema.test.ts`-style spec in `packages/shared/src/schemas/`) asserting that `asiChoiceDataSchema` (a) accepts a valid `{ ability: "STR", amount: 2 }` increase, (b) now REJECTS `{ ability: "Strength", amount: 3 }` (free string + out-of-range int that the old schema silently accepted), and (c) accepts exactly the same increases `asiIncreaseSchema` accepts — pinning the two boundaries to agree. Run with `bun run test -- <that file>`. Before changing the schema, sanity-check existing persisted `choiceData` rows are not relying on the looser shape (the input was already enum-validated on write, so historical data should already satisfy the tighter schema, but confirm there is no migration/transform that wrote a non-abbreviation `ability`).

## Scope / caveats
This is a shared-schema correctness/consistency fix, NOT a duplication or dead-code finding — both schemas are live and used; the issue is that the persisted one is weaker than its own validated input, an asymmetry a reader cannot discover without opening both files. (Near-duplicate code and dead code are owned by `docs/agent_notes/backlog/drift-ai-findings/`; this finding is intentionally about the contract gap, not about collapsing the declaration.) Distinct from existing backlog items: it is not a lint-debt drain, dep bump, useEffect, UX/infra, or test-tier item. Touch only `asiChoiceDataSchema` in `character.ts` (and its import line); do not touch `asiIncreaseSchema`/`asiChoiceSchema` in `character-inputs.ts` (already correct) and do not refactor the circular dependency between the two modules to "share the schema directly" — that is a larger structural change out of scope for an S. Lowest-risk caveat: if any code path persists ASI choiceData that legitimately stores a non-`1|2` amount or a non-abbreviation ability (none found, but verify), the tightening would reject it — the test in (a)/(c) is the guard.
