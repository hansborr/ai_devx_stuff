# 33. activateEncounter lives in utils/ but owns a $transaction, sequences multi-participant writes, and enforces domain invariants

Status: Done — relocated `activateEncounter` to `services/encounter-combat/activate-encounter.ts` (+ colocated test), updated the `routers/encounter.ts` call site and `encounter-combat/MODULE.md`; `blindUpdateParticipant`/`setEncounterState` stay in `utils/`. Behavior-preserving, tests green.
Theme: layering boundary discipline · Area: server · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: server-layering); evidence independently re-verified. · Confidence: high

## Problem
`services/README.md` draws a bright, explicitly-documented line: the distinguishing feature of `utils/` is "no orchestration surface" — anything that owns a transaction boundary, sequences multiple writes, or decides broadcasts is a service. But `utils/encounter-helpers.ts::activateEncounter` does all the things that line forbids: it opens a `prisma.$transaction`, loops `blindUpdateParticipant` over every participant to reindex `sortOrder`, then transitions encounter state — and on top of that enforces two domain invariants by throwing `BAD_REQUEST` (no participants / unrolled initiative). A new developer who reads the README rubric and then opens this file gets the exact opposite of what the doc promised, so the rubric stops being trustable — and the one canonical mutation that turns an encounter live is filed under "pure primitives" instead of next to the rest of combat orchestration, which is where they'd look for it.

## Evidence
- `packages/server/src/utils/encounter-helpers.ts:142-152` — `activateEncounter` owns `await prisma.$transaction(async (tx) => { ... })`, loops `blindUpdateParticipant(tx, p.id, { sortOrder })` over `sorted`, then calls `setEncounterState(tx, ...)` to move `setup → active` — multi-write orchestration under one transaction.
- `packages/server/src/utils/encounter-helpers.ts:129-140` — enforces two domain invariants in the same helper: `throw new TRPCError({ code: "BAD_REQUEST" })` for zero participants and for `!allInitiativeRolled(participants)`. Business rules, not a projection.
- `packages/server/src/services/README.md:65-67` — "The distinguishing feature is 'no orchestration surface' … a service sequences the reads, writes, transactions, and broadcasts."
- `packages/server/src/services/README.md:86-88` — three-question rubric, Q1: "Does it orchestrate — own a transaction boundary, sequence multiple writes, or decide on broadcasts? If no → `utils/`." `activateEncounter` answers yes to two of the three.
- `packages/server/src/services/README.md:57-61` — the `utils/*-mutations.ts` carve-out is explicitly narrow: concurrency primitives "do not own a transaction boundary, do not sequence multi-step protocols." `activateEncounter` is not one of those primitives — it calls them.
- `packages/server/src/utils/encounter-helpers.ts:144` / `:146` — the two primitives it sequences (`blindUpdateParticipant`, `setEncounterState`) are the legitimate single-row helpers: `participant-stats-mutations.ts:178` is a single-row blind update; `encounter-state-mutations.ts:65` is a single `updateMany` CAS. They belong in `utils/`; the orchestrator that fans them out under a transaction does not.
- `packages/server/src/routers/encounter.ts:321-322` — the call site: `if (from === "setup" && input.to === "active") { await activateEncounter(ctx.prisma, input.id); }` — the router treats this as the state-transition orchestration step for going live, parallel to the `setEncounterState` call in the else branch.
- `packages/server/src/services/encounter-combat/` exists (with `MODULE.md`, `initiative-action.ts`, `turn-action.ts`) and is the natural relocation home — its `MODULE.md:48` already documents `rollAllInitiative` (the setup-phase initiative concern) as owned here.
- `packages/server/src/utils/encounter-helpers-auth-lifecycle.test.ts:209-281` — `activateEncounter` already has dedicated coverage (`throws BAD_REQUEST with no participants` :219, `… when not all participants have initiative` :226, `activates encounter and sorts participants by initiative` :249). These tests move with the function; no new behavior coverage is invented.

## Proposed direction
Relocation only — preserve behavior. Move `activateEncounter` from `utils/encounter-helpers.ts` into the existing `services/encounter-combat/` module (a small `activate-encounter.ts` behind the module facade, alongside `initiative-action.ts`), since the encounter going live is a combat-lifecycle concern that already has a home and a `MODULE.md`. Update the single call site at `routers/encounter.ts:321-322` to import from the service rather than `utils/`. Be TDD-aware: the three existing tests at `encounter-helpers-auth-lifecycle.test.ts:209-281` are the regression net — move that `describe("activateEncounter", …)` block into the `encounter-combat` test suite (or a focused `activate-encounter.test.ts`) unchanged first, watch it stay green, then relocate the implementation; the two `BAD_REQUEST` invariant tests and the sort-order test pin the exact contract. Leave `blindUpdateParticipant` and `setEncounterState` in `utils/` — they are correctly-classified single-row primitives the relocated service will keep calling. Follow `docs/guides/add-module-doc.md` if `encounter-combat/MODULE.md` needs an "owned mutations" line for the new entry point, and confirm the rubric in `services/README.md:82-94` against the moved function so the doc and the tree agree. No `shared` or `client` changes — this is server-internal (`shared -> server -> client` flow untouched); no Prisma schema change, so no migration.

## Scope / caveats
Pure structural relocation: do not change the transaction, the invariant checks, the sort, or the call semantics — only the file the function lives in and its import path. This is explicitly NOT a duplication or dead-code finding — `activateEncounter` is live (called from `encounter.ts:322`), has a single implementation, and the fix moves one function rather than removing or merging anything; it therefore stays clear of the drift-ai-findings backlog (near-duplicate / dead-code), which owns those categories. It is distinct from the agent-friction harness backlog (no agent-tooling ergonomics involved) and from the lint/ratchet and dependency-upgrade backlogs. Sequencing note: the move touches the `utils/encounter-helpers.ts` public surface — re-check `bun run code:intel -- dependents` on the helper before committing in case a test or sibling util imports `activateEncounter` directly beyond the one router call site found here, and re-export from `encounter-helpers.ts` only if a transitional shim is needed to keep the change small. Low risk, low value-per-line, but it restores the README's credibility for the next person who reads it to learn "where does orchestration go."
