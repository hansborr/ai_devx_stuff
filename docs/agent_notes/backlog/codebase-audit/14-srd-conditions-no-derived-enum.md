# 14. SRD_CONDITIONS has no exported derived Zod enum; condition-name fields are bare free strings, unlike sibling damage-types

Status: Done — 2026-06-14. Added `srdConditionSchema = z.enum(SRD_CONDITIONS)` (mirrors `damageTypeNameSchema`) and hard-tightened every condition-name field to it: `character.ts` (`characterConditionSchema.conditionName`), `character-inputs.ts` (add/remove condition inputs), `encounter.ts` (`conditionEntrySchema.name`), `monster.ts` (`conditionImmunities`, now closed — the three sibling damage fields stay open strings because the seed carries genuine prose there); `homebrew.ts` now imports the named schema instead of inlining `z.enum(SRD_CONDITIONS)`. Data-gating: the monster seed `conditionImmunities` carried only capitalized canonical names (no prose), so normalized all 369 values to lowercase at the seed JSON (format-preserving, prettier-clean); read seams (`character-mapping.ts`, `monster.ts` router, `stats-conditions.ts`) parse rows through the schema rather than casting; capitalized test fixtures (`character-updates`, `mutation-logging`, `character-sheet`, `participant-stats`) normalized to lowercase, and condition-builder test helpers narrowed to `SrdCondition`. Glossary display-name parser left untouched (deliberately distinct concern).
Theme: shared-contract drift · Area: shared · Severity: medium · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: shared-contracts); evidence independently re-verified. · Confidence: high

## Decision (locked 2026-06-13)
**Add `srdConditionSchema = z.enum(SRD_CONDITIONS)` and hard-tighten the condition-name fields to it. Canonical casing is lowercase. Do NOT use a permanent normalizing shim — normalize the fixtures and any persisted dev rows instead.**

Rationale: the audit confirms the real write paths already emit lowercase; the only uppercase sources are some unit-test fixtures and the glossary *display* parser. A forever lowercase-transform on the input would just mask future drift. Hard-tighten + fix the fixtures is the cleaner end-state, and renormalizing persisted rows is safe **because this is a dev-seeded app with no production users** (`db:reset` reseeds) — so the leaf's "Sequencing risk" / "reject capitalized rows in a local DB" concern is trivial here, not a blocker.

Keep the glossary display-name (`parse-glossary-entry` → `"Blinded"`) distinct from the canonical lowercase key — they are deliberately different concerns and the display side is out of scope.

## Problem
`packages/shared/src/rules/conditions.ts` is the authoritative SRD-condition source: it defines the `SRD_CONDITIONS` tuple, the `SrdCondition` type, the full `CONDITION_DESCRIPTIONS` map, and the tick/incapacitation helpers — yet, unlike its sibling `damage-types.ts`, it never exports a `z.enum(SRD_CONDITIONS)`. As a result every schema field that names a condition is a bare free string (`character.ts:170`, `character-inputs.ts:298/308`, `encounter.ts:58`), so any string — including the wrong casing — validates and persists. A new developer reading `character-inputs.ts` cannot tell that `conditionName` is supposed to be one of 15 fixed lowercase tokens; the constraint lives only in `conditions.ts` runtime helpers with no schema link, and `homebrew.ts:179` already inlines `z.enum(SRD_CONDITIONS)` for `conditionImmunities`, proving the enum is wanted but was never factored into a reusable named schema. The drift is not theoretical: because `CONDITION_DESCRIPTIONS`, `hasCondition`, and `isIncapacitated` all key on the lowercase tuple, a capitalized value stored in the DB renders as a plain label with no description and is never matched by tick/incapacitation logic.

## Evidence
- `packages/shared/src/rules/conditions.ts:7-25` — `SRD_CONDITIONS` tuple (15 lowercase tokens) + `SrdCondition` type; the only validation surface is the runtime `isValidCondition` at :62-64. No `z.enum` is exported and `zod` is not even imported in this file.
- `packages/shared/src/rules/damage-types.ts:25` — the sibling rules module *does* export `export const damageTypeNameSchema = z.enum(DAMAGE_TYPES);` alongside its tuple/type/`isValid...` helper. Same shape, opposite treatment — the inconsistency is the onboarding tax.
- `packages/shared/src/schemas/character.ts:170` — `conditionName: z.string()` (no constraint) inside `characterConditionSchema`.
- `packages/shared/src/schemas/character-inputs.ts:298,308` — `conditionName: z.string().min(1)` in both `addCharacterConditionInputSchema` and `removeCharacterConditionInputSchema`; these are the tRPC mutation inputs, so the wire contract accepts any non-empty string.
- `packages/shared/src/schemas/encounter.ts:58` — `name: z.string().min(1)` in `conditionEntrySchema` (the encounter-participant condition); contrast the same file's damage fields at `homebrew.ts:176-178`, which use `damageTypeNameSchema`.
- `packages/shared/src/schemas/monster.ts:141` — `conditionImmunities: z.array(z.string())` — a free-string condition list, directly parallel to `homebrew.ts:179`'s `z.array(z.enum(SRD_CONDITIONS))` for the *same* concept. So one sibling entity schema (`monster`) leaves condition names un-validated while another (`homebrew`) uses the SRD tuple; `monster.ts` should be swapped to the new `srdConditionSchema` in step 2 alongside the others.
- `packages/shared/src/schemas/homebrew.ts:4,179` — imports `SRD_CONDITIONS` from `../rules/conditions.js` and inlines `z.array(z.enum(SRD_CONDITIONS))` for `conditionImmunities`; the enum is constructed ad-hoc at the call site instead of imported as a named schema.
- `packages/client/src/components/campaign/combat/condition-toggle-popover.tsx:48` — renders `CONDITION_DESCRIPTIONS[condition]` keyed off the lowercase tuple; a capitalized stored value has no description.
- `packages/client/src/components/campaign/combat/participant-stats.tsx:49-69` — renders `c.name` verbatim, so a capitalized `ConditionEntry.name` displays but bypasses every lowercase-keyed helper.
- Observable drift in the test corpus (both casings stored against the same fields): lowercase at `vault-access.test.ts:193`, `encounter-participants-add.test.ts:487`, `character-updated-broadcast.test.ts:143,160` (`conditionName: "poisoned"/"blinded"`); capitalized at `character-updates.test.ts:147,202` and `mutation-logging.test.ts:278` (`conditionName: "Poisoned"/"Stunned"`), `character-sheet.test.tsx:160` (`conditionName: "Poisoned"`), and `participant-stats.test.tsx:82-115` (`name: "Poisoned"/"Stunned"/"Blinded"/"Charmed"/"Frightened"`). `isValidCondition("Poisoned") === false`, so these capitalized values are exactly the ones that silently escape description/tick logic.

## Proposed direction
Fix shape only (do not implement here):
1. In `packages/shared/src/rules/conditions.ts`, add `import { z } from "zod";` and export a named `srdConditionSchema = z.enum(SRD_CONDITIONS)` next to the existing tuple/type — mirroring `damage-types.ts:25` exactly so the two rules modules read identically. (TDD: extend the existing `SRD_CONDITIONS` block in `packages/shared/src/rules/conditions.test.ts:21-53` with cases asserting `srdConditionSchema.parse("poisoned")` succeeds and `.safeParse("Poisoned")`/`"BLINDED"` fails — pinning the lowercase contract through the schema, not just the runtime helper.)
2. Follow the package-flow order shared -> server -> client. In `shared`, swap the bare condition-name fields to the new schema: `character.ts:170`, `character-inputs.ts:298/308`, `encounter.ts:58` (`conditionEntrySchema.name`), `monster.ts:141` (`conditionImmunities`), and replace the inline `z.enum(SRD_CONDITIONS)` at `homebrew.ts:179` with the named import for consistency. Each swap is a tightening, so add a `.safeParse` rejection case to the nearest existing schema test before the change.
3. Tightening the input schemas will surface the capitalized server/client test fixtures listed above as failures — that is the point. Decide the canonical casing (lowercase, per the tuple and `CONDITION_DESCRIPTIONS`) and normalize those fixtures (`character-updates.test.ts`, `mutation-logging.test.ts`, `character-sheet.test.tsx`, `participant-stats.test.tsx`) to lowercase as part of the change; if any production write path can emit capitalized values, normalize at that boundary too rather than loosening the schema. Cross-check the seed/glossary parser (`parse-glossary-entry.test.ts:45` produces `"Blinded"`) so display-name vs. canonical-key remain distinct concerns.
4. No new doc is required, but note the new `srdConditionSchema` export in `packages/shared/src/rules/` so the contract is discoverable next to `damageTypeNameSchema`.

## Scope / caveats
- This is a shared-contract consistency + correctness finding (a bare free-string field where a derived enum already exists and is used elsewhere), explicitly NOT a duplication or dead-code finding — those are owned by `docs/agent_notes/backlog/drift-ai-findings/` and are off-limits. The ad-hoc `z.enum(SRD_CONDITIONS)` at `homebrew.ts:179` is mentioned only as proof the enum is wanted; the fix factors a *new* exported schema rather than deleting a duplicate, and the core value is closing the validation gap, not removing repetition.
- Distinct from the out-of-scope backlog: it is not a lint-debt drain, dep bump, useEffect guardrail, UX/infra item, or test-tier plan.
- Do not change `SRD_CONDITIONS` casing, the `CONDITION_DESCRIPTIONS` keys, or the tick/duration helpers — they are the canonical source and are correct. Do not touch `packages/server/src/generated/prisma/**`.
- Sequencing risk: step 2 tightens tRPC mutation inputs and a persisted schema, so it can reject capitalized data already in a developer's local DB. Land the schema + tests together, audit any existing capitalized rows (seed/fixtures), and prefer boundary normalization over schema relaxation if real data is found.
