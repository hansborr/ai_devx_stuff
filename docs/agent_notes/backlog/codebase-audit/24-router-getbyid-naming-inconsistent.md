# 24. Single-entity routers disagree on "fetch one by id" naming (getById vs bare get), hurting cross-router predictability

Status: In progress — convention documented + callers migrated to bare `get` (batch 5a, 2026-06-14); `getById` retained as a temporary deprecated compat alias in `magic-item.ts`/`monster.ts`. Remaining: remove the alias in a future cleanup once no pre-rename client bundles remain.
Theme: tRPC procedure naming · Area: server · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: naming-consistency); evidence independently re-verified. · Confidence: high

## Decision (locked 2026-06-13)
**Standardize on bare `get`** (the current 4-of-6 plurality, reads cleanly as `trpc.<entity>.get`). Document it in `docs/guides/add-trpc-procedure.md` and explicitly exempt the legitimate multi-noun routers (`homebrew.getCollection`/`getEntry`, `srd.getSpecies`/`getClass`/`getSpell`) as a sanctioned exception. The doc addition is shippable on its own and stops further drift. Converge the two outliers (`magicItem.getById`, `monster.getById`) via **add-alias → migrate the 3 client callers → remove the old name** — never a hard rename in one commit.

## Problem
The repo has no shared convention for the single most common router operation — "fetch one entity by id" — so the same conceptual call appears under three different names depending on which router file you open. `magic-item.ts` and `monster.ts` expose `getById`; `map.ts`, `encounter.ts`, `character.ts`, and `campaign.ts` use a bare `get`; `homebrew.ts` uses `getCollection`/`getEntry` and `srd.ts` uses `getSpecies`/`getClass`/`getSpell`. A new developer cannot predict the procedure name from the entity — they must open each router to learn its dialect, and the tRPC guide (`docs/guides/add-trpc-procedure.md`) never states which form to pick, so each new router re-rolls the choice and the spread widens. The inconsistency is self-reinforcing: `srd.ts` builds its procedures from a factory literally named `srdGetByIdProcedure` yet exposes them as `getSpecies`/`getClass`/`getSpell`, so even the "getById" spelling and the "domain-noun" spelling coexist in one file.

## Evidence
- `packages/server/src/routers/magic-item.ts:120` (`const getById = publicProcedure`) and `:158` (exported in `magicItemRouter` as `getById`) — style A.
- `packages/server/src/routers/monster.ts:170` (`const getById = publicProcedure`) and `:205` (exported as `getById`) — style A.
- `packages/server/src/routers/character.ts:84` (`const get = protectedProcedure`) and `:177` (exported as `get` in `characterRouter`) — style B (bare `get`).
- `packages/server/src/routers/encounter.ts:212` (`get: protectedProcedure`), `packages/server/src/routers/map.ts:47` (`get: protectedProcedure`), `packages/server/src/routers/campaign.ts:145` (`get: protectedProcedure`) — style B.
- `packages/server/src/routers/homebrew.ts:257` (`getCollection: protectedProcedure`) and `:371` (`getEntry: protectedProcedure`) — style C (domain noun).
- `packages/server/src/routers/srd.ts:253,270,362` — `getSpecies`/`getClass`/`getSpell`, each built from `srdGetByIdProcedure({...})`; the factory itself is defined at `packages/server/src/utils/srd-query-helpers.ts:66` as `srdGetByIdProcedure` — so the "getById" name lives in the helper but never reaches the procedure surface.
- `docs/guides/add-trpc-procedure.md` (66 lines) — the canonical guide for adding a procedure; contains no fetch-one naming convention (no mention of `getById`, bare `get`, or "by id").
- `getById` is client-load-bearing, so the two `getById` routers cannot be silently renamed: `packages/client/src/components/compendium/magic-item-detail-dialog.tsx:93` (`trpc.magicItem.getById.queryOptions(...)`), `packages/client/src/components/campaign/npcs/monster-detail-dialog.tsx:230` (`trpc.monster.getById.queryOptions(...)`), and `packages/client/src/components/vtt/drawer/monster-stat-block-state.ts:86` (`trpc.monster.getById.queryOptions(...)`).

## Proposed direction
Decide one convention and write it down before changing any code; the fix is primarily a documented standard plus a small, deliberate rename, not a sweep.
1. **Pick the convention and document it.** Add a short "Fetching one entity by id" subsection to `docs/guides/add-trpc-procedure.md` naming the chosen form. Bare `get` is the current plurality (4 of 6 entity routers) and reads cleanly as `trpc.<entity>.get`, so it is the lower-churn target; `getById` is the more self-describing alternative. Either is defensible — the value is in choosing one and recording the rationale, including the carve-out for multi-noun routers (`homebrew`'s collection-vs-entry split and `srd`'s per-resource procedures are legitimately different operations and should be explicitly exempted, not forced into a single `get`).
2. **Converge the outliers behind a deprecation window.** Because `magicItem.getById` and `monster.getById` are consumed by three client call sites above, renaming to the chosen form (if `get` wins) must add the new procedure alias first, migrate the three client callers, then remove the old name — not a hard rename in one commit. If `getById` wins instead, rename the four bare `get` procedures (`character`, `encounter`, `map`, `campaign`) and update their (server-internal-first, then client) callers, following the package-flow order shared -> server -> client.
3. **TDD-aware.** Each affected router has existing procedure tests; extend the relevant router test (e.g. the `monster`/`magic-item` router integration tests for the alias-then-remove path, and the `character`/`encounter`/`map`/`campaign` router tests if those are the ones renamed) to assert the procedure resolves under the new name before deleting the old. The client query-options call sites are covered by their component/hook tests — update those alongside the rename. Follow `docs/guides/add-trpc-procedure.md` (the guide you are extending) for procedure wiring.

## Scope / caveats
- This is a **naming-consistency** finding about procedure surface names; it is explicitly **not** a duplication or dead-code finding (those are owned by `docs/agent_notes/backlog/drift-ai-findings/`) — every procedure cited is live and exercised; the issue is the divergent spelling of an identical operation, not redundant or unused code.
- Do **not** flatten the deliberately different operations: `homebrew.getCollection`/`getEntry` (two distinct fetch shapes) and `srd.getSpecies`/`getClass`/`getSpell` (per-resource SRD lookups) are correct as multi-noun procedures; the convention should sanction them as a named exception, not rename them to `get`.
- Sequence the `getById` -> `get` (or vice versa) migration as add-alias / migrate-callers / remove-old; a hard rename in a single commit would break the three client detail dialogs/state hooks. Treat the doc addition (step 1) as shippable on its own — it captures the decision and stops further drift even before any rename lands.
- Distinct from existing backlog: this is not a lint-debt drain, dependency bump, UX/infra item, or agent-harness ergonomics finding, and no current backlog leaf addresses tRPC procedure-name conventions.

## Implementation notes (batch 5a)
- Convention chosen and documented: bare `get`. The three client callers were migrated to `trpc.<entity>.get` and the canonical procedure on each router is `get`.
- Transitional state (current): `magicItem.getById` and `monster.getById` exist as **deprecated compat aliases** pointing at the same procedure as `get` (`getById: get` in each router object literal). This honors the prescribed add-alias → migrate-callers → (later) remove-old sequence — never a hard rename in one commit — so an already-loaded/cached client bundle built against `main` that still calls `getById` keeps resolving through any deploy window instead of getting procedure-not-found.
- An earlier batch-5a step (item history) had hard-removed the old `getById` names; that removal was reverted to this alias-retained state to restore the deprecation window.
- Tests: `magic-item.test.ts` and `monster.test.ts` each assert the `getById` alias resolves and returns a result identical to `get` for the same id.
- Follow-up cleanup (future leaf/commit): once no pre-rename client bundles remain in the wild, delete the `getById` alias and its alias-specific tests so only the canonical `get` surface remains.
