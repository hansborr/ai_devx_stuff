# 6. Client auth/session token lifecycle is undocumented: in-memory token store, two divergent refresh paths, multiple consumers

Status: Done — added `docs/guides/client-auth-session.md` (in-memory token, both refresh paths + singleflight, login/logout reset surface, full consumer/writer list) and cross-linked it from `docs/authorization.md`, `docs/socket-architecture.md` (near the handshake-token line), and `packages/client/src/hooks/MODULE.md`. Documentation-only, no behavior change; existing seams (`auth-context.test.tsx`, `token-store.test.ts`, `socket-context.test.tsx`) already pin every invariant the doc asserts (incl. map-canvas store reset on login/logout), so no new test was needed.
Theme: discoverability / onboarding · Area: client · Severity: medium · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: client-architecture); evidence independently re-verified. · Confidence: high

## Problem
The client session mechanism is spread across four files with **two distinct token-refresh implementations** and a module-global in-memory access token, and no doc describes the flow. `token-store.ts` holds the access token in a bare `let accessToken` (gone on hard reload). `auth-context.tsx` bootstraps the session on mount via the **tRPC `auth.refresh` mutation**; `trpc.ts` independently implements a **second** refresh via a raw `fetch("/trpc/auth.refresh")` behind a singleflight, wired into a silent `httpBatchLink` 401-retry interceptor. The same token is read for the Socket.io handshake (`socket-context.tsx`) and for raw image uploads (`use-map-image-upload.ts`), and is also written from `settings-page.tsx` after a password change. `docs/authorization.md` is server-only and never mentions the client, and `docs/socket-architecture.md` documents only the handshake *contract* (`socket.handshake.auth.token`), not where that token comes from. A newcomer cannot tell which refresh path runs when, why there are two, that login/logout also clear the query cache and reset two zustand stores, or that a hard reload silently relies on the mount-time refresh to re-bootstrap. That is exactly the kind of cross-file, implicit control flow that is expensive to reverse-engineer and dangerous to change blind.

## Evidence
- `packages/client/src/lib/token-store.ts:1-9` — the access token is a bare module-global `let accessToken: string | null = null` behind `get/setAccessToken`; non-persistent, so a hard reload starts with `null` and depends on the mount-time refresh below.
- `packages/client/src/hooks/auth-context.tsx:41-68` — `useRefreshOnMount` bootstraps the session on mount via the tRPC `auth.refresh` **mutation** (`refreshMutation.mutateAsync()`), then `setAccessToken` + `fetchCurrentUser`; guarded by a `didRefresh` ref because the first call rotates the refresh token.
- `packages/client/src/hooks/auth-context.tsx:19-23` — `clearUserScopedState` resets the TanStack Query cache plus two zustand stores (`useCombatStore.reset()`, `useMapCanvasStore.reset()`); called on both `login` (:84) and `logout` (:102), with `setAccessToken` adjusted alongside (:85, :103).
- `packages/client/src/lib/trpc.ts:14-44` — a **second, independent** refresh path: `refreshAccessToken` does a raw `fetch("/trpc/auth.refresh")` and writes the same store, fronted by a `getRefreshPromise` singleflight (`refreshPromise`).
- `packages/client/src/lib/trpc.ts:58-72` — silent 401-retry: the `httpBatchLink` custom `fetch` intercepts a 401, awaits the shared refresh, and retries once with the new `Authorization` header — entirely invisible to callers.
- `packages/client/src/hooks/socket-context.tsx:16,54,61` — the Socket.io provider reads the same in-memory token (once to gate connection, again inside the `auth` callback on every (re)connect); does **not** participate in either refresh path.
- `packages/client/src/hooks/use-map-image-upload.ts:5` and `packages/client/src/pages/settings-page.tsx:23` — additional consumers/writers of the store (raw upload reader; post-password-change writer) that a "two files" mental model misses.
- `docs/authorization.md:1-37` — server-only (auth helpers, error codes, note/NPC/homebrew visibility); zero client coverage. `docs/socket-architecture.md:22` documents only that "the client sends the access token in `socket.handshake.auth.token`," not its provenance. The hooks orientation doc `packages/client/src/hooks/MODULE.md` describes the socket lifecycle but never the token's source or the dual refresh.

## Proposed direction
Documentation-first; **do not refactor the auth flow as part of this leaf** (consolidating the two refresh paths is a separate, riskier change). Shape:
1. Add a short client-session doc — either a new `docs/guides/client-auth-session.md` (it is task-guide-shaped, like the other `docs/guides/*`) or a `MODULE.md` next to the token store / auth context — that maps: where the access token lives (in-memory, non-persistent) and why; the **mount-time bootstrap** refresh vs. the **401-interceptor** refresh, when each fires, and why both exist; the singleflight; and the full login/logout reset surface (query cache + the two zustand stores). List every consumer/writer found in Evidence so "where does the token come from / who resets it" is answerable in one place.
2. Add one cross-link line to `docs/authorization.md` ("client-side session/token handling: see <new doc>") and one to `docs/socket-architecture.md` near :22, so the server-side reader is pointed at the client provenance.
3. Optionally fold a one-line pointer into `packages/client/src/hooks/MODULE.md` under Data Flow / Gotchas.
4. TDD note: this is doc + cross-link work, so no behavior changes and no new runtime tests. The existing seams already pin the behavior the doc describes — `auth-context.test.tsx` (mount refresh + reset), `token-store.test.ts`, and `socket-context.test.tsx` (handshake token). If the doc asserts a specific invariant that lacks a test (e.g. "logout clears the map-canvas store"), add/extend the matching assertion in `auth-context.test.tsx` rather than inventing a new file.

## Scope / caveats
In scope: documenting and cross-linking the existing client session flow; touching only docs (plus an optional assertion in an existing test). Out of scope: unifying the two refresh implementations, adding token persistence, or changing 401/handshake behavior — those are behavioral changes that belong in their own leaf and would need the server auth contract reviewed first (package-flow `shared -> server -> client`). This is **not** a duplication or dead-code finding: the two refresh paths are genuinely different mechanisms (tRPC mutation vs. raw fetch interceptor) serving different triggers, and every cited symbol has live consumers — so it does not overlap the drift-ai near-duplicate/dead-code backlog. It is also distinct from the planned useEffect guardrails (no effect bug claimed here), the Storybook catalog, lint-debt/ratchet drains, and the UX/infra audits.
