# 23. Combatant/token "kind of thing" is discriminated by `type` in shared schemas but `kind` in the client drawer/token UI unions

Status: Done — implemented 2026-06-14 (batch 5a)
Theme: naming consistency at the shared->client seam · Area: cross-cutting · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: naming-consistency); evidence independently re-verified. · Confidence: high

## Decision (locked 2026-06-13)
**Rename the client `kind` discriminator to `type`** to match the shared contract (shared is the source of truth) — client-only, the smaller blast radius. Do NOT merge the three value sets (`npc`/`object` are genuinely different domains); the goal is a consistent discriminator *name* plus a documented, tested narrowing at the seam. Confirm no socket/tRPC payload serializes `kind` (it is in-client UI state, per the leaf) before renaming.

## Problem
The same domain question — "what kind of combatant/token is this?" — is answered by a field named `type` on the shared (contract) side of the boundary and `kind` on the client (drawer/menu) side, and the two even carry different value sets. A new developer who learns `participant.type === "monster"` from the shared schema then opens the VTT drawer store and finds `target.kind === "monster"`, and must discover that an explicit hand-written translation bridges the two. Worse, three overlapping-but-distinct string enums are in play: participant `type` is `character|monster|npc`, token `type` is `character|monster|object`, and the drawer/menu `kind` is only `character|monster` — so the reader cannot assume the discriminators are interchangeable, and the `npc`/`object` cases silently disappear at the seam. This raises time-to-understanding and the risk that someone "lines up" the unions incorrectly when adding a case.

## Evidence
- `packages/shared/src/schemas/encounter.ts:24,26,85` — `PARTICIPANT_TYPES = ["character","monster","npc"]`, `participantTypeSchema`, and `encounterParticipantSchema` discriminates with `type: participantTypeSchema`.
- `packages/shared/src/schemas/map.ts:37,39,71` — `TOKEN_TYPES = ["character","monster","object"]`, `tokenTypeSchema`, and `mapTokenSchema` discriminates with `type: tokenTypeSchema` (note: `object`, not `npc`).
- `packages/client/src/stores/vtt-drawer-store.ts:4-7` — `DrawerTarget` union discriminates with `kind` and only enumerates `character|monster` (no `npc`/`object`); set via `openCharacter`/`openMonster` (lines 54-79) which write `{ kind: "character", ... }` / `{ kind: "monster", ... }`.
- `packages/client/src/lib/drawer-perms.ts:43-56,68-86` — consumes the target via `target.kind === "character"` / `=== "monster"`. (Adds yet a third discriminator name: `DrawerAccess` at lines 18-20 uses `target: "character"|"monster"`.)
- `packages/client/src/components/vtt/in-vtt-drawer.tsx:31,73,97,116,139,162,195-196` — repeatedly branches on `target.kind`; line 116 cross-references `access.target !== target.kind`, mixing the `kind` and `target` discriminator names in one expression.
- `packages/client/src/components/campaign/tokens/token-context-menu.tsx:16-32` — `resolveOpenSheetIntent` reads `token.type === "character"` / `=== "monster"` (the shared `type`) and emits an `OpenSheetIntent` union keyed on `kind`; this is the explicit `type`->`kind` translation at the seam (the `object` token case falls through to `null`).

## Proposed direction
Pick one discriminator name and value-set convention for "kind of combatant/token" and align the client unions to the shared contract (package-flow order: shared is the source of truth, so prefer renaming the client `kind` -> `type` rather than the reverse, leaving the shared Zod schemas untouched). The smallest coherent change is client-only: rename the `DrawerTarget` discriminator from `kind` to `type` (and likewise the `OpenSheetIntent` union in `token-context-menu.tsx`), so `resolveOpenSheetIntent` becomes a straight value-set narrowing (`character|monster|object` -> `character|monster`) rather than a field rename plus narrowing — and add a short comment at that seam documenting why `object`/`npc` tokens map to "no drawer". Be TDD-aware: `packages/client/src/lib/drawer-perms.test.ts` and `packages/client/src/components/vtt/in-vtt-drawer.test.tsx` already exercise the discriminator and should be updated first (red) then made green by the rename; add a case asserting an `object`-type token yields a `null` open-sheet intent so the dropped case is pinned. Check `packages/client/src/components/campaign/tokens/` and any nearby `*MODULE.md` for orientation notes that name `kind`, and update them. Confirm there is no socket/tRPC payload that serializes `kind` (it is purely in-client UI state) before settling on the rename direction.

## Scope / caveats
This is a naming/discoverability finding, NOT a duplication or dead-code finding — both the `type` and `kind` unions are live and consumed; nothing is being deleted as unused, so it does not overlap the drift-ai-findings backlog (which owns near-duplicate and dead code). It is distinct from the lint-debt, useEffect-guardrail, Storybook-catalog, and UX/infra backlogs. Do not change the shared Zod schemas' `type` field or its values (that is a contract change with server and DB-projection blast radius — out of scope for an S rename); keep this client-side. Do not fold the three value sets together (`npc` and `object` are genuinely different domains — encounter participants vs. map tokens); the goal is a consistent discriminator *name* and a documented, tested narrowing at the seam, not a merged enum. If the team prefers the inverse (rename shared `type` -> `kind`), that is a larger, separately-sized change touching server projections and tests and should be its own leaf.
