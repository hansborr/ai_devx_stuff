# 29. Upload REST route uses a separate error convention (HTTP status + {error} body) from the repo-wide tRPC pattern, with no orientation note

Status: Done — signposted on feat/codebase-audit-batch4a-layering. Added file-header + load-bearing-try/catch comments to `routes/upload-routes.ts`, JSDoc on `saveMapImage` in `services/upload-service.ts`, a new `routes/MODULE.md` (indexed), and characterization tests: route maps a `saveMapImage` validation failure to HTTP 400 (not 500), and `saveMapImage` rejects with a plain `Error` (not `TRPCError`). No behavior change.
Theme: error-convention signposting · Area: server · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: error-observability); evidence independently re-verified. · Confidence: high

## Problem
Almost the entire server speaks tRPC `TRPCError` codes, but the single non-tRPC REST surface — `packages/server/src/routes/upload-routes.ts` — uses Fastify `reply.status(...).send({ error })` with hand-mapped HTTP constants, and its backing `upload-service.ts` throws plain `new Error(...)` (not `TRPCError`) for every validation failure. The route's final `try/catch` is the only thing that turns those raw service Errors into a deliberate HTTP 400; without it they would surface as opaque 500s. A newcomer touching uploads has no signpost that this path follows different error rules from the rest of the server, and the convention is implicit and easy to break (e.g. moving a validation check, or calling `saveMapImage` from a new caller without re-wrapping). The contrast is stark because `utils/dice-error-wrap.ts` documents the *exact same* non-`TRPCError` → `BAD_REQUEST` boundary in a doc comment, while the upload path has neither a comment nor a `routes/MODULE.md`.

## Evidence
- `packages/server/src/routes/upload-routes.ts:20-23` — local `HTTP_OK/HTTP_BAD_REQUEST/HTTP_UNAUTHORIZED/HTTP_FORBIDDEN` constants; this file invents its own status taxonomy rather than mapping from `TRPCError` codes like the rest of the server.
- `packages/server/src/routes/upload-routes.ts:80-95` — auth/validation failures are returned as `reply.status(HTTP_UNAUTHORIZED|HTTP_BAD_REQUEST|HTTP_FORBIDDEN).send({ error: ... })`; note `assertCampaignDm`'s thrown `TRPCError` is swallowed by a bare `catch {}` at :90-92 and remapped to a flat HTTP 403 + `{ error }`, discarding the structured code.
- `packages/server/src/routes/upload-routes.ts:97-103` — the success/catch block calls `saveMapImage`, then `catch (err)` downgrades the service's plain `Error.message` to HTTP 400; this `try/catch` is the sole guard preventing `saveMapImage`'s raw Errors from becoming 500s.
- `packages/server/src/services/upload-service.ts:95-107` — `saveMapImage` throws plain `new Error(...)` for file-type / size / empty / signature-mismatch validation (`:97,:100,:103,:106`), never `TRPCError`; nothing in the service signals it depends on a caller to translate these.
- `packages/server/src/utils/dice-error-wrap.ts:3-21` — the documented contrast: a doc comment explains it re-throws non-`TRPCError` failures as `BAD_REQUEST` "so callers never see a raw 500" and preserves structured `TRPCError`s; the upload path has no equivalent note. Confirmed in active use by `services/combat-actions/combat-actions.ts:58` and `services/spell-casting/spell-casting.ts:38`.
- `packages/server/src/routes/` — directory contains only `upload-routes.ts` and `upload-routes.test.ts`; no `MODULE.md`/`*-MODULE.md` orientation doc exists for the REST surface (verified). `registerUploadRoutes` is wired at `app.ts:196`; the only other Fastify route is the `/health` probe at `app.ts:209`, confirming uploads is the lone meaningful REST error surface.

## Proposed direction
Signpost the boundary; do not re-architect uploads onto tRPC (multipart streaming is the legitimate reason this is REST). Shape:
1. Add a short doc comment at the top of `routes/upload-routes.ts` (mirroring `dice-error-wrap.ts`'s wording) stating: this is the repo's one REST surface, it deliberately maps failures to HTTP status + `{ error }` rather than `TRPCError`, and the `saveMapImage` `try/catch` is load-bearing because the service throws plain `Error`. Cross-reference `docs/authorization.md` for the intentional 403-on-`assertCampaignDm` mapping.
2. Add a one-line JSDoc note on `saveMapImage` in `upload-service.ts:95` warning that it throws plain `Error` for validation (by design, so the REST route can map to 400) and that any new caller must wrap those — the same self-documentation `dice-error-wrap.ts` gives its callers.
3. Optionally add a tiny `packages/server/src/routes/MODULE.md` (2–4 lines) so the discoverability question "where do non-tRPC HTTP routes live and what error rules apply" has an answer, consistent with the repo's `MODULE-INDEX.md` convention.
4. TDD-aware: this is primarily documentation, but pin the load-bearing behavior so the signpost cannot rot. Extend `packages/server/src/routes/upload-routes.test.ts` to assert a `saveMapImage` validation failure surfaces as HTTP 400 with an `{ error }` body (not 500), and `packages/server/src/services/upload-service.test.ts` to assert `saveMapImage` rejects with a plain `Error` (documenting the contract the route relies on). Run `bun run test -- packages/server/src/routes/upload-routes.test.ts` and `bun run test -- packages/server/src/services/upload-service.test.ts`.

This is server-only; no `shared`/`client` changes, so package-flow ordering does not apply.

## Scope / caveats
- In scope as an error-observability / onboarding-discoverability finding: the issue is the *absence of a signpost* for a deliberately-different error convention, not a defect in the convention itself. The upload code works; a newcomer just has no warning it plays by different rules.
- Explicitly NOT a duplication or dead-code finding — `upload-routes.ts`/`upload-service.ts` are live (registered at `app.ts:196`) and the HTTP-constant block is not a duplicate of anything; those classes are owned by `drift-ai-findings/` and are not what this proposes.
- Distinct from existing backlog: not a UX/infra item (`production-readiness.md`, `ux-audit-*`), not a lint/dep/test-tier item, and not an agent-harness ergonomics item — it targets human onboarding to the server's error model.
- Do NOT convert uploads to tRPC or change the actual HTTP status mapping; behavior must stay identical. Keep the deliberate `NOT_FOUND`/auth mismatch semantics from `docs/authorization.md` intact when documenting the 403 remap. Low risk: the substantive change is comments plus characterization tests over already-passing behavior.
