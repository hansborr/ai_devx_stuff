# 37. Load-bearing 'fire-after-set' holder idiom repeats 4x in map-canvas-store but its TS-narrowing rationale is documented only once

Status: Done — implemented 2026-06-14 (batch 5a)
Theme: under-documented load-bearing idiom · Area: client · Severity: low · Size: XS

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: complexity-hotspots); evidence independently re-verified. · Confidence: high

## Problem
`map-canvas-store.ts` uses the same subtle idiom in four actions: declare a single-key holder object (`const pending = { onCancel: null }`), capture the consumer callback *inside* the Zustand `set` updater, then invoke `pending.onCancel?.()` **after** `set` returns. The object wrapper exists solely to defeat TypeScript control-flow narrowing (a plain `let x = null` would narrow to `null` across the closure boundary), and the rationale comment lives only on the first occurrence in `setActiveTool`. A new developer landing on `confirmTargetPick` or `cancelTargetPick` sees the bare pattern with no local explanation and must scroll ~250 lines back to learn why the wrapper is there. The trap is that the idiom is load-bearing in two independent ways at once — drop the object wrapper and it still compiles (until the callback line), and move the fire *inside* the `set` updater and it also compiles — but either change silently breaks fire-after-commit ordering, so a "simplification" looks safe and isn't.

## Evidence
- `packages/client/src/stores/map-canvas-store.ts:266-268` — the ONLY rationale comment ("Holder pattern: TS narrows `let x = null` to `null` across closure boundaries even with an explicit annotation, so capture the callback on an object the analyzer treats as opaque"), sitting on `setActiveTool`.
- `packages/client/src/stores/map-canvas-store.ts:269,476,521,537` — four near-identical holder declarations (`const pending: { onCancel: ... } = { onCancel: null }` at 269/476/537; the `confirmTargetPick` variant at 521 uses `onPick` instead). Only line 269 carries the comment; 476/521/537 are bare.
- `packages/client/src/stores/map-canvas-store.ts:294,510,534,550` — the deferred `pending.onCancel?.()` / `pending.onPick?.(tokenId)` calls fire AFTER `set` returns. Moving any of these inside the updater, or dropping the holder wrapper, compiles but breaks the intended "callback observes already-committed state" ordering.
- `packages/client/src/stores/map-canvas-store.ts:83-84` — `TargetPickCallback`/`TargetPickCancel` type aliases the holder annotates; confirms the wrapper is purely a narrowing workaround, not a behavioral type.
- `packages/client/src/stores/map-canvas-store.test.ts:378-392` — existing behavioral coverage ("does not fire onCancel for an in-flight target-pick session") asserts *whether* a callback fires, but no test pins the fire-AFTER-commit ordering (that the callback observes the post-`set` state), so a refactor that breaks ordering would pass the current suite.

## Proposed direction
Extract the idiom once and document it once, so each call site is self-explaining and the ordering contract is test-pinned:
1. Add a small local helper in `map-canvas-store.ts`, e.g. `withDeferredCallback`/`fireAfterCommit`, that owns the holder object and the post-`set` invocation, carrying the single narrowing-rationale comment in its body. Each of the four actions then reads as one intention-revealing call rather than a three-part hand-rolled pattern, removing the need to scroll back. (If a true shared helper feels like over-extraction for four sites, the minimal alternative is a one-line back-reference comment on lines 476/521/537 pointing at the line-269 explanation — lower payoff but still kills the scroll-back.)
2. TDD: before touching the code, add a test to `packages/client/src/stores/map-canvas-store.test.ts` that pins the load-bearing ordering for at least `confirmTargetPick`/`cancelTargetPick` — assert that the `onPick`/`onCancel` callback, when invoked, observes the *already-committed* store state (e.g. `activeTool` already restored to `previousTool`, `targetPick.active` already `false`). That regression test is what makes the refactor safe and documents the contract the comment currently only narrates. Run `bun run test -- packages/client/src/stores/map-canvas-store.test.ts`.
3. This is client-only; no shared/server contract is touched, so the shared->server->client package-flow order is not engaged. See `packages/client/src/components/campaign/maps/MODULE.md` for the surrounding map feature orientation if naming the helper to match local conventions.

## Scope / caveats
- Touch only `map-canvas-store.ts` and its sibling test; do not alter the four actions' externally observable behavior — the goal is to make the *same* fire-after-commit semantics legible and test-protected, not to change timing.
- This is explicitly NOT a duplication or dead-code finding: it is not proposing to dedupe the four blocks for size reduction (those belong to `drift-ai-findings/`), and the idiom is fully live. The finding is about an under-documented, easily-misread load-bearing pattern and the missing ordering test — a discoverability/maintainability concern for a new developer, distinct from the near-duplicate/dead-code work owned elsewhere.
- Distinct from existing backlog: not a useEffect guardrail, not a lint-debt drain, not a component-catalog or UX item. If step 1's helper extraction feels too large for XS, ship the step-2 ordering test plus step 1's comment-only fallback — that alone closes the onboarding gap at minimal risk.
- Risk note: the narrowing workaround is genuinely necessary; any helper must preserve the opaque-object capture (a generic that returns `T | null` could re-introduce the very narrowing the holder defeats), so verify the extracted helper still requires no `as`-cast at the four call sites.
