# 35. Five undocumented 100-char name-cap constants make it unclear whether per-domain name limits are intentional

Status: Done 2026-06-13. Encounter participant entity-vs-input split resolved: the file-private `MAX_PARTICIPANT_NAME_LENGTH` is gone; both the participant entity (`encounter.ts:92`, `MAX_NAME_LENGTH`) and the participant inputs (`encounter-inputs.ts`) now reference the shared `MAX_NAME_LENGTH`, with a one-field/one-constant comment. The map name, token label, and encounter name caps stay exported (client + map-inputs consume them by name) but are now domain-named aliases of the shared `MAX_NAME_LENGTH` with "shares the global name cap" comments instead of bare `100`. No bound changed (all were 100), so no persisted/seed/fixture data is affected; SRD seed data has no encounter/map/token entities. Added participant-name boundary tests asserting input and entity agree at the shared cap.
Theme: shared-contract clarity · Area: shared · Severity: low · Size: XS

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: shared-contracts); evidence independently re-verified. · Confidence: high

## Decision (locked 2026-06-13)
**Disambiguate intent; do not force-merge.** Two parts:
1. **Fix the encounter entity-vs-input split** (the concrete bug): the participant `name` entity cap (`encounter.ts:92`, shared `MAX_NAME_LENGTH`) and input cap (`encounter-inputs.ts:13` file-private `MAX_PARTICIPANT_NAME_LENGTH`) validate one field and must reference the same constant. Resolve it.
2. For map name / token label / encounter name, point them at the shared `MAX_NAME_LENGTH` with a one-line "shares the global name cap" comment unless a domain reason makes them independent. Keep `HOMEBREW_MAX_NAME_LENGTH = 200` as the precedent that divergence is allowed *when commented*.

## Problem
`constants.ts` exports a shared `MAX_NAME_LENGTH = 100` that the campaign, character, NPC, inventory, combat-roll, and encounter *entity* schemas all import and reuse. But the same 100-char cap is independently re-declared four more times under different names (`MAX_MAP_NAME_LENGTH`, `MAX_TOKEN_LABEL_LENGTH`, `MAX_ENCOUNTER_NAME_LENGTH`, and a file-private `MAX_PARTICIPANT_NAME_LENGTH`), with no comment indicating whether the divergence from the shared constant is an intentional per-domain knob or an accidental copy. Because the same file already proves a per-domain cap *can* be deliberate (`HOMEBREW_MAX_NAME_LENGTH = 200`), a newcomer touching the map/encounter contracts cannot tell which constant is the source of truth for "name length" or whether changing one should change the others. The encounter domain is internally self-contradictory: the participant **entity** schema caps `name` with the shared `MAX_NAME_LENGTH`, while the participant **input** schemas cap the very same concept with the local `MAX_PARTICIPANT_NAME_LENGTH` — two constants for one field, a textbook "where does the real limit live?" trap that slows safe change.

## Evidence
- `packages/shared/src/constants.ts:33` — `export const MAX_NAME_LENGTH = 100;` (the shared cap). Imported and reused for `name` fields across `campaign-inputs.ts:17,55`, `character-inputs.ts:30,120`, `npc-inputs.ts:16,35`, `inventory-inputs.ts:23,63,101`, `attack-roll-inputs.ts:49`, `spell-action-inputs.ts:37`.
- `packages/shared/src/schemas/map.ts:9-10` — `MAX_MAP_NAME_LENGTH = 100` and `MAX_TOKEN_LABEL_LENGTH = 100`, two independent 100 re-declarations (consumed at `map-inputs.ts:47,71,116,133` and the client map/token dialogs).
- `packages/shared/src/schemas/encounter.ts:11` — `export const MAX_ENCOUNTER_NAME_LENGTH = 100;`, a third re-declaration, while the *same file* imports `MAX_NAME_LENGTH` (`encounter.ts:3`) and uses it for the participant entity `name` at `encounter.ts:92`.
- `packages/shared/src/schemas/encounter-inputs.ts:13` — file-private `const MAX_PARTICIPANT_NAME_LENGTH = 100;` (no comment, see lines 12-16 — sits between two other bare numeric consts). It caps participant `name` input at `encounter-inputs.ts:85,206`, i.e. the *same* concept the entity caps with the shared `MAX_NAME_LENGTH` — one field, two constants.
- `packages/shared/src/schemas/homebrew.ts:36` — `export const HOMEBREW_MAX_NAME_LENGTH = 200;` carries the comment "Shared length limits for homebrew collection/entry names and descriptions." This deliberate, commented per-domain cap is what makes the four un-commented 100 siblings ambiguous: a reader cannot distinguish intent from accident.

## Proposed direction
Fix is documentation/intent-disambiguation, not a forced merge — do not blindly collapse all five into one constant (that would erase the legitimate per-domain knob that `HOMEBREW_MAX_NAME_LENGTH` establishes). Shape:
1. Decide, per domain, whether each 100-cap is intentionally independent. For any that are genuinely "same contract as the shared name cap," re-export/import `MAX_NAME_LENGTH` (or alias it locally with a one-line comment, e.g. `// map names share the global name cap`) instead of a bare `100`. For any that are deliberately distinct knobs, add a short rationale comment mirroring the `homebrew.ts:36` precedent so intent is explicit.
2. Resolve the encounter entity-vs-input split: the participant entity (`encounter.ts:92`) and participant input (`encounter-inputs.ts:85,206`) must reference the *same* constant, since they validate one field; pick one and comment why.
3. TDD-aware: the cap behavior is already pinned by `map-inputs.test.ts:106,114,116,387` (uses `MAX_MAP_NAME_LENGTH`/`MAX_TOKEN_LABEL_LENGTH`). If a domain is re-pointed at the shared constant, keep those tests referencing the chosen exported constant (not a literal `100`) so the boundary value stays asserted; add an analogous boundary test for the encounter participant-name path if one is missing, asserting entity and input agree.
4. Package-flow order: this is shared-contract-only (`packages/shared`); the client map/token dialogs already import the map constants by name, so no client edit is needed beyond following the import if a constant is renamed. No server changes. See `packages/shared/src/schemas/` conventions and the "Shared Zod schemas are the contract; derive types from them" rule in AGENTS.md.

## Scope / caveats
This is a clarity/intent finding about whether near-identical *constants* are deliberate, plus one concrete internal inconsistency (entity vs. input cap for the encounter participant `name`). It is explicitly NOT a duplication/dead-code finding (those are owned by `docs/agent_notes/backlog/drift-ai-findings/`): the deliverable here is documenting/clarifying intent and removing a footgun for newcomers, not deleting a duplicate code block — and the recommendation deliberately preserves per-domain caps where intentional rather than deduplicating them away. It is distinct from existing backlog items (no lint-debt, dep-bump, UX, or harness-ergonomics overlap). Risk is minimal (XS): if any cap is re-pointed at the shared constant, the only behavioral change would be if a domain's intended limit truly differs from 100 today — which is exactly the ambiguity this finding exists to force a decision on; resolve it as a documented choice rather than an accidental edit. Do not touch `HOMEBREW_MAX_NAME_LENGTH` (200) or `MAX_TEXT_LENGTH`/`MAX_DESCRIPTION_LENGTH` (5000) — those are clearly intentional and out of scope.
