# 38. confirm-cast-strip unwind() triggers cleanup via setActiveTool('select') side effects instead of the named cancelTargetPick action

Status: Done — implemented 2026-06-14 (batch 5a)
Theme: implicit cross-store coupling · Area: client · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: complexity-hotspots); evidence independently re-verified. · Confidence: high

## Problem
Cancelling or confirming a spell cast threads through three modules whose connection is invisible until you read all three. `confirm-cast-strip.tsx`'s `unwind()` calls `useMapCanvasStore.getState().setActiveTool("select")` *for its side effects* — clearing any active template AND firing target-pick's `onCancel` — then separately calls `useVttDrawerStore.getState().expand()`. The store already exposes a named `cancelTargetPick` action with the same `onCancel`-firing semantics, and it is a live action (used by `tool-handlers.ts:292`), but the strip bypasses it. A new developer tracing "what does Cancel do?" must hold `confirm-cast-strip`, `map-canvas-store`, and `vtt-drawer-store` in their head simultaneously, and the only signal that `setActiveTool` is being called for behaviour rather than to literally pick the select tool is a hand-written comment. That comment is load-bearing knowledge that is one refactor away from going stale.

## Evidence
- `packages/client/src/components/vtt/drawer/confirm-cast-strip.tsx:202-210` — `unwind()` calls `setActiveTool("select")` purely for its template-clear + onCancel side effects, then `expand()`; the 203-207 comment explicitly documents the implicit coupling ("setActiveTool('select') handles in-place cleanup… fires its onCancel callback").
- `packages/client/src/components/vtt/drawer/confirm-cast-strip.tsx:136-139,148-150` — both the Cancel button (`handleCancel`) and the Confirm success path route through this same `unwind()`, so the coupling governs every exit from the strip.
- `packages/client/src/stores/map-canvas-store.ts:265-294` — `setActiveTool`'s documented side effects that `unwind` relies on: it captures `targetPick.onCancel` (273-275), resets template/measurement/fog/drawing/selection state (277-288), and fires `pending.onCancel?.()` after the set (294).
- `packages/client/src/stores/map-canvas-store.ts:155,536-551` — a named `cancelTargetPick` action already exists with the same onCancel-firing shape (`pending.onCancel = s.targetPick.onCancel` at 541, `pending.onCancel?.()` at 550) and is used elsewhere (`hooks/canvas-input/tool-handlers.ts:292`), but the strip does not call it.
- `packages/client/src/stores/map-canvas-store.ts:540,543` — note the behavioural delta: `cancelTargetPick` is a guarded no-op when no session is active (`if (!s.targetPick.active) return s;`) and restores `targetPick.previousTool` rather than forcing `"select"`, and it does NOT clear template state. So it is not a literal drop-in — `unwind`'s template-clear case (post-placement / no-op cancel) still needs explicit handling.
- `packages/client/src/components/vtt/drawer/confirm-cast-strip.test.tsx:242-291` — existing tests pin the current unwind behaviour for both Cancel, Escape, and Confirm-success paths (each pre-seeds a `template-*` tool then asserts the strip unwinds).
- `packages/client/src/stores/map-canvas-store.test.ts:526-565` — `cancelTargetPick` and `setActiveTool` already have characterization tests (onCancel firing, previousTool restore, no-op-when-inactive), which a refactor can lean on.

## Proposed direction
Fix the *expression* of the cancel, not the behaviour. The honest shape is to make the strip's intent explicit so the side-effect comment stops being the only documentation. Two viable shapes, smallest first:
1. Give the strip a single intention-named helper. Either add a thin `cancelCast()`/`unwindCast()` to the map-canvas store that composes the template-clear + target-pick cancel under one named action (so `unwind()` reads `cancelCast(); expand()`), or, if a store action is overkill, keep `unwind()` but split its two concerns into two named local calls that each say what they mean — `clearTemplate()` (already exists at `map-canvas-store.ts:149`) plus `cancelTargetPick()` — rather than relying on `setActiveTool("select")` to do both implicitly. Preserve the exact current behaviour: template state must be cleared even when target-pick was never active (the case the comment calls out), and the active tool must end at `"select"`.
2. Whichever shape, keep `expand()` as the explicit `vtt-drawer-store` step; the cross-store sequencing is real and should stay visible.

TDD: the existing `confirm-cast-strip.test.tsx:242-291` cases (Cancel, Escape, Confirm-success) are the regression net — they should pass unchanged. Add one assertion that the target-pick `onCancel` still fires on Cancel when a single-target pick is live (mirroring `map-canvas-store.test.ts:526` semantics) so the refactor cannot silently drop the onCancel side effect. This is client-only (no shared/server contract change), so it does not perturb the shared->server->client flow. Read `packages/client/src/components/vtt/drawer/MODULE.md` (the strip's "Data Flow" section already names the cast-rail/strip ↔ `useMapCanvasStore`/`useVttDrawerStore` orchestration) and `docs/guides/client-effects.md` before touching the `useUnwindOnEscape` effect at `confirm-cast-strip.tsx:212-222` (leave that effect as-is; it is legitimate external-keydown sync).

## Scope / caveats
This is a clarity/discoverability finding, NOT a duplication or dead-code finding — `cancelTargetPick` is live (called from `tool-handlers.ts:292`) and `setActiveTool` is heavily used; nothing here is unused or a near-duplicate, so it is outside the drift-ai-findings remit. It is distinct from the useEffect-guardrails program (the Escape effect is correct and untouched), from any lint-debt/ratchet leaf, and from the storybook/UX/infra backlogs. Do NOT change observable behaviour: `cancelTargetPick`'s guarded-no-op + `previousTool` restore is intentionally narrower than `unwind`'s force-to-`"select"` + template-clear, so a naive swap would regress the post-template-placement cancel path — preserve the template-clear-when-target-pick-inactive case. Keep the change inside the strip plus, if taken, one new composed store action; do not refactor `setActiveTool` or the target-pick action family themselves. Low severity: the current code is correct and tested; the cost is purely time-to-understanding for someone new to the VTT cast flow.
