# 10. Zustand stores/ directory has no MODULE.md despite owning the densest, highest-fan-out client VTT state

Status: Done — added `packages/client/src/stores/MODULE.md` (orientation doc: per-store slice ownership, the Zustand-vs-TanStack-Query boundary by reference to architecture decision #16, and the shared reset contract across `combat-map-content.tsx` + `auth-context.tsx`), cross-linked to the vtt/drawer, canvas-input, and maps MODULE.md docs, and registered it via `bun run module:index`. Docs-only; no runtime changes.
Theme: missing orientation doc for the highest-fan-out client state surface · Area: client · Severity: medium · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: docs-coverage); evidence independently re-verified. · Confidence: high

## Problem
`packages/client/src/stores/` holds the three live Zustand stores that drive the VTT — `map-canvas-store.ts` (577 lines, the single densest non-generated client source file), `vtt-drawer-store.ts` (138), and `combat-store.ts` (56) — imported by 20 / 14 / 5 non-test client files across hooks, components, and `auth-context`. The directory has no `MODULE.md` and none of the three files carries an orientation header (each opens straight into `import { create } from "zustand"`), even though `docs/module-docs.md` requires a module doc precisely for surfaces that "own … store writes, or cross-module contracts." All three stores are live simultaneously on the combat-map surface and are reset together by hand in one effect, yet the only store-ownership prose a newcomer can find lives *inside* the feature docs (`vtt/drawer`, `canvas-input`, `maps`) that point *at* these stores — so a first-time contributor landing in `stores/` has nothing explaining what each store owns, why they are three separate stores, or where the boundary with the TanStack Query cache (architecture decision #16) falls. That is concretely expensive: changing store shape or the reset contract means reverse-engineering 21 importers and three feature docs to reconstruct an invariant that is documented nowhere central.

## Evidence
- `packages/client/src/stores/` — 3 live Zustand stores and **no** `MODULE.md`: `map-canvas-store.ts` (577 lines), `vtt-drawer-store.ts` (138), `combat-store.ts` (56); confirmed by directory listing and `wc -l`. By contrast 28 `MODULE.md` files exist deeper in `client/src` (e.g. `components/vtt/drawer/MODULE.md`, `hooks/canvas-input/MODULE.md`, `components/campaign/maps/MODULE.md`) — none in `stores/`.
- `packages/client/src/stores/map-canvas-store.ts:1-11`, `vtt-drawer-store.ts:1-9`, `combat-store.ts:1-8` — each file opens directly into imports/constants/types; no top-of-file orientation comment on any of the three.
- Import fan-out (excl. self, tests, and `*.test-helper.*`): `map-canvas-store` 20, `vtt-drawer-store` 14, `combat-store` 5 — spanning `components/campaign/{maps,combat,tokens,encounters}`, `components/vtt/**`, `hooks/{canvas-input,vtt-drawer}`, and `hooks/auth-context.tsx`. (Counting test-helpers too raises these to 21 / 14 / 6; the non-test figures are the relevant fan-out.)
- `packages/client/src/hooks/auth-context.tsx:16-17,19-23` — imports both `useCombatStore` and `useMapCanvasStore` and resets them in `clearUserScopedState` on logout; the cross-store "user-scoped state to clear" contract lives inline here, undocumented.
- `packages/client/src/components/campaign/combat/combat-map-content.tsx:80-87` — `resetTransient` (map canvas), `resetDrawer` (vtt drawer), and `resetCombat` (combat) are all reset together in one `useEffect` keyed on `map.id`/`encounter.id`, with no doc stating that these three stores share a reset boundary.
- `packages/client/src/stores/map-canvas-store.ts` is the densest non-generated, non-test client source file at 577 lines (the only larger client files are test infra: `test/mock-trpc.tsx`, `test/fixtures-*`).
- `docs/module-docs.md:22-34` — "Where Required" mandates a `MODULE.md` for surfaces that "own transactions, cache writes, socket invalidation, optimistic updates, **store writes, or cross-module contracts**" (line 29); the required sections include a **State Ownership** section. The `stores/` directory satisfies this trigger and has no doc.
- `docs/architecture-plan.md:95-96` — decision #16 "Zustand is only for ephemeral client state — TanStack Query owns server state"; this is the boundary a store doc should restate, currently findable only by reading the architecture plan.
- Sibling docs point inward with nothing to land on: `components/vtt/drawer/MODULE.md:86-88` states `stores/vtt-drawer-store.ts` "owns drawer open/close state, `mode`, …" and `stores/map-canvas-store.ts` "owns map tool state"; `hooks/canvas-input/MODULE.md:17,49` documents writing `useMapCanvasStore` slices "from outside"; `components/campaign/maps/MODULE.md:54-57` describes narrow canvas-store slices — store ownership prose is scattered across feature docs, none of it at the store.

## Proposed direction
Add a single `packages/client/src/stores/MODULE.md` following the charter in `docs/module-docs.md` (Purpose / Data Flow / External Entry Points / State Ownership / Test Seams / Gotchas), plus an optional `Concepts:` breadcrumb line. The doc should: (1) name each of the three stores and the one-line slice each owns (consolidating the prose currently scattered across the vtt/drawer, canvas-input, and maps MODULE.md docs — link to them rather than duplicate detail); (2) state the Zustand-vs-TanStack-Query boundary by reference to architecture decision #16 (`docs/architecture-plan.md:95-96`) so a newcomer learns where new state should live; (3) document the shared reset contract — that `combat-map-content.tsx:80-87` resets all three together per map/encounter and `auth-context.tsx:19-23` clears the user-scoped pair on logout — since this is the cross-store invariant most likely to be accidentally broken. Consider a short top-of-file `// orientation:` comment on `map-canvas-store.ts` only if the MODULE.md is judged insufficient for the densest file; the doc is the primary fix. This is docs-only and client-local, so no package-flow (shared->server->client) sequencing applies. TDD note: there is no behavior change to unit-test; the enforceable check is discoverability — run `bun run module:index` after adding the doc so the new `MODULE.md` is registered in the root `MODULE-INDEX.md` (per `docs/module-docs.md:55-59`), and confirm `module:index` is clean. If a module-doc freshness/coverage gate exists, ensure the new doc satisfies it.

## Scope / caveats
Scope is exactly one new orientation doc (and at most a brief in-file header), and the optional `module:index` regen — touch no store logic, no importers, and no existing feature MODULE.md beyond adding cross-links. This is a docs-coverage finding, **not** a duplication or dead-code finding: every store, every importer, and every reset call cited is live and exercised, so it does not overlap the drift-ai-findings backlog (which owns near-duplicate and dead/unused code). It is distinct from the agent-friction-2026-06 pack (that pack targets AI-harness ergonomics; this is human-onboarding orientation), from the planned Storybook component catalog (that covers `components/ui/` primitives, not stores), and from the useEffect-guardrail program (the `combat-map-content.tsx` effect is cited as evidence of an undocumented contract, not proposed as an effect bug). Risk is minimal; the only sequencing note is to keep the doc as cross-links to the existing vtt/drawer, canvas-input, and maps docs rather than re-stating their detail, so the store doc does not itself become a denormalized cache that drifts.
