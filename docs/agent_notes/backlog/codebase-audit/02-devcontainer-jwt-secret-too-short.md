# 2. Devcontainer `.env.example` ships a 31-char `JWT_SECRET` below the enforced 32-char minimum, crashing the server on first boot if copied unedited

Status: Done — 2026-06-13. Lengthened `.devcontainer/.env.example` JWT_SECRET to a 38-char dev placeholder (passes the 32-char refine), clarified `.devcontainer/README.md` quick-start, exported `MIN_JWT_SECRET_LENGTH` from `env.ts` (constant export only — enforcement unchanged), and added a scripts-project guard test (`scripts/devcontainer-env-example.test.ts`) asserting the template secret length >= `MIN_JWT_SECRET_LENGTH`.
Theme: first-boot env footgun · Area: tooling · Severity: medium · Size: XS

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: onboarding-setup); evidence independently re-verified. · Confidence: high

## Problem
The devcontainer template `JWT_SECRET` is exactly 31 characters, one short of the 32-character minimum the server enforces at import time. A new developer who follows the documented quick-start — copy `.env.example` to `.env`, edit only `PROJECT_NAME` and `POSTGRES_PASSWORD` "at minimum", trust that the env is "fully ready once the container starts" — gets a server that throws on boot because `loadServerEnv()` runs eagerly at module load. The failure is a Zod validation error (`JWT_SECRET: must be at least 32 characters`) buried in the dev-servers log, not an obvious "you need to edit this" prompt, so the very first impression of the project is an unexplained crash whose root cause is two files away from where the developer was told to look. This costs a new developer their first hour debugging a self-inflicted, fully avoidable trap that the template itself sets.

## Evidence
- `.devcontainer/.env.example:25` — `JWT_SECRET=changeme-generate-a-real-secret`; the value `changeme-generate-a-real-secret` is exactly 31 characters (verified `printf '%s' '…' | wc -c` = 31), i.e. one below the minimum.
- `packages/server/src/config/env.ts:8` — `const MIN_JWT_SECRET_LENGTH = 32;`.
- `packages/server/src/config/env.ts:98-101` — `JWT_SECRET: requiredStringSchema.refine((value) => value.length >= MIN_JWT_SECRET_LENGTH, \`must be at least ${…} characters\`)`; a 31-char value fails this refine.
- `packages/server/src/config/env.ts:172-176` — `loadServerEnv()` calls `safeParse` and `throw new Error("Invalid server environment:\n…")` on failure.
- `packages/server/src/config/env.ts:178` — `export const serverEnv = loadServerEnv();` runs at import, so a short secret throws the moment the module is loaded (on boot), not lazily.
- `.devcontainer/README.md:12` — quick-start says `# Edit .devcontainer/.env — set PROJECT_NAME, POSTGRES_PASSWORD at minimum`, which omits `JWT_SECRET` from the things a user is told they must change.
- `.devcontainer/README.md:19` — `so the environment should be fully ready once the container starts.` — the doc affirmatively promises a working boot.
- `.devcontainer/.env.example:24` — the section comment `# --- Auth (generate with: openssl rand -base64 48) ---` tells the user how to make a good secret but does not say the shipped placeholder is itself invalid.

## Proposed direction
Fix shape only — do not implement here. The cheapest correct fix is to make the shipped placeholder a value that *passes* the 32-char refine (so an unedited copy boots) while remaining obviously a placeholder — e.g. lengthen `changeme-generate-a-real-secret` to ≥32 chars in `.devcontainer/.env.example:25`. Note `env.ts:15-18` blocks two specific checked-in secrets only under `NODE_ENV=production`, so a passing dev placeholder stays safe for the devcontainer's development default.

TDD-aware: `env.ts` already has a test surface for the env schema; add a guard that closes the loop between the template and the enforced minimum so the two can never silently diverge again — a script test (scripts project) that reads `.devcontainer/.env.example`, extracts `JWT_SECRET`, and asserts `value.length >= 32` (importing or mirroring `MIN_JWT_SECRET_LENGTH` from `packages/server/src/config/env.ts` rather than hardcoding `32`). Run it with `bun run test:scripts:file -- <the new test>`. Pair the value fix with a one-line README correction at `.devcontainer/README.md:12` so the "at minimum" list either includes `JWT_SECRET` or the doc states the shipped secret is dev-ready as-is. Package-flow order is not a factor (this is `.devcontainer/` + a scripts-project test only); no `shared`/`server`/`client` source changes are required.

## Scope / caveats
Touch only `.devcontainer/.env.example`, optionally `.devcontainer/README.md`, and add one scripts-project guard test. Do NOT alter `packages/server/src/config/env.ts` enforcement — the 32-char minimum is correct and intentional; the defect is the template undershooting it, not the rule. Do NOT weaken or remove the eager `serverEnv = loadServerEnv()` boot-time validation (fail-fast on bad env is desirable). Do NOT touch the production-only `UNSAFE_PRODUCTION_JWT_SECRETS` set or its superRefine. This is a concrete, verified config/onboarding bug (a value one char below an enforced bound that breaks first boot), not a duplication or dead-code finding (those are owned by `drift-ai-findings/`), and it is distinct from the planned dependency upgrades, lint-debt drains, UX/infra audits, and agent-harness ergonomics items. A grep of the existing backlog found no leaf citing `JWT_SECRET` length or the `.env.example` placeholder, so it is not a re-file. Low risk: the change is data + docs + one assertion, with no behavioral effect on a correctly-configured environment.
