# 21. No human command-tiering: README documents 8 of 94 root scripts, doctor diagnostic and single-test commands are invisible

Status: Proposed — codebase maintainability/onboarding audit 2026-06-13. Not yet started.
Theme: command discoverability · Area: docs · Severity: low · Size: S

Source: codebase maintainability/onboarding audit 2026-06-13 (lens: tooling-newcomer-clarity); evidence independently re-verified. · Confidence: high

## Problem
`package.json` exposes **94** root scripts spanning eight families (test/verify/lint/worktree/docs/codemod/harness/db), but `README.md` documents exactly **8** of them and `AGENTS.md` names ~6 "non-obvious" ones — so a newcomer who runs `bun run` to learn the project sees the full 94-line wall with **zero signal** about which are daily drivers versus specialist/CI machinery. Three high-value newcomer tools are buried entirely: `bun run doctor` is a polished read-only setup diagnostic that streams `PASS`/`WARN`/`FAIL` lines with exact remediation commands, yet it appears nowhere a human looks (not README, not AGENTS); the single-file-test commands carry a sharp trap (`bun run test:scripts -- <file>` hard-rejects file args with exit 2, and `--filter @musi/scripts` can never work because `scripts` is not a workspace package) that is documented only in one dense AGENTS prose bullet, not in the README Scripts table. This directly taxes a first-time developer: they cannot tell the everyday surface from CI plumbing, the one command built to debug a broken local setup is undiscoverable, and the obvious-looking way to run a single script test silently fails.

## Evidence
- `package.json:17-111` — 94 root `scripts` entries across test/verify/lint/worktree/docs/codemod/harness families; grep for `everyday`/`specialist`/`tier`/`daily driver` across `README.md`, `AGENTS.md`, and `package.json` returns zero hits (only the unrelated `prettier`/`format` substring matches).
- `README.md:45-54` — the Scripts table lists exactly 8 commands (`dev`, `build`, `test`, `test:changed`, `lint`, `lint:changed`, `typecheck`, `e2e`); no grouping or "start here" cue beyond it.
- `AGENTS.md:12-18` — the "Non-obvious ones" list under `## Commands` names ~6 script families (`verify:changed`, `db:migrate`/`prisma:generate`, `db:{push,seed,reset,studio}`, `code:intel`, `test:scripts:file`); it is explicitly agent-facing prose, not the README humans read.
- `package.json:79` + `scripts/doctor.sh:1-15,444` — `bun run doctor` is a read-only aggregated diagnostic ("Read-only — never mutates state. Emits PASS/WARN/FAIL lines with exact follow-up commands"; e.g. `note_fail "missing $root_env — run 'bun run worktree:init' to provision this worktree"` at :444). `grep -in doctor README.md AGENTS.md` returns no matches — the single best "is my setup OK?" tool is undocumented for humans.
- `scripts/test-scripts.sh:38-47` — `test:scripts` rejects any non-`--changed` argument with `printf 'test:scripts: unknown argument...'` + `exit 2`, so `bun run test:scripts -- <file>` fails; the working single-file command (`test:scripts:file`, `package.json:46`) is named only in the AGENTS bullet above, and `grep -in 'test:scripts' README.md` returns no matches.
- `docs/generated/harness-controls.md:3,6` — the only inventory that *groups* the script/harness surface is generated and "agent-facing", grouped by `kind` (lint-rule, ratchet, sensor, ...) for diagnostic navigation, not by human task — so there is no human-tasked map of the 94 scripts anywhere.

## Proposed direction
Documentation-shape change only; no script behavior changes. (1) Restructure the `README.md` Scripts section (lines 43-56) into two short tiers: an **Everyday** table (dev, verify:changed, test/test:changed, lint:changed, typecheck, e2e, **doctor**) and a one-line "specialist / CI tooling — run `bun run` to list all 94" pointer, so the daily surface is obvious and the long tail is acknowledged rather than dumped. (2) Add a `doctor` row to the Everyday table and a one-liner in the Quickstart (README.md:17-41) — "if setup misbehaves, run `bun run doctor` for a read-only PASS/WARN/FAIL report with fixes." (3) Promote the single-test guidance into the README table with the exact trap inline (`test:scripts:file` for a script test, `test -- <file>` for any project; **not** `test:scripts -- <file>`), mirroring the AGENTS.md:18 wording so the two stay consistent. TDD-aware: the README is prose with no test, but `bun run docs:harness-controls:check` (`package.json:81`) and `module:index:check` (`:96`) are the existing doc-freshness gates — confirm this edit does not touch a generated region either guards (it does not; README and harness-controls.md are separate). If a reviewer wants drift protection for the new tier, the lighter-weight option is a follow-up assertion that every command named in the README Everyday table exists as a `package.json` script key — but keep that out of this leaf's scope. No package-flow ordering applies (docs-only).

## Scope / caveats
Touch only `README.md` (and optionally one Quickstart line); do **not** edit `package.json` scripts, `scripts/doctor.sh`, `scripts/test-scripts.sh`, or the generated `docs/generated/harness-controls.md`. This is a **discoverability/onboarding** finding about where human-facing command docs live and how they are tiered — it is explicitly **not** a duplication or dead-code finding (those are owned by `docs/agent_notes/backlog/drift-ai-findings/`), and it is not harness-for-agents ergonomics (owned by `agent-friction-2026-06/`): the angle here is the *human* newcomer reading README, not agent test ergonomics or coverage-map governance. It does not overlap the storybook component-catalog, lint-debt-drain, dep-bump, or UX/infra backlog items. Risk is minimal (prose only). Sequencing: independent — no `dependsOn`. Caveat: keep the tier curated and short; do not attempt to document all 94 scripts (that recreates the wall this leaf is trying to remove) — the point is signal, not completeness.
