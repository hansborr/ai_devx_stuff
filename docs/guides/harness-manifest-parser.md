# Reading harness.controls.json

`harness.controls.json` is the harness's registration manifest. Three modules
own the seam that reads it, and `harness:check` enforces which files may import
which. If you hit a tripwire failure mentioning `MANIFEST_DIRECT_READERS`, this
page is the answer.

## The three modules

| Module | Owns | May import |
|---|---|---|
| `scripts/harness/harness-manifest.ts` | Path, IO, and include assembly. `harnessManifestPath`, `readHarnessManifest`, `loadHarnessManifest`. No shape opinion. | Node builtins plus the dependency-free guards in `scripts/lib/records.ts` |
| `scripts/harness/harness-manifest-schema.ts` | Shape. The Zod contract, `parseHarnessManifest` / `safeParseHarnessManifest`, and the `HarnessManifest` type. No IO. | Zod and sibling vocabulary |
| `scripts/harness/harness-manifest-loader.ts` | Joining the two: `loadTypedHarnessManifest(repoRoot)` and `loadTypedHarnessManifestIfPresent(repoRoot)`. | both of the above |

**Import the loader.** That is the whole rule for new code:

```ts
import { loadTypedHarnessManifest } from "./harness-manifest-loader.js";

const manifest = loadTypedHarnessManifest(repoRoot);
for (const control of manifest.controls) {
  // control is a discriminated union over `kind`
}
```

Use `loadTypedHarnessManifestIfPresent` when the tree may legitimately carry no
manifest at all. It returns `undefined` for an absent file and still throws for
a present-but-invalid one.

## The generated lint-rule include

The manifest is assembled from two files, and `readHarnessManifest` is the only
place that knows it:

- `harness.controls.json` — hand-authored, owns every control kind **except**
  `lint-rule`;
- `harness.controls.lint-rules.generated.json` — generated by
  `scripts/harness/generate-lint-rule-controls.ts`, owns `kind: "lint-rule"`
  exclusively.

Lint-rule controls carry no authored information: identity and source are the
rule filename, and the enforcement command is whichever activation surface runs
the rule. Generating them into an include rather than rewriting the manifest in
place keeps the generator away from 2,800 lines of hand-authored controls it
would otherwise have to reformat and rewrite.

Anything reading the manifest through this module (or the loader above it) sees
one assembled `controls` array, include entries appended after the authored
ones. **Read it through the seam**: `scripts/harness/generate-harness-controls.ts`
had its own `readFileSync` and had to be moved onto `readHarnessManifest`, or
its generated inventory would have silently lost every lint rule.

A missing include is tolerated, because a reduced tree can legitimately carry a
root manifest and no include — most failure fixtures in
`scripts/tests/test-generate-harness-controls.sh` do, and each has to fail on
the defect it is testing rather than on the missing include. This is not about a
tree with *no* manifest: `readHarnessManifest` throws on the root read first, and
the lint-ratchet fixture below (which synthesizes no manifest) never reaches
these readers — it uses `harnessManifestPath` and its own `existsSync`. In the
real tree a missing include cannot pass silently:
`harness:check` rule parity fails for every registered `local/*` rule with no
control, and the generator's `--check` freshness gate fails on the missing
output. An include that exists but is malformed is a hard error.

The harness-check fixture carries an include of its own so the seam is exercised
end to end rather than only in unit tests: its `lint/local/fixture-rule` control
is authored in the fixture's `harness.controls.lint-rules.generated.json` and
nowhere else, and `scripts/tests/test-harness-check.sh` asserts the assembled
manifest reaches both the validator and the harness-controls doc generator, plus
the dropped-include and malformed-include failure modes.

## Why the leaf and the schema are separate

Not portability — **fixture copy closure**. `harness-manifest.ts` is copied
verbatim into two reduced trees:

- the lint-ratchet smoke fixture's portable runtime set
  (`PORTABLE_RUNTIME_FILES` in `scripts/tests/test-lint-ratchet.sh`);
- the harness-check fixture copy manifest
  (`scripts/tests/harness-check-fixture-manifest.generated.txt`). Its walkable
  entries are derived from the real import graph by
  `scripts/harness/generated-surface-dependencies.ts`; reasoned
  `generatedSurface.fixtureExtras` add runtime files the walker cannot infer.

Every import added to the leaf lands in both closures — both fixture sets
therefore also carry `scripts/lib/records.ts`, the leaf's one non-builtin
import. Keeping the leaf to that narrow set keeps those fixtures small, so the
Zod contract lives one layer up and only trees that actually validate shape copy
it.

## Division of labor

The parser owns **JSON shape and manifest-local assembly**: top-level fields,
the per-kind field inventory (strict keys, so an unknown field is a
registration typo), primitive field typing, control-id uniqueness, the
non-emptiness of legacy `slots`, and the ordered `verifySlotCatalog` /
`slotProfile` carriers. A successful parse resolves profiles immediately, so
every downstream reader still receives materialized `slots` arrays plus the
reasoned marker-bridge divergences that actually change bridge signatures.

Everything else stays with its consumer, keeping that consumer's aggregated,
test-pinned diagnostics authoritative:

| Concern | Owner |
|---|---|
| `commandPolicy` facet | `scripts/harness/command-policy-schema.ts` |
| `generatedSurface` facet | `scripts/harness/generated-surfaces.ts` |
| `hookWiring` facet | `scripts/harness/hook-wiring-schema.ts` |
| `skillWiring` facet | `scripts/harness/skill-inventory-schema.ts` |
| Materialized slot vocabulary — names, scripts, args, env, dynamic resolvers | `scripts/harness/verify-step-schema.ts` |
| Catalog/profile resolution, including non-empty selected modes and valid override targets | `scripts/harness/verify-step-programs.ts` |
| The four verify consumers' mandatory profile modes and reasoned marker-bridge divergence projection | `scripts/harness/harness-manifest-schema.ts` |
| Which other/adopter controls must declare materialized `slots` at all | Their owning consumer |
| Raw control field inventory and live-tree-free non-lint field diagnostics | `scripts/harness/control-field-validation.ts` |
| Anything compared against the live tree | `scripts/harness-check.ts` and its `registration-*` collectors |

Slot-program cardinality stays at the manifest seam because **nothing
downstream rejects an empty program.** A legacy `"slots": []` is rejected by
the carrier's `.min(1)`. Profile-backed gates cannot use that carrier because
their authored controls contain no array, so `verify-step-programs.ts` rejects
a selected mode that resolves to zero slots. Without those paired guards the
generator could render `MUSI_PRE_COMMIT_STEPS=()`, the marker-bridge subset
check would be vacuous, and `scripts/lib/verify-engine.sh` would write a SUCCESS
marker after iterating no checks.

The production ids `verify-wrapper/verify`, `verify-wrapper/verify-changed`,
`verify-wrapper/verify-parallel`, and `hook/pre-commit` are pinned to their
settled full/changed profiles during resolution. Other verify-wrapper and hook
controls may continue to author legacy materialized `slots`; the shared schema
keeps that adopter path intentionally.

So when you migrate a consumer, delete its hand-rolled controls-array check,
entry object-ness check, id-presence check and duplicate-id check — those are
the contract's now — and keep its semantic checks.

## The read tripwire

`scripts/harness/manifest-contract-check.ts` scans non-test TS/JS under
`scripts/` for imports of the leaf's read-capable exports
(`readHarnessManifest`, `loadHarnessManifest`, `harnessManifestPath`) and fails
`harness:check` in two directions:

- an importer that is not on the `MANIFEST_DIRECT_READERS` allowlist — the
  bypass regrowth the tripwire exists to stop;
- an allowlisted file that no longer imports one — a stale entry. **The list
  only shrinks.**

Importing `HARNESS_MANIFEST_FILENAME` alone is path-only and never trips it.
`import type` and inline `{ type ... }` specifiers are erased and stay exempt.

The tripwire is import-based and deliberately cooperative. It cannot see
shell/`jq` consumers: `scripts/ai-hooks/check-wiring.sh` parses the manifest
with `jq` on purpose, to validate committed hook configs *without trusting the
generator*. That independence is the point, so it is out of scope by design.

### Migrating a reader

1. Replace the leaf import with `loadTypedHarnessManifest` from the loader.
2. Delete the shape checks the contract now owns; keep the semantic ones.
3. Delete the file's `MANIFEST_DIRECT_READERS` entry.
4. Re-run the gates below. If the consumer is a `generatedSurface` source, its
   walkable fixture dependencies are derived automatically. The trigger check
   still names exact `triggerPaths` entries to add. Add a `fixtureExtras` entry
   only for a non-import runtime dependency, with a one-line `reason`, then
   re-run `bun run verify:steps`; residue hygiene rejects import-closure echo.

Fixture derivation is an optimization layered additively over declaration and
validation, not a replacement for that contract. The explicit
`MUSI_HARNESS_CHECK_ALLOW_NO_FIXTURE_PATHS=1` permission has two narrow,
structurally distinguished cases:

- A reduced tree with **no** `fixtureExtras` declarations consumes its copied,
  precomputed projection. Both entry points return before loading the walker,
  which is how the harness-check smoke tree remains runnable without its
  TypeScript dependency.
- A walker-less repository may declare its **full** copy list as reasoned
  `fixtureExtras`. Both entry points first try to load the walker; only when the
  walker module is unavailable does the permission select the degenerate
  `empty closure ∪ fixtureExtras` projection. File checks and projection
  freshness still run over those declarations. Closure-based residue and
  trigger checks are necessarily unavailable in that mode.

When declarations exist and the walker loads, the permission changes nothing:
the generator renders the derived union and `harness:check` performs file,
residue, trigger-closure, and projection-freshness validation. This makes an
inherited smoke environment variable unable to disarm validation in the real
tree. The smoke script also explicitly removes the variable from its later
real-tree invocation as a process-boundary regression guard.

```bash
# the tripwire, the closure checks, and every live-tree comparison
bun run harness:check
# focused
bun run test:scripts:file -- scripts/harness/manifest-contract-check.test.ts
# the reduced fixture trees the closure checks describe
bash scripts/tests/test-harness-check.sh
bash scripts/tests/test-lint-ratchet.sh
```

### When not to migrate

Two readers stay on the allowlist as `sanctioned-reader`, each with its reason
recorded inline. They are the shape of the exceptions worth making:

- **`generate-harness-controls.ts`** owns the one-pass granular registration
  report. It uses the whole-manifest parser and fails closed when authored slot
  profiles need resolution; otherwise its raw fallback preserves the granular,
  per-control diagnostics and narrows successful records through the loose
  `categorizedControlFieldsSchema`.
- **`check-registry.ts`** ships in the lint-ratchet portable runtime copy set and
  runs against trees with partial or absent manifests. Importing the typed
  parser would expand that copy closure and couple every `lint:ratchet`
  invocation to whole-manifest validity.

The test: does the throwing whole-manifest parse either destroy a deliberately
worded diagnostic or reach a tree that cannot satisfy the whole contract? If
neither, migrate.

## External schema

Everything above is for in-repo contributors. Someone outside the repo — an
adopter who copied `harness.controls.json`, or tooling generated against it —
gets `schemas/harness.controls.schema.json`, a JSON Schema (draft 2020-12).
`harness.controls.json` carries a `"$schema": "./schemas/harness.controls.schema.json"`
pointer, so editors pick it up with no configuration, and any generic validator
works:

```bash
npx ajv-cli validate -s schemas/harness.controls.schema.json -d harness.controls.json --spec=draft2020
```

It is **generated**, by `scripts/harness/generate-manifest-json-schema.ts`:

```bash
bun run harness:manifest-schema         # refresh
bun run harness:manifest-schema:check   # freshness gate, also run by harness:check
```

Derivation is one-way. The Zod contract above stays the single source of truth
and the schema is a `z.toJSONSchema` projection of it, so the two cannot
disagree; never hand-edit the output. The emitter imports only
`harness-manifest-schema.ts` — not the manifest, and not the leaf — so
publication stays outside the fixture-copy closure and the
`MANIFEST_DIRECT_READERS` seam. Keys are codepoint-sorted on the way out so the
freshness gate fires on contract diffs rather than on Zod's traversal order.

Two things to know before trusting it as a gate:

- It publishes strictness only at the levels the Zod contract owns — root keys,
  per-kind field inventories, primitive typing, legacy `slots` non-emptiness,
  and catalog/profile carrier shape. Facet interiors and command vocabulary are
  deliberately open, per the division-of-labor split above. The schema's own
  root `description` says all of this; read it first. Resolution rules such as
  profile-mode pinning and non-empty selected programs remain repo-side.
- Checks JSON Schema cannot express stay repo-side: control-id uniqueness,
  `repairCommand` required exactly when `repairKind` is `codemod`, the slot
  vocabulary, and every live-tree comparison. **A document this schema accepts
  can still fail `bun run harness:check`.**

There is no `formatVersion` and no bump policy. The schema file is gated for
freshness and committed, so its git diff between two pins *is* the compatibility
signal.
