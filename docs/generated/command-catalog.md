# Command Catalog

> Generated by `scripts/harness/generate-command-catalog.ts`. Do not edit by hand.
> Refresh with `bun run docs:command-catalog`.

Every package.json script in this repository: 193 keys across 7 tracked manifests, grouped by name family. This page is the authority for *what a command is for*; `README.md` and `AGENTS.md` cover the everyday subset and link here for the rest.

Nothing here is hand-written per row. 85 commands project their purpose from the harness control that registers them (see [harness-controls.md](./harness-controls.md) for the full principle, source file and repair path); the remaining 108 project it from the `commandCatalog` section of `harness.controls.json` — the scripts no control reaches, plus the few aggregating commands whose controls are the rules they run rather than descriptions of the command. `bun run harness:check` fails when any script in any tracked manifest has neither — which is what stops a new command from landing undocumented.

**Where to run it from.** The `Command` column carries the full form. Root scripts are plain `bun run <script>`; workspace packages need `--filter <package>` because a bare `bun run` resolves against the nearest `package.json`; anything outside the workspaces needs `--cwd`.

**Effect** is what running the command does to your tree:

- `check` — Reports or fails. Writes nothing you have to review.
- `repair` — Rewrites tracked files to fix what a check reports.
- `generator` — Rewrites a committed generated artifact from its source.
- `ci-primitive` — A build/test/typecheck step the gates and CI compose from.
- `lifecycle` — Runs from a package-manager or git hook, not by hand.
- `dev-utility` — Interactive or operator tooling. No gate depends on it.
