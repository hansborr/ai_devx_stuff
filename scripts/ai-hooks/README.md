# AI Hook Adapters

This directory owns the shared hook bodies used by the Claude, Codex, and
Copilot adapters. The architecture-level inventory is in `docs/ai-harness.md`;
this file is the implementation and manifest authoring reference.

## Shim Contract

Files under `.claude/hooks/`, `.codex/hooks/`, and `.copilot/hooks/` are thin
adapters and are **generated projections**: `bun run harness:wiring`
(`scripts/harness/generate-hook-wiring.ts` with `scripts/harness/hook-shims.ts`
and `hook-shim-files.ts`) renders every shim from the `hookWiring` entries in
`harness.controls.json`, right alongside the three hook configs. Do not edit a
shim by hand — `bun run harness:wiring:check` (run by `harness:check` and the
commit gates) byte-compares each shim, asserts regular-file type and the
executable bit, rejects symlinks, and flags orphan `*.sh` files and stray
non-file `*.sh` entries in the three owned directories; write mode prunes
orphans, so removing a manifest entry reconciles its shim away. Both modes
fail closed if an owned directory path is itself a symlink or non-directory.
Note: the generator prunes regardless of `check-wiring.sh`'s declared-unwired
exemption list (`DECLARED_UNWIRED_ADAPTERS_FILE`, kept empty today), so if
that list is ever populated the two must be reconciled or `harness:wiring`
will delete the exempted shim. A shim resolves the repo root, translates
harness-specific payload details, and `exec`s (or dispatches) one shared body
from `scripts/ai-hooks/`. Keep behavior in the body unless the harness shape
forces the adapter to differ.

Everything a shim needs is derived from existing manifest fields: the shim
path comes from the harness `command` (only the two recognized command shapes
are accepted, and the target must be a single safe `<name>.sh` segment inside
that harness's own adapter directory), the exec target from `hookWiring.body`
(confined to `scripts/ai-hooks/<safe-name>.sh`), and the template from the
adapter directory. Unrecognized shapes, traversal, collisions, and unknown
Copilot matcher/event combinations fail generation instead of guessing —
notably copilot `Stop`, because `ai_copilot_dispatch` has no stop mode.

`check-wiring.sh` stays as the generator-independent semantic backstop: every
generated-config adapter must resolve exactly one canonical body.
`hookWiring.body` declares that shared body explicitly; the checker binds each
generated harness command back to its manifest control before validating the
adapter edge. It does not infer policy from adapter basenames or the control's
informational `source`. Unreferenced adapter files are rejected unless
temporarily inventoried in that checker for a separately owned cleanup.

The `harness:check` smoke fixture (`scripts/tests/test-harness-check.sh`)
obtains its two `.claude/hooks/` shims as declared copies: they stay listed in
the generator record's reasoned `generatedSurface.fixtureExtras`, so the
fixture copies the committed generated bytes and its own `harness:wiring:check`
run validates them against the fixture manifest.

The `REPO_ROOT` a shim derives from its own file location identifies the
checkout that *registered* the hook — use it only to source the body and its
libraries. It is NOT the checkout a command operates on: a session parked at one
worktree routinely commits in another via `cd <wt> && git commit` or
`git -C <wt> commit`. Anything keyed to where the work lands — HEAD snapshots,
per-worktree locks, branch policy, the success summary — must resolve the target
from the *invocation* context (`ai_resolve_target_dir` reads the command's
leading `cd`/`git -C` forms, then the payload `cwd`), not from the hook file's
home. Keying those on `REPO_ROOT` makes every worktree commit look like it
landed in the main checkout (false "no commit landed", mis-keyed locks).

Codex shims use the same template but fall back to `/workspace`. The Bash-surface
aggregates (`bash-pre-tool-use.sh` and `bash-post-tool-use.sh` in this
directory) group command policy, commit state, and `bun run` cache behavior
behind one hook entry per event; `.codex/hooks/pre-tool-use.sh` and
`.codex/hooks/post-tool-use.sh` exec them directly.

Copilot shims are translation adapters rather than pure exec shims: Copilot
delivers camelCase payloads (`toolName`, `toolArgs` as a JSON string, no
per-call tool id), and expects event-specific response JSON
(`permissionDecision` on preToolUse, `additionalContext`/`modifiedResult` on
postToolUse). `copilot-adapter.sh` owns that
translation: `ai_copilot_dispatch <mode> <surface> <body>` filters by toolName
after native matcher selection, normalizes the payload — synthesizing a
`tool_use_id` from the session id plus toolArgs so pre/post state correlates —
runs the shared body, and translates its response. The `<mode>` and
`<surface>` arguments are derived by the shim generator from the manifest
event and Copilot matcher, never authored by hand. The extra toolName filter is
defense in depth against config drift. Copilot preToolUse command hooks are
fail-closed on crashes, so dispatch always exits 0 and unparseable payloads
translate to "no opinion". Copilot only loads repo hooks from folders the user
has trusted in `~/.copilot/config.json`.

## Shared Bodies

`common.sh` owns the vendor payload boundary — reading a tool payload and its
response blob into a neutral shape — the response emissions every adapter uses,
and small primitives no other file owns. Parsing one specific tool's text is not
its job and has been moved out: git command classification to `git-classify.sh`,
and inferring a wrapped `bun run`'s exit code from bun's own output to
`cache.sh`, beside the marker family that consumes it. Nor is speaking one
vendor's response dialect: `ai_claude_updated_command` /
`ai_claude_result_command`, the two Claude-native shapes, now live in
`claude-adapter.sh` beside `copilot-adapter.sh`, sourced by the three Claude
hook bodies that emit them. `edited-paths.sh` is the single translation point
for edited file paths: `ai_edited_payload_paths` reads Claude file paths and
Codex apply_patch headers, while callers decide how to resolve and filter them.
`policy.sh` owns command policy decisions. It is a facade over four bounded
modules it sources as siblings: the four extracted responsibility groups listed
below moved out of it verbatim, while the predicates and helpers that stayed —
including several the `commandPolicy` manifest names — remain defined in the
facade itself. Moving code between the facade and a module is a pure
relocation; the shell corpus is the parity gate.

| Module | Holds |
|---|---|
| `command-normalize.sh` | `ai_strip_noncommand_text`, the heredoc-aware view of a command |
| `command-paths.sh` | the shell path tokenizer and redirect/sed/tee/copy write-path extraction |
| `git-classify.sh` | the commit lexer, both `git commit` classifiers, checkout target resolution, and the git deny predicates |
| `policy-eval.sh` | `ai_policy_decision` and `ai_policy_rule_matches` — the rule loop and its decision record; `ai_policy_violation_reason` is the compatibility projection |

Sourcing is fail-closed. `policy.sh` tracks whether every module loaded and, at
the foot of the file, denies every command when one did not, naming the module
set in its reason so the agent it just locked out knows which files to restore.
Without that, a checkout missing a module would degrade silently: the vanished
function reads as "command not found", the scan continues on a partial policy,
and the gate lets the command through. `common.sh` deliberately does not source
these modules — every live caller of the moved helpers already sources
`policy.sh`, and the corpus copies `common.sh` into fixture repos without its
siblings.

`policy.sh`'s ordered hard-deny **rule set** is declarative data: one row per
rule in the root `commandPolicy` array of `harness.controls.json`, rendered by
`bun run harness:command-policy`
(`scripts/harness/generate-command-policy.ts`) into the committed
`policy-rules.generated.sh` fragment that `policy.sh` sources. A row carries the
rule id, its 1-based `order` (scan order — the first matching `hard` row wins;
otherwise the first matching `soft` row advises), its `class`
(`hard`, or the latent `soft` guidance class), its `scope` (`command`, or
`checkout` when the verdict depends on the resolved target checkout), the
message it emits, its ordered matchers (a regex `pattern`, a `grep -qF`
`literal`, or a named shell `predicate` whose body lives somewhere in the
command-policy shell module set), and its Claude-native projection. Pattern
placeholders follow the shell expander's contract: `${AI_POLICY_GIT_CMD}` may
occur once at the start and `$AI_POLICY_CMD_END` once at the end; manifest
validation rejects any other placement before generation.

That last field is total over every row: a row either lists the
`.claude/settings.json` `permissions.deny` matchers it contributes, or records
why it is deliberately shared-policy-only. `permissions.deny` is exactly those
projected matchers, in rule order and then matcher order, and
`bun run harness:command-policy:check` (run by `harness:check`) fails when the
committed array drifts from that projection. Checkout-scoped rules cannot be
projected at all — a static matcher cannot see a branch — and `git-stash` stays
an explicit non-projection because a native deny fires before the shared hook
can supply its contextual reason.

`ai_policy_decision <record-name> <command> [work-root]` is the single policy
boundary. The caller passes the name of an associative array; names beginning
with `__ai_policy_boundary_` are reserved for the boundary's implementation.
The function replaces the array with exactly these fields:

| Field | Contract |
|---|---|
| `verdict` | `block` for a matched `hard` row, `advise` for a matched `soft` row, or `allow` when no row matches |
| `ruleId` | The matched manifest rule id; empty for `allow`; reserved `policy-rule-data-error` / `policy-module-data-error` for the two fail-closed recovery paths |
| `message` | The predicate-owned or generated rule message; empty for `allow` |

The array boundary preserves message bytes without a delimiter or JSON parse in
the hot path. It is also the interface any future typed policy model must
match: the same three named fields, verdict vocabulary, precedence, rule id,
message, and reserved fail-closed records. There are no `soft` rows today; this
seam does not add one. If one is added, its first match is provisional advice:
scanning continues, the first matching `hard` row wins, and advice is returned
only when no hard row matches. The adapters map `advise` according to their
existing contracts: Claude replaces the command with successful guidance, the
aggregate Codex/Copilot pre-hook keeps its existing block policy, and an
executing-hook preflight runs only `block` through `ai_emit_block`. Every
consumer treats a verdict outside the three-value vocabulary as a fail-closed
rule-data error.

`ai_policy_decision` walks `AI_POLICY_RULE_IDS` in manifest order and dispatches
each generated matcher through a direct, non-subshell
`ai_policy_rule_matches` call: regex rows use
`ai_policy_has_command`, literals retain fixed-string matching, and named
predicates keep their procedural bodies in the command-policy shell module set
— the `policy.sh` facade plus the bounded modules it sources. The generator
scans that whole set for every manifest-named predicate and haystack transform
(`AI_HOOKS_COMMAND_POLICY_SHELL_PATHS` in `scripts/harness/harness-paths.ts` is
the list), so a name defined in none of them still fails generation before a
stale fragment can render. Predicate-owned messages flow through a caller-owned
message variable without changing their bytes;
other rules answer from the generated message map. The checkout-scoped
`git-commit-on-main` rule deliberately stays last so a more specific command
violation wins first. `ai_policy_violation_reason` remains a compatibility
projection of this record for shell-corpus and out-of-tree callers that still
consume its status/stdout API. The fragment also defines the public
`AI_POLICY_*` reason aliases used by the shell corpus, so messages have one
authored copy. `test.sh` pairs every projected
native matcher with its exact command-policy rule and a shared-policy fixture,
and pairs every intentional non-projection with a contextual fixture; stash and
the staged-only restore exclusion are pinned explicitly.

The generated policy-reference table in `docs/generated/harness-controls.md`
lists every rule in evaluation order with its native matcher projection or its
explicit non-projection reason.

The marked porting-knob block near
the top of `common.sh` owns repo-specific shell default literals; `cache.sh`
derives shared state directories from those defaults and owns marker helpers.

Most bodies should work for both harnesses once paths flow through
`ai_edited_payload_paths` and `ai_resolve_edited_payload_path`. Harness-specific
gaps are allowed only when they are deliberate and documented in
`harness.controls.json` with `hookWiring.notes.<harness>`, so the generated
controls doc explains why an adapter is absent.

## Locking

The Claude `bun-run-quiet` wrapper keeps a worktree-scoped lock because it
protects shared Bun result markers and log files. Its default lock wait uses the
same interactive budget as verification (`MUSI_INTERACTIVE_TIMEOUT`, then
`MUSI_GATE_INTERACTIVE_TIMEOUT_DEFAULT`), and time spent waiting is subtracted
from the post-lock watchdog. `AI_BUN_LOCK_WAIT` and `AI_BUN_TIMEOUT` remain
overrides; the lock wait is capped to the total hook budget so one wrapper
invocation does not consume multiple interactive windows.

Commit queueing has two layers. `.husky/pre-commit` fail-fasts on the
worktree-scoped verify lock, then waits on a Git-common-dir commit queue lock so
sibling worktrees sharing the same repository serialize pre-commit checks across
Claude, Codex, and human commits. Claude's executing `git-commit-quiet` wrapper
also takes that Git-common-dir queue around the full child `git commit`, while
keeping its worktree-scoped lock nonblocking for same-worktree duplicate
commits.

## `hookWiring`

`harness.controls.json` is the source for `.claude/settings.json` hooks,
`.codex/hooks.json`, and `.github/hooks/copilot.json`.
`scripts/harness/hook-wiring-schema.ts` is authoritative for the schema.

`event` is the harness event name; `scripts/harness/hook-wiring-schema.ts`
holds the full supported enum. The events this repo wires today are
`SessionStart`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Stop`, and
`SubagentStop`. For Copilot the generator renders `PreToolUse`/`PostToolUse`
as `preToolUse`/`postToolUse`. No stop hook targets Codex or Copilot, so
`Stop` and `SubagentStop` are wired for Claude only (as user-visible
`systemMessage`s) and no `agentStop` entry is generated.

`body` is the repo-relative canonical shared body that every wired adapter for
the control must invoke. Keep it tied to the control and event when changing
adapter commands; `source` describes the control for inventory purposes and is
not the executable-body contract.

`surface` is the optional neutral tool surface the hook policies — `bash` or
`edit`. It may be declared only on the tool-use events
(`PreToolUse`/`PostToolUse`/`PostToolUseFailure`), whose matchers are pure
adapter syntax; a `SessionStart` matcher such as `startup|resume|compact` is
authored policy and is rejected if it claims a surface. Declaring `surface`
opts every binding of the control into canonical projection: the schema asserts
that each `matcher` byte-equals `CANONICAL_MATCHER[harness][surface]` and each
`command` byte-equals the canonical projection of `body` into that harness's
adapter directory, printing the expected string when they diverge. Omitting it
on a `PreToolUse`/`PostToolUse` binding that already uses canonical matcher
syntax trips a tripwire demanding either the declaration or a
`notes.<harness>` explanation — that is how the four Bash aggregators, which
route a shared body through one fixed shim name, stay expressible.

`matcher` is the harness matcher for a command group. It is required for
`PreToolUse` and `PostToolUse` on Claude, Codex, and Copilot; `Stop` hooks omit
it. On a control that declares a `surface` it is not free text: it is a
canonical-checked copy of the projection tables in
`scripts/harness/hook-wiring-schema.ts`, so fix drift by rewriting the manifest
copy, and change the table only for a deliberate adapter-syntax change. Copilot
CLI 1.0.68 has been live-tested honoring native matchers, and
`.copilot/hooks/` adapters still filter by toolName as defense in depth.

`timeout` is an optional positive integer in seconds. Use it when the harness
needs a bounded runtime for slower hooks such as Prisma generation. Copilot
renders it as `timeoutSec`.

`order` is a positive integer used by the generator to sort hooks within an
event. Lower order runs first; ties sort by control id.

`harnesses` contains the concrete `claude`, `codex`, and/or `copilot` command
entries. A Codex command must include `statusMessage`; Claude commands may omit
it, and Copilot commands must omit it. Each `command` follows one of two
templates — `bash $CLAUDE_PROJECT_DIR/.claude/hooks/<basename of body>` for
Claude, `bash "$(git rev-parse --show-toplevel)/.<codex|copilot>/hooks/<basename
of body>"` for the others — and is canonical-checked against `body` whenever
the control declares a `surface`. Unknown fields on either the facet or a
command entry are rejected as registration typos rather than ignored.

`notes.<harness>` explains a deliberate missing harness target, or a wired
binding whose command is not the canonical projection of `body`. Every hook
must either wire each known harness or explain the omission, and every wired
binding must either match the projection or carry its own note.

## Verify Slots

The root `verifySlotCatalog` declares one ordered full/changed program, and the
four gate controls select it with thin `slotProfile` records. The typed
manifest parser resolves those profiles to materialized slot arrays before the
generator emits `scripts/verify/steps.generated.sh`.
`scripts/harness/verify-step-schema.ts` is authoritative for the resolved slot
schema:

```json
{
  "name": "scripts",
  "full": { "script": "test:scripts" },
  "changed": {
    "kind": "replace",
    "reason": "Changed mode classifies script-smoke inputs.",
    "slot": {
      "script": "test:scripts:changed",
      "dynamic": "staged-script-classifier",
      "condition": "when changed inputs require script smoke"
    }
  }
}
```

`name` is the stable slot id. `script` must be a package.json script name; the
generator renders it as `bun run <script>`. `args` and `env` are optional command
tokens and environment entries. `dynamic` selects a built-in resolver such as
`precommit-test-timings` or `staged-script-classifier`. `condition` is
documentation-only and renders into `docs/generated/harness-controls.md`.
`fastCommitSkip` marks a pre-commit slot that fast-commit mode drops.
`produces` and `requiresArtifact` name a build artifact from the vocabulary in
`scripts/harness/verify-step-artifacts.ts` (today: `dist-outputs`); the parallel
runner defers a requiring slot only while that artifact's probe reports it
missing. Both belong on the catalog entry rather than a `full` / `changed` /
override body, so a replacement command can never drop its slot out of the
scheduler's deferral set, and generation rejects a program whose requiring slot
has no producing slot beside it.
Every catalog entry must explicitly inherit, replace with a reason, or omit
with a reason in changed mode; profile overrides also require a reason.

## Porting This

These values are Musi-specific and should be changed when adapting the setup to
another repo:

- `repo-root-fallback` — `/workspace` fallbacks in the generated shim
  templates (`scripts/harness/hook-shims.ts`) and `common.sh`'s
  `ai_repo_root`.
- `canonical-adapter-matcher` — the per-harness tool-surface matcher syntax
  (`Bash` / `Edit|Write` / `apply_patch` / `bash|powershell` / `create|edit`)
  that `hook-wiring-schema.ts` asserts every `surface`-declaring binding against.
- `canonical-adapter-shim-dir` — the `.claude`/`.codex`/`.copilot` adapter
  directories in `hook-wiring-schema.ts`'s canonical command projection; they
  mirror `HOOK_SHIM_DIRS` in `hook-shims.ts`, which owns the generator's write
  targets.
- `hook-state-paths` — `/tmp/musi-*` state and result paths. Repo-specific
  literals live in `common.sh`'s marked block; `cache.sh` consumes them while
  preserving the existing environment overrides.
- `bun-command-runner` — the `bun run` command assumption in
  `verify-step-schema.ts` `verifyStepCommandTokens`.
- `verify-consumers` — the hardcoded verify `CONSUMERS` table in
  `generate-verify-steps.ts` and its aligned profile/marker ids in
  `harness-manifest-schema.ts`; adding a consumer also means catalog profile,
  manifest, and wrapper changes.
- `test-changed-classifiers` — the package, ESLint, config, and scripts layout
  classifiers in `test-changed.sh`.
- `pre-push-scope-trigger` — the whole-file inputs
  (`sensor-near-duplicates.baseline.json`, `drift-ai.config.json`) and the
  scanner extension source rendered into the `.husky/pre-push` boundary trigger
  by `scripts/harness/pre-push-scope-trigger.ts` (`bun run
  harness:pre-push-trigger` regenerates).
- `baseline-restore-allowlist` — the generated baseline paths accepted by
  `restore-generated-baseline-stage.sh`.
- `wrapped-bun-scripts` — the wrapped-script whitelist in `policy.sh`: a
  hand-maintained heredoc plus the generator-contributed slices rendered into
  `classified-bun-scripts.generated.sh` from `harness.controls.json`
  `generatedSurface.bunHook` facets (`bun run verify:steps` regenerates).
- `command-policy` — the ordered hard-deny rule set and its Claude-native
  permission projection: rows in the root `commandPolicy` array of
  `harness.controls.json`, rendered into `policy-rules.generated.sh` (`bun run
  harness:command-policy` regenerates). This is the knob an adopter turns for
  "this deny list, my commands"; the shell predicates a row names stay in
  `policy.sh`.
- `protected-files` — the advisory/deny path table in `protected-files.sh`.
  The repo-root `.allow-protected-edits` marker is repo-wide; create it only for
  deliberate protected-file maintenance and remove it after use.
- `suppression-allowlists` — the repo-specific suppression exceptions now
  stored in `scripts/data/eslint-disable-broad-allowlist.txt` and
  `scripts/data/ts-nocheck-allowlist.txt`.
- `generated-surface-freshness` — the generated input/output/check registry:
  `generatedSurface` facets on `harness.controls.json` control records, loaded
  and rendered by `scripts/harness/generated-surfaces.ts`.
- `fixture-copy-manifest` — the smoke-fixture copy closure rendered into
  `scripts/tests/harness-check-fixture-manifest.generated.txt` from the static
  import closure plus reasoned `generatedSurface.fixtureExtras` (`bun run
  verify:steps` regenerates); `harness:check` rejects derivable residue.
- `environment-prefixes` — the `MUSI_*` and `AI_*` environment variable
  prefixes used by wrappers, caches, hooks, and tests.

### Not Configurable Without Code Changes

Some harness assumptions are structural rather than manifest-level knobs:

- The manifest path is fixed at repo-root `harness.controls.json`.
- Hook wiring outputs are fixed at `.claude/settings.json`,
  `.codex/hooks.json`, `.github/hooks/copilot.json`, and the generated shims
  under `.claude/hooks/`, `.codex/hooks/`, and `.copilot/hooks/`.
- Verify step generation assumes `scripts/verify/steps.generated.sh` and the
  `scripts/verify/` wrapper layout.
- Hook bodies and smoke tests assume Bash; several hooks and checks also assume
  `jq`.
- Generated verify steps assume `bun run`.
- Shared hooks assume repo-relative `.claude/hooks/`, `.codex/hooks/`,
  `.copilot/hooks/`, and `scripts/ai-hooks/` adapter/body layout.
